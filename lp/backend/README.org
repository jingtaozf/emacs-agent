#+TITLE: lp/backend — Concrete Backends (Agent + Multiplexer + Pi)

Every module here is a concrete *backend* — an implementation that
satisfies a protocol declared in =lp/sdk/code-agent-backend.org=.  The
frontend (=lp/org/=, =lp/chat/=) NEVER branches on backend type;
dispatch flows through =cl-defmethod= on the backend instance.

Three sub-families live side-by-side: ACP agents (stdio JSON-RPC),
multiplexer drivers (cmux / tmux), and the Pi RPC backend.

* Modules

** Agent family (ACP — JSON-RPC over stdio)

| File | Role |
|------+------|
| [[file:code-agent-jsonrpc.org][code-agent-jsonrpc.org]] | Pure JSON-RPC 2.0 transport class.  Every ACP-derived backend builds on this. |
| [[file:code-agent-acp.org][code-agent-acp.org]] | Generic Agent Client Protocol backend.  Drives spawn → initialize → authenticate → session/new → session/prompt for any ACP-conforming agent. |
| [[file:code-agent-acp-gemini.org][code-agent-acp-gemini.org]] | Profile: Google Gemini CLI (=--experimental-acp= + 3 auth methods). |
| [[file:code-agent-acp-codex.org][code-agent-acp-codex.org]] | Profile: OpenAI Codex via the =codex-acp= shim binary. |
| [[file:code-agent-acp-opencode.org][code-agent-acp-opencode.org]] | Profile: OpenCode direct-ACP (sidesteps the cmux-profile config-mutation path). |

** Multiplexer family (terminal driver + workspace-bridge)

| File | Role |
|------+------|
| [[file:code-agent-multiplexer.org][code-agent-multiplexer.org]] | Abstract base + Protocol 2b generics (send-text / capture-screen / wait-for-ready).  cmux and tmux subclass this. |
| [[file:code-agent-cmux-backend.org][code-agent-cmux-backend.org]] | cmux concrete backend (macOS-native, Swift+Ghostty, =cmux= CLI). |
| [[file:code-agent-tmux-backend.org][code-agent-tmux-backend.org]] | tmux concrete backend (cross-platform, =tmux send-keys / capture-pane / pipe-pane=). |

** Pi family (pi.dev RPC backend + UI bits)

| File | Role |
|------+------|
| [[file:code-agent-pi-backend.org][code-agent-pi-backend.org]] | Pi RPC backend — pi.dev as an alternate LLM provider; auto-loaded. |
| [[file:code-agent-pi-extensions.org][code-agent-pi-extensions.org]] | TypeScript Pi-side extensions tangled to =~/.pi/agent/extensions/{emacs-mcp,doom-loop}.ts= — emacs-mcp closes the MCP loop so Pi can call Emacs tools; doom-loop catches token-/tool-repetition loops natively. |
| [[file:code-agent-pi-ui.org][code-agent-pi-ui.org]] | Optional Pi-specific UI affordances (status surface, completion bridge). |

* Read order

1. [[file:code-agent-multiplexer.org][code-agent-multiplexer.org]] or [[file:code-agent-acp.org][code-agent-acp.org]] first
   depending on which family you're touching.  Both are the abstract
   base of their branch; concrete subclasses inherit ~80% of their
   shape from these.
2. The concrete subclass next — cmux/tmux/Gemini/Codex/OpenCode.
3. [[file:code-agent-jsonrpc.org][code-agent-jsonrpc.org]] when investigating ACP wire-level bugs.
4. The Pi family stands alone — load order is independent of the
   ACP/multiplexer branches.

* Boundaries

- /backend/ → /sdk/: every module here =require=s
  [[file:../sdk/code-agent-backend.org][code-agent-backend.org]] for protocol generics.  Adding a new
  backend means adding a =cl-defstruct= here and =cl-defmethod=
  implementations of the relevant generics — nothing in /sdk/ or the
  frontend changes.
- /backend/ → /org/: frontend modules in /org/ never call into a
  concrete subclass directly; they call generics from /sdk/.  This
  is the rule that makes new backends drop in.
