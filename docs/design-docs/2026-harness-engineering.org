*Root cause of fragility*: The entire HTTP->JSON-RPC->dispatch->tool->response
pipeline has zero unit tests. Only state-preservation, mode-line, and
report-invocation have coverage. The core request handling is a black box.

* Design Principles

1. *Test the seams, not the plumbing* -- mock =process-send-string= to verify
   HTTP output format; mock =ws-body= to inject requests. No real HTTP server
   needed for unit tests.

2. *One test file per layer* -- keep tests focused:
   | Layer | Test File | What It Tests |
   |-------+-----------+---------------|
   | Protocol | =test-mcp-protocol.el= | dispatch, initialize, tools/list, tools/call |
   | Handler | =test-mcp-eval-handler.el= | evalElisp handler edge cases |
   | HTTP | =test-mcp-http.el= | request parsing, response format, error codes |
   | Lifecycle | =test-mcp-lifecycle.el= | start/stop, tool registration |

3. *FIX: messages on every failure* -- consistent with harness engineering.

4. *No real server in unit tests* -- all tests work with mocked process objects.

* F15: Centralized Session Cleanup

The core architectural fix. 7 code paths currently perform session cleanup
with hand-picked subsets of 8 operations. 3 paths are severely incomplete
(cancel-all, recover-not-found, loop-abort).

*Root cause*: No shared cleanup abstraction.

*Design*:
- NEW =claude-org--cleanup-session= -- single function, fixed operation order
- NEW =claude-org--cleanup-queued-blocks= -- extracted queue cleanup helper
- Refactor all 7 callers to delegate to =cleanup-session=

| Caller | Before | After |
|--------+--------+-------|
| handle-complete | 15 lines manual | =cleanup-session= + dequeue |
| insert-error | 20 lines manual | =cleanup-session= + insert |
| cancel | 25 lines manual | backend-cancel + msg + =cleanup-session= |
| cancel-all | 10 lines (incomplete!) | per-session =cleanup-session= |
| recover (limit) | redundant double-calls | delegates to insert-error |
| recover (not-found) | 3 lines (incomplete!) | =cleanup-session= |
| loop-abort | 2 lines (incomplete!) | =cleanup-session= |

Tests: ~12 in =test-claude-org-cleanup.el=

* Docs-Centric Knowledge Architecture

** Goals

- SDD story outputs (research, specs, features) persist in =docs/= as the system of record
- New conversations can discover and build on prior stories' findings
- =CLAUDE.md= remains a ~100-line TOC pointing to deeper docs
- Cross-story knowledge sharing via aggregated product-specs
- Mechanical enforcement: structural tests verify INDEX freshness and completeness

** Non-Goals

- Removing SDD workflow from the notebook (it stays for active work)
- Automating doc-gardening agent (future work)
- Changing the SDD prompt/tag system (=:sdd:=, =:research:=, etc.)
- Migrating all 76 existing SDD sections retroactively

** Proposed Solution

*** 1. New docs/ subdirectories

| Directory | Purpose | Populated by |
|-----------+---------+--------------|
| =docs/design-docs/= | Specs from SDD stories | SDD =:spec:= phase |
| =docs/research/= | Research outputs | SDD =:research:= phase |
| =docs/product-specs/= | Living specs aggregated across stories | Manual or post-SDD |
| =docs/references/= | External knowledge, API docs | Any time |

Each subdirectory has an =INDEX.md= serving as discoverable TOC.

*** 2. INDEX.md Format

Each INDEX.md is a table that agents can scan quickly:

* Goals

- Move research output, spec, and features from notebook subsections to =docs/= folder
- Make =docs/= the *single source of truth* for all SDD artifacts
- Simplify notebook SDD structure to only System Prompt + Workflow sections
- Enable cross-story knowledge sharing (all stories share =docs/= folder)
- Follow OpenAI's progressive disclosure: =CLAUDE.md= as TOC -> =docs/= as detailed content
- No backward compatibility needed -- clean break from current notebook-centric approach

* Non-Goals

- Backward compatibility with existing notebook SDD sections
- Migrating existing 76+ SDD sections to docs/ folder (historical, leave as-is)
- Auto-syncing between notebook and docs/ (single truth = docs only)
- Wiki-style cross-linking or search engine over docs/
- Complex metadata schemas or frontmatter beyond simple org properties

* Proposed Solution

** 1. Simplified Notebook Structure

SDD stories in the notebook reduce from 5 sections to 2:

| Before (Current) | After (New) |

| Features :features: | REMOVED -- lives in =docs/design-docs/= (as section) |

The notebook becomes *pure interaction space*: write instructions, execute queries,
read streaming responses. All persistent knowledge goes to =docs/=.
