* Context

The project drives AI coding agents from Emacs through two fundamentally
different wire models:

1. *JSON-stream over stdio* — the CLI subprocess emits newline-delimited
   JSON; Emacs reads token-by-token into the response section. Used by
   Claude Code (=--output-format stream-json=) and by three ACP agents
   (OpenCode, Gemini, Codex) speaking JSON-RPC 2.0.
2. *Terminal multiplexer* — the CLI runs inside a shell pane managed by
   a multiplexer (today only cmux); Emacs types prompts into the pane
   and a Python =workspace-bridge= writes response text back into the
   org buffer through MCP callbacks.

Today the first family has a proper protocol (=claude-agent-backend-query=
et al. dispatched polymorphically via =cl-defgeneric=); the second family
is a ~1880-line ad-hoc module (=code-agent-org-cmux.org=) that the frontend
branches into via =(string-equal CLAUDE_BACKEND "cmux")= checks at six
call sites.

*Catalysts for fixing this now*:
- We want to add *tmux* as a sibling to cmux — Linux users have no cmux
  equivalent and the concept of "drive an AI CLI through a multiplexer"
  generalises cleanly.
- The ad-hoc cmux module keeps accruing features (loop support, agent
  profiles, IDE server launch, permission notification, verbose streaming)
  and each one has to be plumbed into the frontend with another string
  check. The cost of a new multiplexer is super-linear in this design.
- The four agent implementations (=json-backend=, =acp-opencode=,
  =acp-gemini=, =acp-codex=) are *siblings* in reality but unevenly
  modelled — OpenCode/Gemini/Codex share an ACP JSON-RPC base, Claude
  Code is named =json-backend= with no kinship indication.

* Goals / Non-goals

** Goals

- *Symmetry*: agents and multiplexers are parallel families, not
  master–slave. The frontend dispatches identically through both.
- *Smalltalk OOP*: dispatch on the receiver's class via =cl-defmethod=
  everywhere. No string discriminators in the frontend. Per project rule
  =.claude/rules/oop-smalltalk-protocols.md=.
- *Feature preservation*: every feature in the existing codebase
  (audited 2026-04-24) keeps working. No regressions, no silent drops.
- *Pluggability*: adding a new agent or multiplexer is a new file with
  a struct + =cl-defmethod= implementations + one registry entry. Zero
  frontend changes.
- *tmux parity* for v1 with cmux on the essentials: launch, send, read,
  stream, status. Platform-specific niceties (workspace color) stay
  cmux-only via =supports-p= capability flags.
- *Hot-reload* on every layer — no per-backend registration ceremony.

** Non-goals

- Migrating Claude Code to *speak true ACP* (possible per Zed's
  integration; out of scope — stream-json works and is stable).
- Rewriting the Python =workspace-bridge= — its MCP call sites get
  renamed to the Protocol 3 generics (atomic cut-over, no compat
  shims per project policy), but the async-via-status-files adapter
  pattern stays exactly as it is.
- tmux *control mode* (=tmux -CC=). v1 uses polling + =pipe-pane= —
  simpler, sub-second latency, no state machine or base64 reassembly.
  Defer to v2 if anyone asks.
- Cross-platform testing infrastructure for tmux — developer-level
  best-effort; the E2E harness stays macOS-first.

receiver (Smalltalk "one object implements multiple protocols"):

** Why three layers on the agent side

Three of the four agents (OpenCode, Gemini, Codex) share an ACP JSON-RPC
v1 wire format; their concrete subclasses differ only in spawn-cmd +
capability flags. Putting =claude-agent-acp-agent-backend= in the middle
keeps the ACP machinery written once, inherited three times.

Claude Code's =--output-format stream-json= is *not* literally ACP, so it
sits as a sibling to the ACP abstract, not a child of it. Adding a fifth
agent that speaks ACP = flat subclass (cheap); adding one that speaks
something else = new sibling (also cheap).

** Why two layers on the multiplexer side

cmux and tmux have almost identical APIs at the conceptual level:
launch, send-keys, capture-pane, stream-output, query-status. The base
class holds:
- The Python-bridge adapter contract (status files, workspace hash table,
  request-id persistence)
- The verbose buffer machinery (ANSI strip, 256 KB cap, kill-buffer-hook
  that stops the follower — all shipped from the 2026-04-24 memory-leak
  fix)
- Agent-profile resolution (which profile to use given =AGENT_TYPE=)
- Claude-only-args filter (strip =--permission-mode= / =--ide= when
  launching Copilot or OpenCode)

Concrete subclasses supply roughly six =cl-defmethod= implementations
each — ~300 lines per multiplexer.

* Protocol 1: lifecycle  (unchanged)

Already defined in =claude-agent-backend.org=. Listed here for completeness:

| Generic | Responsibility |
|---------+---------------|
| =query (backend prompt callbacks &rest args)= | Send a prompt; return opaque cancel handle |
| =cancel (backend handle)= | Stop an in-flight query |
| =cleanup (backend)= | Release all held resources |
| =ready-p (backend)= | Accept a new query? |
| =active-p (backend)= | Has an in-flight query? |
| =session-id (backend)= | Current session id, or nil |
| =send-input (backend input)= | Send during active query (permission reply) |
| =supports-p (backend capability)= | Capability query — see matrix |
| =classify-error (backend error)= | Error → =context-limit= / =session-expired= / =network= / =auth= / =unknown= |
| =verbose-buffer (backend)= | Backend-managed debug buffer, or nil |

* Protocol 2a: agent wire  (=claude-agent-agent-*=)

Specialised on =claude-agent-agent-backend=. Every concrete agent must
implement what it needs; default methods live on the abstract base.

The *root Protocol 1 method* =claude-agent-backend-query= on
=claude-agent-agent-backend= is implemented *once* and orchestrates the
sub-protocol: =handshake= → optional =load-session= → =send-prompt= →
loop over =stream-event= → route permission requests to
=handle-permission=. Concrete agents don't override =-query=; they
supply the six primitives above.

The Protocol 1 =-query= method on =claude-agent-multiplexer-backend=:
=ensure-session= → =wait-for-ready= → =send-text= prompt → =send-key :enter=
→ register query → =start-follower= if verbose mode is on → return. The
actual response arrives asynchronously via the =workspace-bridge= into
Protocol 3 =append-response=.

* Protocol 3: org-integration  (=code-agent-org-backend-*=)

Dispatches on the root =claude-agent-backend=. Defaults live on the root
(backend-agnostic org-buffer math); family bases override where
behaviour diverges; concrete subclasses rarely need to override at all.

* Workflow sequences (canonical six)

** W1: execute ai block — agent family (Claude Code / ACP)

#+begin_example
User C-c C-c in ai block
  └─▶ code-agent-org-execute                                          [frontend, backend-agnostic]
        ├─▶ prep: loop state, auto-title, execute-hook, queue-if-busy
        └─▶ code-agent-org-backend-execute-block (backend, block-info) ← Protocol 3
              └─▶ method on agent-backend:
                    ├─▶ insert-prompt (no-op; ai block IS the prompt)
                    ├─▶ open-response-section → marker
                    ├─▶ register-query
                    ├─▶ send-prompt ─────────▶ Protocol 2a: CLI subprocess, streams events
                    │     └─▶ on each token: append-response (marker, text)
                    │     └─▶ on permission req: handle-permission
                    └─▶ on stream-end: finalize-response (marker, meta)
                          └─▶ query-completed → advance loop / dequeue next
#+end_example

** W2: execute ai block — multiplexer family (cmux / tmux)

#+begin_example
User C-c C-c in ai block
  └─▶ code-agent-org-execute                                          [same frontend]
        └─▶ code-agent-org-backend-execute-block (backend, block-info) ← Protocol 3
              └─▶ method on multiplexer-backend:
                    ├─▶ ensure-session ────▶ Protocol 2b: launch or reuse workspace
                    ├─▶ wait-for-ready
                    ├─▶ insert-prompt ─────(writes :claude_chat: instruction)
                    ├─▶ open-response-section → marker
                    ├─▶ write from-emacs flag
                    ├─▶ register-query (writes .request-id)
                    ├─▶ send-text (prompt)  ▶ Protocol 2b
                    ├─▶ send-key :enter     ▶ Protocol 2b
                    ├─▶ start-follower (if verbose mode)
                    └─▶ return — done (response arrives async)

Later, Python hook:  UserPromptSubmit / PostToolUse / Stop
  └─▶ workspace_bridge.py → MCP evalElisp
        └─▶ code-agent-org-backend-append-response   (Protocol 3)
            code-agent-org-backend-finalize-response (Protocol 3)
            code-agent-org-backend-query-completed   (Protocol 3)
#+end_example

** W3: permission request — agent family

#+begin_example
Agent emits session/request_permission (ACP) OR can_use_tool control-request (claude-code)
  └─▶ agent-backend method: handle-permission
        ├─▶ consult claude-agent-permission-functions hook chain
        │     ├─▶ check-patterns (allow/deny)
        │     ├─▶ cached decision
        │     └─▶ interactive y/n (or AskUserQuestion completing-read)
        └─▶ respond: ACP session/response OR control_response on stdin
#+end_example

** W4: permission request — multiplexer family

#+begin_example
Agent (inside TUI) pauses, prints "Allow this Bash command? [y/n]"
  └─▶ Python PreToolUse hook → MCP evalElisp
        └─▶ code-agent-org-backend-permission-notify (Protocol 3)
              ├─▶ default:   mode-line alert
              ├─▶ cmux:      default + sidebar alert + workspace focus + macOS notify
              └─▶ tmux:      default (no sidebar API)

User types y/n in TUI → PostToolUse hook fires
  └─▶ Python → MCP evalElisp
        └─▶ code-agent-org-backend-permission-resolved (Protocol 3)
#+end_example

** W5: cancel (C-c C-k)

#+begin_example
User C-c C-k
  └─▶ code-agent-org-cancel                                           [frontend]
        └─▶ code-agent-org-backend-cancel-from-org                     ← Protocol 3
              ├─▶ agent-backend:    claude-agent-query-interrupt
              ├─▶ cmux-backend:     send-key (agent profile's cancel-keys)
              └─▶ tmux-backend:     send-key (agent profile's cancel-keys)
#+end_example

** W6: session recovery (after Emacs restart)

#+begin_example
User re-opens org file; code-agent-org-mode enables
  └─▶ code-agent-org--recover-all-sessions
        └─▶ for each CLAUDE_SESSION_ID in buffer:
              └─▶ create backend from registry
              └─▶ code-agent-org-backend-recover-session                ← Protocol 3
                    ├─▶ agent-backend:   read session property → load-session
                    │                    (next query uses --resume)
                    └─▶ mux-backend:     resolve-session-by-heading
                                         → repopulate workspace maps
                                         → start-follower if verbose was active
                                         → apply-style (cmux only)
                                         → ensure IDE server (cmux only)
                                         → rename tab
#+end_example

* Testing strategy

Four test surfaces, each exercising one layer of the new stack:

** Structural tests

=tests/test-structural.el= gains a =test-structural-backend-protocol-completeness=
that iterates through =claude-agent-backend--registered-concrete-classes=
and verifies every concrete backend has a =cl-defmethod= for every
mandatory Protocol 1 + 2a/2b generic. Fails the build at import time if
a method is missing.

** Protocol 3 shared harness

=tests/test-code-agent-org-backend-protocol.el= (new) — single suite exercising
=execute-block=, =insert-prompt=, =open-response-section=,
=append-response=, =finalize-response=, =cancel-from-org=,
=recover-session= against:

- A mock =claude-agent-mock-backend= (canonical reference implementation
  for protocol conformance)
- Each concrete backend with fixtures

Ensures frontend-contract drift is caught immediately.

** Protocol 2b shared harness (multiplexer)

=tests/test-multiplexer-protocol.el= (new) — =launch-session=,
=send-text=, =capture-screen=, =start-follower=, =stop-follower=,
=wait-for-ready=, =session-status= against:

- =cmux-backend= with mocked =cmux= CLI (existing test fixture pattern)
- =tmux-backend= with *real tmux* in a test session (tmux is lightweight
  enough to spawn in CI)

Same fixtures, two runs — catches divergence at the Protocol 2b
boundary.

** Protocol 2a tests

Existing ACP tests stay. Add a symmetric suite for =claude-code-backend=
(already present as =test-claude-agent-unit.el=; rename to match new
structure).

** E2E living harness

=tests/e2e/org/workspace-test.org= grows one tmux workspace alongside
the existing cmux ones. =tests/e2e/living-workspace-test.org= documents
how to run it. Covers feature-parity across the full stack.

* Risks + mitigations

| Risk | Likelihood | Impact | Mitigation |
|------+-----------+--------+------------|
| Feature drop (something in the audit silently disappears) | Medium | High | The feature-migration matrix above is the contract; each phase's PR description lists features preserved/moved. Structural tests catch "method missing" at import time |
| cmux extraction (Phase 3) regresses a live session | Medium | High | Parallel code during extraction — old code runs until all backend methods pass. Atomic cutover is small + reversible |
| tmux v1 can't express a cmux concept (e.g. workspace colour) | Medium | Low | Expected. Document as gap; frontend uses =supports-p= |
| =pipe-pane= stream hits unbounded-buffer bug | Low | Medium | The Emacs-side follower reads from a file and inherits the 256 KB cap from =multiplexer-backend= base |
| Python bridge calls break when MCP targets rename | Medium | High | Phase 3 lands Emacs Protocol 3 generics *and* Python MCP call-site updates in a single PR. Both sides live in this repo, so atomicity is achievable. No compat aliases — per project no-backward-compat rule |
| Live-reload =rx '**' range error= (pre-existing) | Ongoing | Low | Independent issue; tests still pass in batch mode. Don't entangle |
| Queue file format churn | Low | Medium | Keep =.custom-ids= format unchanged; new backends read/write it as-is |
| Session-property collision across agents | Low | Medium | Each concrete agent backend declares =session-property-name= via generic — no cross-agent clobber |

* Decisions taken

Per project rule =.claude/rules/no-backward-compatibility.md=, we do
*not* ship compat shims, defalias wrappers, or re-exports. The old
shape is deleted in the same commit that lands the new one, and all
callers are updated together.

| Decision | Resolution |
|----------+------------|
| Phase 1 granularity | *Single PR* with thorough tests (~800 lines diff, self-contained). Alternative "4 smaller PRs" rejected as harder to verify end-to-end behaviour-neutrality |
| Naming for Claude Code backend | =claude-agent-claude-code-backend= — matches =claude-code.el= entry point; unambiguous |
| Old =claude-agent-json-backend= name | *Deleted* in Phase 2, not aliased. Every caller is updated in the same PR. Registry carries only the new name |
| Old =claude-agent-acp-opencode= / =-gemini= / =-codex= module names | *Deleted* in Phase 2 (renamed to =claude-agent-opencode= / =-gemini= / =-codex=). Registry entries + =claude-code.el= requires updated in the same commit |
| MCP target renames (workspace-bridge endpoints) | *Atomic cutover*: Emacs-side Protocol 3 generics and Python-side MCP call sites land in one PR. No =defalias= layer. Requires the Emacs reload and the Python =hooks.json= redeploy to be co-ordinated — acceptable because both live in this repo |
| Old =code-agent-org-cmux.org= | *Deleted* at Phase 3 cut-over, not kept as a shim. Its Emacs-side user commands (menus, keybindings, interactive functions) move to =claude-agent-cmux-backend.org= or into =code-agent-org.org= if truly backend-agnostic |
| Old =code-agent-org-terminal-base.org= | *Deleted* at Phase 5, absorbed into =claude-agent-multiplexer.org= base |
| User-facing mode name | Rename =code-agent-org-mode= → =code-agent-org-mode= (plus =-mode-hook= and =-mode-map=). The project drives four agents (Claude Code, OpenCode, Gemini, Codex) across two multiplexer backends; "Claude" in the mode name is historical + misleading. Lands in Phase 1 alongside the Protocol 3 plumbing. Old symbols *deleted*, not aliased |
| Broader =code-agent-org-*= function namespace | *Not renamed in this refactor*. ~500 call sites across the codebase and tests; the diff would dwarf the protocol work. Flagged as a future design doc (candidate title: "Agent-agnostic namespace rename"). When done, the rule is: =code-agent-org-*= → =code-agent-org-*= (mechanical), any =claude-agent-*= stays as-is because that *is* the backend SDK layer |
