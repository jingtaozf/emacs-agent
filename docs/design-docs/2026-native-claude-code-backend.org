#+TITLE: Design: Native Claude Code Backends
#+DATE: 2026-03-03
#+STATUS: superseded (Tri-Protocol refactor + iTerm2/native backend removal)

* Reality check (2026-04-27)
Of the three approaches surveyed, only the JSON-stream / stdio path survives
today (now refined as the agent-family side of the Tri-Protocol architecture
via `claude-agent-claude-code-backend`).  The "iTerm2-driven" and
"native-eat/vterm" approaches were removed in commit 1038144.  Multiplexer
control (cmux + tmux) is the replacement family.  Read this doc for
historical comparison; consult `2026-tri-protocol-backend-refactor.org` for
the live design.

* Overview

This document covers three backend approaches for running Claude Code
from Emacs, each targeting different trade-offs:

| Backend | How it works | Control API | Best for |
|---------+--------------+-------------+----------|
| =json-stream= | Emacs subprocess (=-p --stream-json=) | Elisp (direct) | Tight integration, structured messages |
| =claude-cli= | eat/vterm TUI inside Emacs | Elisp (terminal) | Interactive use, visible TUI |
| =iterm2= | iTerm2 external terminal | Python + shell hooks | OOM isolation, long sessions |

All backends share:
- System prompt pipeline (=:system_prompt:= sections, behavior prompts)
- =CLAUDE_SESSION_ID= for SDD session identity
- =CLAUDE_CLI_SESSION= for Claude Code =--resume=
- Backend protocol (=claude-agent-backend.org=)

* Shared Infrastructure

** System Prompt Assembly

All backends reuse =claude-org--build-system-prompt= (or the SDD bridge
equivalent =claude-org-sdd-bridge-system-prompt=) to assemble:

- =prompts/system/*.org= files
- =:system_prompt:= tagged org sections
- Tag/header behavior prompts
- Line width hints, elisp reload hints

The assembled text is passed via =--system-prompt= CLI flag.

** Backend Protocol (=claude-agent-backend.org=)

All backends implement the =claude-agent-backend= protocol:

| Generic | Purpose |
|---------+---------|
| =backend-query= | Start a query, invoke callbacks |
| =backend-cancel= | Cancel an in-flight query |
| =backend-cleanup= | Release resources |
| =backend-active-p= | Is a query running? |
| =backend-session-id= | Resume ID for continuity |
| =backend-send-input= | User input (permission prompts) |
| =backend-supports-p= | Capability feature flag |
| =backend-classify-error= | Error classification for recovery |

** Backend Dispatch via =CLAUDE_BACKEND=

=claude-org-execute= (C-c C-c) reads the =CLAUDE_BACKEND= org property
(inherited) to select which backend handles the AI block:

| Value | Backend | Behavior |
|-------+---------+----------|
| (unset / ="json-stream"=) | JSON Stream | Default. Subprocess, real-time streaming. |
| ="native"= | Claude CLI | eat/vterm terminal inside Emacs. |
| ="iterm2"= | iTerm2 Bridge | External terminal, auto-launch tab. |

This is checked via =org-entry-get nil "CLAUDE_BACKEND" t= (inherited),
so it can be set once on a parent heading and apply to all AI blocks
within that subtree.

** Org Properties (Common)

| Property | Purpose | Used by |
|----------+---------+---------|
| =CLAUDE_SESSION_ID= | SDD session key | All |
| =CLAUDE_CLI_SESSION= | Claude Code =--resume= ID | All |
| =PROJECT_ROOT= | Working directory | All |
| =CLAUDE_BACKEND= | Backend selector (see above) | Dispatch |

* Backend 1: JSON Stream (subprocess)
:PROPERTIES:
:CUSTOM_ID: backend-json-stream
:END:

** Summary

Spawns =claude -p --output-format stream-json= as an Emacs subprocess.
Responses stream as newline-delimited JSON, parsed by process filter.
This is the *original and most mature* backend.

Implemented as =claude-agent-json-backend= in =claude-agent-backend.org=.

** Architecture

#+begin_example
Org File
├── C-c C-c on ai block
│         │
│         ▼
│   claude-org-execute
│         │
│         ▼
│   claude-agent-backend-query (json-stream)
│         │
│         ▼
│   claude-agent-query
│   → start-process "claude" "-p" "--output-format" "stream-json"
│         │
│         ▼  (newline-delimited JSON on stdout)
│   Process Filter
│   ├── :on-token  → stream text into response section
│   ├── :on-message → structured message dispatch
│   └── :on-complete → finalize response
#+end_example

** Capabilities

| Capability | Supported |
|------------+-----------|
| =:streaming-tokens= | Yes |
| =:structured-messages= | Yes |
| =:tool-use= | Yes |
| =:session-resume= | Yes |
| =:interactive-input= | Yes |
| =:persistent-client= | Yes (bidirectional mode) |

** Two Modes

*** One-shot mode (=-p=)

- =claude-agent-query= spawns a new process per prompt
- Process exits after response completes
- Simple, stateless

*** Persistent client mode

- =claude-agent-client= maintains a long-lived subprocess
- Bidirectional: sends messages via stdin, receives via stdout
- Supports multi-turn conversation without re-spawning

** Known Issues

- *OOM crashes*: Node.js memory leaks cause SIGKILL after sustained use
  ([[https://github.com/anthropics/claude-code/issues/4953][#4953]],
  [[https://github.com/anthropics/claude-code/issues/24480][#24480]],
  [[https://github.com/anthropics/claude-code/issues/22042][#22042]])
- Session recovery exists but OOM kills are unrecoverable mid-response
- Persistent client mode amplifies memory leak (long-lived process)

** Trade-offs

| Advantage | Disadvantage |
|-----------+--------------|
| Structured JSON protocol | OOM crashes (Node.js leak) |
| Real-time token streaming | Crash can lose in-flight response |
| Full callback system | Same Emacs process (no isolation) |
| Mature, well-tested | Persistent mode worsens memory |
| Works on all platforms | No user-visible TUI |

** Status: *Implemented*

Core SDK in =claude-agent.org= + =claude-agent-backend.org=.
Full test suite. Production use.

* Backend 2: Claude CLI Terminal (eat/vterm)
:PROPERTIES:
:CUSTOM_ID: backend-claude-cli
:END:

** Summary

Runs Claude Code TUI as a long-lived interactive terminal inside Emacs
via eat (or vterm). User sees the real Claude Code interface. Prompts
are sent via bracketed paste. Responses come via CLI Stop hook.

Implemented as =claude-agent-claude-backend= in =claude-agent-backend.org=.

** Architecture

#+begin_example
Org File (CLAUDE_BACKEND=native)
├── :system_prompt: sections ──┐
├── PROJECT_ROOT property ─────┤
├── tags/header behaviors ─────┤
│                              ▼
│                 claude-org--build-system-prompt()
│                              │
│    C-c C-c on ai block       │ (assembled text)
│         │                    ▼
│         ▼          claude-org-open-native-terminal()
│    [prompt text]             │
│         │                   ▼
│         │          eat-make "claude" --system-prompt <text>
│         │                    --settings <hooks-file>
│         │                   │
│         └──────────────────► │ (bracketed paste into terminal)
│                              ▼
│                    ┌─────────────────────┐
│                    │  *claude-native<sk>* │
│                    │  Claude Code TUI     │ ← user interacts here
│                    └─────────────────────┘
│                              │
│                    Hook system (--settings)
│                    ├── PreToolUse → permission functions
│                    ├── PostToolUse → buffer revert
│                    └── Stop → response capture to org
#+end_example

** Capabilities

| Capability | Supported |
|------------+-----------|
| =:streaming-tokens= | No (batch via Stop hook) |
| =:structured-messages= | No |
| =:tool-use= | Yes (via hook wrapper) |
| =:session-resume= | Yes |
| =:interactive-input= | Yes (direct terminal) |
| =:persistent-client= | Yes (long-lived TUI) |

** Features

*** F1: Backend dispatch

Extend =claude-org--make-default-backend= to recognize "native":

#+begin_example
(cond
  ((equal prop-value "native")
   (claude-org--session-put session-key :native-mode t)
   nil))  ;; no automated backend
#+end_example

*** F2: =claude-org-open-native-terminal= command

1. Reads system prompts, PROJECT_ROOT, session key
2. Opens eat terminal running =claude= CLI with system prompt
3. Names buffer =*claude-native<session-key>*=
4. Reuses existing live buffer, kills stale ones

*** F3: =claude-org-native-mode= minor mode

| Key | Action |
|-----+--------|
| =C-c C-q= | Kill terminal buffer |
| =C-c C-r= | Refresh (kill + relaunch with updated prompt) |
| =C-c C-s= | Send region from another buffer |

*** F4: C-c C-c execution flow

When =CLAUDE_BACKEND= is "native" and user presses C-c C-c on AI block:
- If terminal doesn't exist → create it, then paste prompt
- If terminal exists and alive → paste prompt into it
- Response capture via Stop hook (batch, not streaming)

** Key Functions

#+begin_example
(defun claude-org-open-native-terminal ()
  "Open a native Claude Code terminal with system prompts."
  (interactive)
  (let* ((session-key (claude-org--current-session-key))
         (project-root (or (claude-org--get-project-root) default-directory))
         (system-prompt (claude-org--build-system-prompt))
         (cli (claude-agent--find-cli))
         (buf-name (format "claude-native<%s>" session-key))
         (existing (get-buffer (concat "*" buf-name "*"))))
    (if (and existing (buffer-live-p existing)
             (get-buffer-process existing)
             (process-live-p (get-buffer-process existing)))
        (funcall claude-org-native-display-function existing)
      (when existing (kill-buffer existing))
      (let ((buf (eat-make buf-name cli nil
                           "--system-prompt" system-prompt)))
        (with-current-buffer buf (claude-org-native-mode 1))
        (funcall claude-org-native-display-function buf)
        (claude-org--session-put session-key :native-buffer buf)))))

(defun claude-org--native-send-prompt (session-key prompt)
  "Send PROMPT to native terminal via bracketed paste."
  (let ((buf (claude-org--session-get session-key :native-buffer)))
    (with-current-buffer buf
      (eat-term-send-string eat-terminal
        (concat "\e[200~" prompt "\e[201~"))
      (run-at-time 0.3 nil
        (lambda ()
          (when (buffer-live-p buf)
            (with-current-buffer buf
              (eat-term-send-string eat-terminal "\r"))))))))
#+end_example

** Trade-offs

| Advantage | Disadvantage |
|-----------+--------------|
| User sees real TUI | Emacs single-thread bottleneck |
| Direct Emacs integration | OOM crash can freeze Emacs |
| Buffer accessible to elisp | 3-4x slower than native terminal |
| Works on all platforms | Complex TUI apps may glitch |
| No external dependencies | No real-time streaming to org |

** Status: *Partially Implemented*

=claude-agent-claude-backend= struct and protocol methods exist.
eat integration works. Hook wrapper exists. Missing: C-c C-c dispatch
from org, native-mode minor mode.

* Backend 3: iTerm2 Bridge (external terminal)
:PROPERTIES:
:CUSTOM_ID: backend-iterm2
:END:

** Summary

Runs Claude Code in iTerm2 as an external terminal process. Emacs
controls iTerm2 via stateless Python scripts (=iterm2-ctl.py=).
Responses come back to Emacs via the SDD bridge hook pipeline
(=sdd-bridge.sh= → MCP → org file).

This backend *includes* the Terminal SDD Bridge as its response capture
mechanism. The SDD bridge (shell hooks + =sdd-bridge.sh=) is the
plumbing layer; iTerm2 Python API is the control layer.

** Motivation

1. *OOM isolation*: =claude -p= subprocess mode has known memory leaks.
   External terminal isolates crashes completely.
2. *Python API*: WebSocket + Protobuf protocol — richer than shell CLI.
   Supports event monitoring, triggers, session object model.
3. *Persistent session IDs*: iTerm2 UUIDs survive Emacs restarts.
4. *GPU rendering*: Metal-accelerated, no Emacs single-thread bottleneck.

** Architecture

#+begin_example
┌──────────────────────────────────────────────────────┐
│  Emacs                                               │
│                                                      │
│  #+begin_src ai                                      │
│  fix the bug in auth.py                              │
│  #+end_src                                           │
│       │ C-c C-c                                      │
│       ▼                                              │
│  claude-org-execute (CLAUDE_BACKEND=iterm2)           │
│       │                                              │
│       ▼                                              │
│  ensure-session (find tab by title, or launch new)   │
│       │                                              │
│       ▼                                              │
│  iterm2-ctl.py send --session <ID> < prompt-file     │
└───────┼──────────────────────────────────────────────┘
        │
        ▼  (WebSocket + Protobuf, ~200ms)
┌───────────────────────────────────────────┐
│  iTerm2                                   │
│  ┌─────────────────────────────────────┐  │
│  │  Tab: "workflow:my story"           │  │
│  │  ┌───────────────────────────────┐  │  │
│  │  │  Claude Code TUI              │  │  │
│  │  │  > fix the bug in auth.py     │  │  │
│  │  │  [Claude responds...]         │  │  │
│  │  └───────────────────────────────┘  │  │
│  └─────────────────────────────────────┘  │
│                    │                      │

│         (UserPromptSubmit / Stop)         │

   ┌─────────────────┼────────────────────┐

   │  sdd-bridge.sh                      │
   │  ├── prompt  → set-busy + insert    │
   │  └── response → set-ready + insert  │
   │         │                           │
   │         ▼  (MCP evalElisp)          │
   │  Emacs: insert into org file        │

   └──────────────────────────────────────┘

** Prerequisites and Graceful Degradation

The iTerm2 backend works best with the *Emacs MCP server* running.
MCP enables the full SDD bridge:

- System prompt assembly (reading org sections via =evalElisp=)
- Session metadata lookup (CLI session ID, story name)
- Response insertion (hook callbacks write into org buffer)
- Plugin hooks (=--plugin-dir=, =--mcp-config=)

=claude-org-iterm2--ensure-session= auto-starts MCP before launching:

#+begin_example
1. Check (emacs-mcp-server-running-p)
2. If not running → call (emacs-mcp-server-start), wait 1s
3. If still not running → warn but proceed
4. Launch claude-sdd (which handles MCP absence gracefully)
#+end_example

*Graceful degradation*: =claude-sdd= always launches Claude Code,
even when MCP is unavailable. Without MCP, it skips system prompt
fetch and plugin hooks, launching bare =claude=. The user can type
instructions directly in the Claude Code TUI. When MCP becomes
available later, full SDD integration resumes on next launch.

** Design Principles

1. *Stateless Python* — each invocation connects, acts, exits.
   =f(session_id, args) -> result=. No daemon, no persistent state.

2. *iTerm2 session ID as key* — stored as org property, survives restarts.

3. *Unidirectional prompt flow* — Emacs sends prompts to iTerm2. Responses
   come back via existing SDD bridge Stop hook pipeline.

4. *Minimal dependencies* — one CLI tool, only =iterm2= pip package.

5. *Single source of truth for status* — sdd-bridge.sh hooks are the
   *only* place that sets busy/ready state. Emacs never sets status
   directly — this avoids double-increment and race conditions.

6. *MCP server auto-start* — =ensure-session= checks
   =emacs-mcp-server-running-p= before launching =claude-sdd=. If the
   server is not running, it calls =emacs-mcp-server-start= and waits
   1 second for the port to bind. If still not running, aborts with
   =user-error=. This is a hard requirement: =claude-sdd= needs MCP
   to fetch the system prompt and session metadata from the org file.

7. *Positive evidence for state detection* — =detect_state= in
   =iterm2-ctl.py= defaults to ="dead"= (no Claude evidence), not
   ="busy"=. Only returns ="busy"= when positive Claude TUI indicators
   are found (box-drawing chars, activity spinner). This prevents stale
   shell tabs from being mistaken for active Claude sessions.

** Identity Model

Three distinct IDs exist in this backend. Do not confuse them:

| ID | Source | Example | Stored in |
|----+--------+---------+-----------|
| SDD session ID | Org property =CLAUDE_SESSION_ID= | =sdd-20260307-143022= | Org file |
| iTerm2 session UUID | iTerm2 API | =w0t0p0:E4A1B2C3-...= | =ITERM2_SESSION_ID= org property |
| Claude CLI session | Claude Code =--resume= | =abc123def= | =CLAUDE_CLI_SESSION= org property |

- *SDD session ID*: keys the hook status file, mode-line state, and
  all Emacs-side session lookups.
- *iTerm2 session UUID*: keys all =iterm2-ctl.py= subcommands (send,
  cancel, status, focus).
- *Claude CLI session*: passed to =claude --resume= for conversation
  continuity across restarts.

** Prompt Origin Detection

The =UserPromptSubmit= hook fires for EVERY prompt, regardless of origin.
Two sources exist:

| Origin | How | AI block exists? | Hook should insert AI block? |
|--------+-----+-----------------+------------------------------|
| Emacs C-c C-c | =execute-ai-block= → =iterm2-ctl.py send= | Yes (already in org) | *No* (would duplicate) |
| Direct typing | User types in Claude Code TUI | No | *Yes* (org needs it) |

*Mechanism*: =execute-ai-block= writes a flag file before sending:

#+begin_example
/tmp/claude-agent-status/$SDD_SESSION_ID.from-emacs
#+end_example

=sdd-bridge.sh= checks this flag on the =prompt= event:
- If flag file exists → delete it, skip =insert-prompt= (Emacs already has it)
- If flag file absent → call =insert-prompt= (user typed directly in Claude)

This is a simple, race-free protocol:
- Flag is written *before* the prompt is sent (sequential in =execute-ai-block=)
- Flag is consumed *atomically* by the hook (read-and-delete)
- One flag per prompt — no accumulation

** Layer Decomposition

This backend has two layers that can be used independently:

*** Layer 1: SDD Bridge (response capture)

The plumbing layer. Works with *any* external terminal.

| Component | File | Purpose |
|-----------+------+---------|
| =sdd-bridge.sh= | =scripts/sdd-bridge.sh= | Hook handler (prompt/response events) |
| =claude-sdd= | =scripts/claude-sdd= | Launcher (session picker, system prompt) |
| Bridge elisp | =claude-org.org= | Insert prompt/response into org file |

Hook pipeline:
#+begin_example
Claude Code finishes responding
  → Stop hook fires
  → sdd-bridge.sh
  → curl to Emacs MCP server
  → claude-org-sdd-bridge-insert-response
  → Response section created in org file
#+end_example

Elisp bridge functions:

| Function | Purpose |
|----------+---------|
| =claude-org-sdd-bridge-system-prompt= | Build system prompt for session |
| =claude-org-sdd-bridge-insert-prompt= | Insert instruction heading + AI block |
| =claude-org-sdd-bridge-insert-response= | Insert response heading with shifted headings |
| =claude-org-sdd-bridge-save-cli-session= | Persist CLI session ID as property |
| =claude-org-sdd-bridge-list-sessions= | List all SDD sessions for picker |
| =claude-org-sdd-bridge-send-prompt= | Send AI block to terminal pane |

*** Layer 2: iTerm2 Control (terminal management)

The control layer. Adds programmatic terminal lifecycle management.

| Component | File | Purpose |
|-----------+------+---------|
| =iterm2-ctl.py= | =scripts/iterm2-ctl.py= | Stateless Python CLI tool |
| iTerm2 elisp | =claude-org.org= | Emacs commands wrapping Python calls |

*** How the Layers Compose

- *SDD bridge alone*: User manually opens terminal, runs =claude-sdd=.
  Responses flow back via hooks. No programmatic terminal control.

- *SDD bridge + iTerm2*: Emacs auto-launches Claude Code in iTerm2 via
  =iterm2-ctl.py=, sends prompts programmatically. Responses still flow
  back via SDD bridge hooks. Full automation.

** Python CLI Tool: =iterm2-ctl.py=

Single script with subcommands. Each is a pure async function.

*** Tab Naming Convention

Tab titles follow the pattern =<heading> [<sdd-session-id>]=, e.g.
=native claude code backend [sdd-20260307-143022]=. The SDD session ID
suffix ensures uniqueness across org files. This is the *primary key*
for tab reuse — =launch= searches for an existing tab matching this
title before creating a new one.

*** Subcommands

| Subcommand | Args | Returns (stdout) | Description |
|------------+------+------------------+-------------|
| =launch= | =--title=, =--cwd=, =--system-prompt-file=, =--resume= | session ID | Find or create tab, launch =claude= |
| =send= | =--session <ID>=, reads stdin | "ok" | Bracketed paste + Enter |
| =cancel= | =--session <ID>= | "ok" | Send Escape to interrupt Claude |
| =status= | =--session <ID>= | JSON (see below) | Check Claude Code state |
| =read= | =--session <ID>=, =--lines N= | screen text | Read last N lines |
| =focus= | =--session <ID>= | "ok" | Activate tab + bring iTerm2 to front |
| =close= | =--session <ID>= | "ok" | Send =/exit=, wait for exit |
| =list= | (none) | JSON array | List all Claude sessions |

*Large content via files/stdin*: System prompts and prompt text can be
multi-KB. Never pass them as CLI args (risk hitting =ARG_MAX=).
- =launch=: reads system prompt from =--system-prompt-file= (temp file)
- =send=: reads prompt text from stdin

*** =launch= — Find or Create

=launch= first searches for an existing tab whose title matches =--title=.
If found and Claude Code is alive in that tab, returns its session ID
(no new tab created). Otherwise creates a new tab.

#+begin_example
async def launch(app, args):
    # 1. Search existing tabs by title
    existing_tab = find_tab_by_title(app, args.title)
    if existing_tab:
        state = detect_state(existing_tab.current_session)
        if state == "ready":   # Claude at input prompt — reuse
            return session.session_id
        if state == "busy":    # Claude processing — reuse
            return session.session_id
        # state == "dead": tab exists but Claude not running
        # Reuse this tab, launch Claude in it below
        tab = existing_tab
    else:
        # 2. No match — create new tab
        tab = await window.async_create_tab()
        await tab.async_set_title(args.title)

    # 3. Build and send claude command in existing/new tab
    session = tab.current_session
    cmd = build_claude_command(args)
    await session.async_send_text(cmd + "\n")

    # 4. Wait for Claude Code to be ready (with timeout)
    ready = await wait_for_ready(session, timeout=20)
    return session.session_id
#+end_example

*Tab reuse*: When a tab with matching title exists but Claude is dead
(e.g. previous launch failed, or Claude exited), =launch= reuses that
tab instead of creating a new one. This avoids tab proliferation.

*IMPORTANT*: The =claude= command must include =--settings= pointing to
the hook configuration file. Without it, =sdd-bridge.sh= hooks won't
fire and no responses will flow back to Emacs.

*** =cancel= — Interrupt Current Instruction

Sends Escape key to Claude Code TUI, which cancels the current
in-progress response. Same as pressing Escape in the terminal.

The Stop hook will fire after cancellation, which triggers
=sdd-bridge.sh= "response" event → =set-ready=. Emacs does *not*
eagerly set ready on cancel — it waits for the hook.

#+begin_example
async def cancel(app, session_id):
    session = find_session(app, session_id)
    if not session:
        return json.dumps({"result": "dead"})
    # Send Escape to cancel current response
    await session.async_send_text("\x1b")
    # Brief wait for Claude Code to process the cancel
    await asyncio.sleep(0.5)
    # Verify state changed (optional, for feedback)
    text = await read_screen(session, lines=3)
    state = detect_state(text)
    return json.dumps({"result": "ok", "state": state})
#+end_example

*** =status= — Rich Status Check

Returns JSON with multiple fields for Emacs to consume:

#+begin_example
async def status(app, session_id):
    session, tab = find_session_and_tab(app, session_id)
    if not session:
        return json.dumps({"state": "dead"})
    text = await read_screen(session, lines=5)
    state = detect_state(text)  # "ready" | "busy"
    return json.dumps({
        "state": state,
        "session_id": session_id,
        "tab_title": tab.tab_name if tab else "",
    })
#+end_example

*** =focus= — Bring Tab to Front

Activates the tab and brings iTerm2 window to foreground.
Returns exit code 2 if session not found (caller can relaunch).

#+begin_example
async def focus(app, session_id):
    session, tab = find_session_and_tab(app, session_id)
    if not session or not tab:
        raise SystemExit(2)  # session not found
    await tab.async_select()
    await app.async_activate()  # bring iTerm2 to front
    return "ok"
#+end_example

*** Error Handling

| Exit code | Meaning |
|-----------+---------|
| 0 | Success, result on stdout |
| 1 | iTerm2 not running or API not enabled |
| 2 | Session not found (stale ID) |
| 3 | Claude Code not ready (for =send= with =--wait=) |

** Status Monitoring

Two complementary mechanisms track whether Claude Code is busy:

*** Mechanism 1: Hook-based status file

Claude Code hooks write status to a shared temp directory, keyed by
*SDD session ID* (=CLAUDE_SESSION_ID=, not iTerm2 UUID).

#+begin_example
# In sdd-bridge.sh:
# $SDD_SESSION_ID comes from the hook environment (set at launch time)
STATUS_DIR="/tmp/claude-agent-status"
mkdir -p "$STATUS_DIR"

case "$EVENT" in
  prompt)
    echo "busy" > "$STATUS_DIR/$SDD_SESSION_ID"
    ;;
  response)
    echo "ready" > "$STATUS_DIR/$SDD_SESSION_ID"
    ;;
esac
#+end_example

Emacs reads this file for instant status checks (no iTerm2 API call):

#+begin_example
(defun claude-org-iterm2--read-hook-status (sdd-session-id)
  "Read Claude Code status from hook-written file."
  (let ((file (expand-file-name sdd-session-id
                "/tmp/claude-agent-status")))
    (if (file-exists-p file)
        (string-trim (with-temp-buffer
                       (insert-file-contents file)
                       (buffer-string)))
      "unknown")))
#+end_example

*** Mechanism 2: iTerm2 screen polling (fallback)

Used when hook status is stale or =unknown=. Calls =iterm2-ctl.py status=
with the *iTerm2 session UUID* (different ID from the hook file key).

*** Combined Status Function

Takes *both* IDs — uses SDD session ID for hook file, iTerm2 UUID for
API fallback:

#+begin_example
(defun claude-org-iterm2--get-status (sdd-session-id iterm2-session-id)
  "Get Claude Code status.
SDD-SESSION-ID keys the hook file; ITERM2-SESSION-ID keys the API."
  (let ((hook-status (claude-org-iterm2--read-hook-status
                       sdd-session-id)))
    (if (member hook-status '("ready" "busy"))
        hook-status
      ;; Fallback to iTerm2 API (~200ms)
      (let* ((json-str (claude-org-iterm2--call "status"
                         "--session" iterm2-session-id))
             (data (json-read-from-string json-str)))
        (alist-get 'state data)))))
#+end_example

** Mode-Line Activity Indicator

When Claude Code is busy in iTerm2, the mode-line shows a spinning
indicator — same UX as the json-stream backend.

*** Single Source of Truth: Hooks Only

*CRITICAL*: Only =sdd-bridge.sh= hook callbacks set busy/ready state.
The =execute-ai-block= function does *NOT* call set-busy — it just sends
the prompt and returns. This avoids double-increment when the
=UserPromptSubmit= hook fires shortly after.

Timeline:
#+begin_example
 t=0  Emacs: execute-ai-block → iterm2-ctl.py send  (no set-busy)
 t=~1s  Hook: UserPromptSubmit → sdd-bridge.sh "prompt"
        → set-busy → mode-line spinner starts
 t=~30s Hook: Stop → sdd-bridge.sh "response"
        → set-ready → insert response → mode-line stops
#+end_example

#+begin_example
;; Called by sdd-bridge.sh "prompt" event via MCP:
(defun claude-org-iterm2--set-busy (sdd-session-id)
  "Mark session as busy, start mode-line spinner."
  (claude-org--session-put sdd-session-id :iterm2-busy t)
  (claude-agent-activity-increment))

;; Called by sdd-bridge.sh "response" event via MCP:
(defun claude-org-iterm2--set-ready (sdd-session-id)
  "Mark session as ready, stop mode-line spinner."
  (when (claude-org--session-get sdd-session-id :iterm2-busy)
    (claude-org--session-put sdd-session-id :iterm2-busy nil)
    (claude-agent-activity-decrement)))
#+end_example

Note: =set-ready= guards against double-decrement — only decrements
if currently busy. This handles edge cases like crash recovery.

*** Crash Recovery via Polling

If Claude Code crashes (OOM, SIGKILL), no Stop hook fires. A periodic
timer reads the hook status file and reconciles stale busy states:

#+begin_example
(defun claude-org-iterm2--poll-status ()
  "Periodic reconciliation: detect crashed sessions still marked busy."
  (maphash
   (lambda (sdd-session-id props)
     (when-let* ((iterm2-id (plist-get props :iterm2-session)))
       (when (plist-get props :iterm2-busy)
         ;; Check if iTerm2 session is actually dead
         (let* ((json-str (ignore-errors
                            (claude-org-iterm2--call "status"
                              "--session" iterm2-id)))
                (state (when json-str
                         (alist-get 'state
                           (json-read-from-string json-str)))))
           (when (or (null json-str) (string= state "dead"))
             (claude-org-iterm2--set-ready sdd-session-id))))))
   claude-org--sessions))
#+end_example

Run every 30 seconds when any iTerm2 session is busy. Disabled otherwise.

** Emacs Integration

*** =claude-org-iterm2--call= (internal)

#+begin_example
(defun claude-org-iterm2--call (subcommand &rest args)
  "Call iterm2-ctl.py SUBCOMMAND with ARGS. Return stdout.
ARGS is a flat list of strings. For \"send\", pass prompt via :stdin."
  (let* ((stdin (plist-get args :stdin))
         (cli-args (cl-remove-if
                     (lambda (x) (or (eq x :stdin)
                                     (equal x stdin)))
                     args))
         (flat-args (flatten-tree (cons subcommand cli-args)))
         (script (expand-file-name "scripts/iterm2-ctl.py"
                                   claude-org-iterm2-script-dir))
         (buf (generate-new-buffer " *iterm2-ctl*"))
         ;; Use temp file for stdin if provided
         (stdin-file (when stdin
                       (let ((f (make-temp-file "iterm2-stdin-")))
                         (with-temp-file f (insert stdin))
                         f)))
         (exit-code (apply #'call-process
                           "python3" stdin-file buf nil
                           script flat-args)))
    (unwind-protect
        (with-current-buffer buf
          (if (= exit-code 0)
              (string-trim (buffer-string))
            (error "iterm2-ctl %s failed (exit %d): %s"
                   subcommand exit-code
                   (string-trim (buffer-string)))))
      (kill-buffer buf)
      (when stdin-file (delete-file stdin-file t)))))
#+end_example

*Why stdin/file, not CLI args?* Prompts and system prompts can be
multi-KB. CLI args are limited by =ARG_MAX= (~262KB on macOS). Using
stdin or temp files avoids this limit entirely.

*** =claude-org-iterm2--ensure-session= (internal)

Core logic: find or create iTerm2 tab for current SDD session.
Returns iTerm2 session UUID. Reuses existing tab if title matches.

Also stores the iTerm2 UUID in the session hash so polling can find it.

#+begin_example
(defun claude-org-iterm2--ensure-session ()
  "Ensure an iTerm2 session exists for the current SDD story.
Returns the iTerm2 session UUID. Launches if needed."
  (let* ((sdd-session-id (claude-org-sdd--current-session-id))
         (saved-iterm2-id (org-entry-get nil "ITERM2_SESSION_ID" t))
         (title (claude-org-iterm2--tab-title)))
    ;; Check saved iTerm2 session is alive
    (if (and saved-iterm2-id
             (condition-case nil
                 (let* ((json-str (claude-org-iterm2--call
                                    "status" "--session" saved-iterm2-id))
                        (data (json-read-from-string json-str)))
                   (not (string= (alist-get 'state data) "dead")))
               (error nil)))  ; iterm2-ctl failed → treat as dead
        saved-iterm2-id
      ;; Launch: finds existing tab by title or creates new
      (let* ((system-prompt (claude-org-sdd-bridge-system-prompt
                              (buffer-file-name) sdd-session-id))
             (sp-file (make-temp-file "claude-sp-"))
             (cli-session (claude-org-sdd-bridge-get-cli-session
                            (buffer-file-name) sdd-session-id))
             (project-root (or (claude-org--get-project-root)
                               default-directory)))
        (with-temp-file sp-file (insert system-prompt))
        (unwind-protect
            (let ((result (apply #'claude-org-iterm2--call
                            "launch"
                            "--title" title
                            "--cwd" project-root
                            "--system-prompt-file" sp-file
                            (when cli-session
                              (list "--resume" cli-session)))))
              (org-set-property "ITERM2_SESSION_ID" result)
              ;; Store mapping so polling can find it
              (claude-org--session-put sdd-session-id
                                      :iterm2-session result)
              (save-buffer)
              (message "Claude Code in iTerm2 (session: %s)" result)
              result)
          (delete-file sp-file t))))))
#+end_example

#+begin_example
(defun claude-org-iterm2--execute-ai-block ()
  "Execute current AI block via iTerm2 backend."
  (let* ((prompt (claude-org--extract-ai-block-content))
         (sdd-session-id (claude-org-sdd--current-session-id))
         (iterm2-id (claude-org-iterm2--ensure-session))

                   sdd-session-id iterm2-id)))

                  status))

     "send" "--session" iterm2-id :stdin prompt)

#+end_example

** Session Lifecycle

#+begin_example
 1. User sets CLAUDE_BACKEND=iterm2 on org section
 2. User writes AI block, presses C-c C-c
    → ensure-session: search tabs by title "<heading> [<sdd-id>]"
    → No match: create tab, launch claude, save ITERM2_SESSION_ID
    → Match found: reuse existing tab
 3. send prompt via stdin → bracketed paste into Claude Code TUI
 4. Hook: UserPromptSubmit → sdd-bridge.sh "prompt"
    → set-busy → mode-line spinner starts
    → insert-prompt into org file
 5. Claude Code processes (user can press I to watch in iTerm2)
 6. Hook: Stop → sdd-bridge.sh "response"
    → set-ready → mode-line spinner stops
    → insert-response into org file
 7. Next AI block → C-c C-c → repeat from step 3
 8. Emacs restart → ITERM2_SESSION_ID persists in org property
    → ensure-session checks status via API → reuses if alive
 9. Tab closed / crashed → status "dead"
    → ensure-session auto-relaunches on next C-c C-c
    → polling timer catches stale busy state within 30s
10. User presses K → cancel → Escape sent
    → Stop hook fires → set-ready (not eager)
#+end_example

** Trade-offs

| Advantage | Disadvantage |
|-----------+--------------|
| Full OOM isolation | macOS only (iTerm2) |
| GPU rendering (Metal) | ~200ms per API call (WebSocket setup) |
| Persistent session IDs | Requires Python 3 + iterm2 package |
| Tab reuse by title (no stale tabs) | Must enable Python API in iTerm2 settings |
| Same mode-line UX as json-stream | Response is batch (not streaming to org) |
| Cancel support | Hook status file is an extra moving part |
| SDD bridge works standalone with any terminal | iTerm2 control layer is macOS only |

** Edge Cases and Mitigations

| Scenario | Problem | Mitigation |
|----------+---------+------------|
| Claude Code OOM crash | No Stop hook fires | Polling timer detects dead session, calls set-ready |
| iTerm2 not running | =iterm2-ctl.py= exits 1 | =ensure-session= shows user-friendly error |
| Python API not enabled | =iterm2-ctl.py= exits 1 | Error message includes setup instructions |
| Tab closed by user | Status returns "dead" | =ensure-session= auto-relaunches on next C-c C-c |
| Emacs restart mid-query | iTerm2 session alive, Emacs state lost | =ITERM2_SESSION_ID= persists; hook file shows "busy"; polling reconciles |
| Prompt > 256KB | CLI arg overflow | Prompt sent via stdin, system prompt via temp file |
| Two org files, same heading | Tab title collision | SDD session ID suffix ensures uniqueness |
| Cancel but Stop hook doesn't fire | Mode-line stuck on busy | Polling timer reconciles within 30s |
| =call-process= blocks during =launch= | Emacs unresponsive ~15s | Acceptable for initial launch; future: =start-process= async |
| User types directly in iTerm2 tab | Prompt not in org file | =UserPromptSubmit= hook still fires → inserts into org |

* Open Questions

1. *Backend switching*: Can a session switch backends mid-story?
   /Recommendation: no — backend is fixed per SDD session./
   /Set CLAUDE_BACKEND once on the story heading./

2. *vterm support for claude-cli*: eat-only initially, add vterm later?
   /Recommendation: yes, eat is lighter and already a dependency./

3. *System prompt refresh*: When =:system_prompt:= sections change, how
   to propagate to the running terminal?
   /Recommendation: manual refresh command (kill + relaunch)./

4. *Hook status file cleanup*: =/tmp/claude-agent-status/= files
   accumulate. When to clean up?
   /Recommendation: clean on =claude-sdd= launch and on Emacs exit hook./

5. *Connection latency (iTerm2)*: Each call takes ~200ms. Worth building
   a persistent daemon?
   /Recommendation: start stateless, optimize if latency becomes a problem./

6. *JSON stream OOM mitigation*: Should json-stream backend auto-restart
   on SIGKILL and resume the session?
   /Recommendation: session recovery already exists. Consider switching/
   /to iterm2 backend for long sessions instead./

7. *Cross-platform iTerm2 alternative*: For Linux users, should we
   support Kitty as a programmatic terminal backend?
   /Recommendation: defer. SDD bridge standalone mode works with any/
   /terminal. Add Kitty control layer as a future backend./
