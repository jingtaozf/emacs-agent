* Test Taxonomy

Tests are organized by user journey groups, not by function groups.
Each journey simulates a real developer workflow end-to-end.

| Journey | Priority | Description |
|---------+----------+-------------|
| J1: New Project Setup | HIGH | Create workspace, set color, execute first query |
| J2: Multi-Story Development | HIGH | Multiple stories in one workspace, switch between them |
| J3: Session Continuity | HIGH | --resume reuses CLI session across executions |
| J4: Workspace Color Palette | MEDIUM | Named colors, hex colors, clear-color |
| J5: Error Recovery | HIGH | Cancel, stale ref recovery, orphan cleanup |
| J6: Status and Sidebar | MEDIUM | set-status, clear-status, sidebar-state readback |
| J7: Verbose Output | MEDIUM | Verbose buffer populated with Claude Code output |
| J8: Scaffold and Navigation | LOW | insert-workspace, insert-story, goto-story |

* Naming Convention

=T<N>-<journey>-<scenario>=

Examples:
- T40-session-continuity-resume
- T41-color-palette-named
- T42-sidebar-status-set

Existing tests (T1-T28) keep their original names for backward compatibility.

* Workspace Design

Each test workspace simulates a real project:

| Workspace | Simulates | Color |
|-----------+-----------+-------|
| e2e-webapp-dev | Web application project | blue |
| e2e-fullstack | Full-stack development | green |
| e2e-infra-ops | Infrastructure operations | orange |
| e2e-color-palette | Color feature testing | (varies) |
| e2e-recovery | Error recovery scenarios | red |

* Property Oracle Pattern

Org properties are ground truth for test assertions:

- CMUX_WORKSPACE_ID: cmux workspace UUID
- CMUX_SURFACE_ID: cmux surface ref
- CLAUDE_CLI_SESSION: Claude Code conversation ID (for --resume)
- ACTIVE_STORY: current story name
- WORKSPACE_COLOR: sidebar color
- CLAUDE_SESSION_ID: Emacs session key

After each execution, verify:
1. Org properties match expected values
2. cmux CLI output matches org properties
3. Phoenix spans reference correct session IDs

* Phoenix Trace Tree

For a standard AI block execution:

#+begin_example
execute-ai-block (root, parentId=null, kind=SERVER)
+-- cmux-ensure-session (kind=INTERNAL)
+-- cmux-execute (kind=INTERNAL)
|   +-- cmux-send-text (kind=CLIENT)
+-- cmux-wait-for-ready
+-- cmux-query-completed
+-- handle-complete (has duration-sec, tool-call-count attrs)
#+end_example

* Fixture Rules

- Append-only: never delete existing test stories
- Every heading gets a unique CUSTOM_ID
- Every workspace: CLAUDE_SESSION_ID, CLAUDE_BACKEND: cmux
- System prompts describe realistic project contexts
- AI queries are practical developer tasks (not "say hello")
- No duplicate CUSTOM_IDs across the file

* Priority Tiers

| Tier | Definition | Action on failure |
|------+------------+-------------------|
| HIGH | Blocks release -- core workflow broken | Fix immediately |
| MEDIUM | Regression risk -- secondary features | Fix before next release |
| LOW | Nice-to-have -- cosmetic or rare paths | Track, fix when convenient |

* Anti-Flakiness Principles

Based on industry research (2025-2026), these principles guide test reliability:

1. *Explicit wait conditions over fixed sleeps*: Never assert immediately after
   an action. Wait for the state to be reachable. ~45% of all E2E flakiness
   comes from async wait issues (timers instead of condition polling).

2. *Stable selectors*: Navigate org by CUSTOM_ID, never heading text. CUSTOM_IDs
   are unique stable identifiers; heading text can match multiple sections.

3. *Test isolation*: Each test uses its own session-key and temp buffer. No
   shared state leaks between tests. Mock only the external gateway
   (=claude-org-cmux--call=), never Emacs internals.

4. *Deterministic assertions*: Assert on org properties and function return
   values, not on timing-dependent output. Properties are ground truth.

5. *Guard against timer-based flakiness*: Loop iterations use cancel guards
   (check exec-status before firing). Tests verify guards work for both
   "cancelled" and "error" states.
