#+TITLE: Design Doc: VTerm Inside Emacs
#+DATE: 2026-03-12
#+STATUS: removed (in-Emacs vterm/eat backend deleted in commit 1038144)

* Reality check (2026-04-27)
The "run Claude inside an Emacs vterm/eat buffer" approach was implemented,
then deleted.  External terminal multiplexers (cmux on macOS, tmux on
cross-platform) replaced it under the Tri-Protocol architecture.  This doc
remains as a useful comparison of in-Emacs terminal emulator options
(vterm vs eat), but the feature it proposed is no longer pursued.

* Goals

1. Provide a high-quality terminal emulator inside Emacs for the claude-agent
   project, suitable for running Claude Code CLI and other interactive programs
2. Minimize external dependencies while maximizing terminal compatibility
3. Support macOS (Intel + Apple Silicon) and Linux as primary platforms
4. Enable tight integration between terminal sessions and claude-agent workflows
5. Avoid reinventing the wheel — leverage proven, battle-tested components

* Non-Goals

1. Windows support in initial implementation (can be added later)
2. Replacing system terminal emulators (this is for Emacs-embedded use)
3. Supporting every obscure terminal escape sequence (focus on xterm-256color)
4. Building a general-purpose terminal package for MELPA (initially internal)

* Approach Analysis

** Option A: Fork and Improve emacs-libvterm

*** Description
Fork the emacs-libvterm project (~6,500 LOC) and fix known issues while adding
claude-agent integration.

*** Pros
- Proven architecture with ~1,700 GitHub stars
- Uses battle-tested libvterm engine (same as Neovim)
- Small, auditable codebase
- Shell integration scripts already exist (bash/zsh/fish)
- Community knowledge transferable

*** Cons
- Inherits C module complexity (CMake build, libvterm dependency)
- Segfault risk from C code
- No Windows support
- Apple Silicon build issues need fixing
- Alpha-stage API instability

*** Effort
Medium — mostly improvement work, not greenfield development.

** Option B: Pure Elisp (EAT-inspired)

*** Description
Build a pure-Elisp terminal emulator, potentially forking or adapting EAT's
approach (~10,000 LOC).

*** Pros
- Zero build dependencies
- No crash risk
- Works everywhere Emacs runs (including Windows)
- Better Emacs integration (no module boundary)
- Text rewrap on resize works naturally

*** Cons
- Slower for high-throughput output (fundamental Elisp limitation)
- Very large single-file design (EAT) is hard to maintain
- Less tested than libvterm for edge cases
- Would need to reimplement terminal state machine

*** Effort
High — terminal emulation in Elisp is complex (EAT is ~10K LOC).

** Option C: Rust Dynamic Module with termwiz/alacritty_terminal

*** Description
Create an Emacs dynamic module in Rust wrapping termwiz or alacritty_terminal
crate, compiled to .so/.dylib.

*** Pros
- Modern, memory-safe terminal engine (no segfaults)
- Well-tested crates (millions of downloads)
- Cross-platform potential (termwiz supports Windows)
- Active development and rich feature set

*** Cons
- Rust toolchain requirement for building
- Rust → Emacs module FFI is more complex than C
- Larger dependency tree than libvterm
- Less community familiarity in Emacs ecosystem
- Compilation time significantly longer than C

*** Effort
High — Rust-Emacs FFI, new build system, unfamiliar territory for Emacs users.

** Option D: Hybrid — libvterm C module with EAT-style Elisp fallback

*** Description
Primary: Use libvterm via C dynamic module (like emacs-libvterm).
Fallback: Pure Elisp terminal emulation for environments without module support.

*** Pros
- Best of both worlds: performance when available, compatibility otherwise
- Incremental development: start with libvterm fork, add Elisp fallback later
- Covers all platforms eventually

*** Cons
- More code to maintain (two implementations)
- Behavior differences between backends
- Testing surface doubles

*** Effort
Very High — essentially building two solutions.

* Recommended Approach: Option A (Fork emacs-libvterm)

** Rationale

1. *Smallest codebase to migrate*: ~6,500 LOC total (4K C + 2.5K Elisp)
2. *Proven in production*: Used by thousands of Emacs users daily
3. *Best performance*: libvterm C engine handles heavy output efficiently
4. *Fastest to deliver*: Fork + fix + integrate, rather than build from scratch
5. *claude-agent alignment*: Claude Code can help migrate and improve the
   business logic rapidly — this is exactly the "migrate from battle-tested
   codebase" strategy the project favors
6. *libvterm is the right engine*: ~7K LOC C library, MIT license, used by
   Neovim, clean API, active maintenance

** Key Improvements Over Upstream

| Issue | Fix Strategy |
|-------+-------------|
| No text rewrap on resize | Implement resize callback that re-renders with new dimensions |
| Apple Silicon build | Fix CMakeLists.txt architecture detection, test on M1/M2 |
| Segfault crashes | Add null checks, defensive programming, error recovery |
| No multi-session | Built-in session management (integrate with claude-agent sessions) |
| No Evil-mode | Add evil-state-aware keybinding layer |
| Build complexity | Simplify: vendored libvterm, auto-detect toolchain |

* Technical Design

** Architecture
#+begin_example
  ┌──────────────────────────────────────┐
  │  claude-agent-vterm.el               │  Elisp: buffer mgmt, keybindings,
  │  (Integration Layer)                 │  session management, AI hooks
  ├──────────────────────────────────────┤
  │  vterm-module.so / .dylib            │  C: Emacs module API ↔ libvterm
  │  (Dynamic Module)                    │  bridge, scrollback, rendering
  ├──────────────────────────────────────┤
  │  libvterm                            │  C: VT escape parser, screen state
  │  (Vendored Library)                  │  machine, cell storage
  └──────────────────────────────────────┘
       ↕ pty
  ┌──────────────────────────────────────┐
  │  Shell / Claude Code CLI / Program   │
  └──────────────────────────────────────┘
#+end_example

** Data Flow

1. User types key → Elisp captures → C module translates → libvterm processes
   → writes to pty → shell/program receives
2. Shell/program outputs → pty → C module reads → libvterm parses escape
   sequences → updates screen state → C module renders to Emacs buffer
   (text + face properties)

** Module Structure

| Component | File(s) | Purpose |
|-----------+---------+---------|
| C module | vterm-module.c, elisp.c, utf8.c | libvterm ↔ Emacs bridge |
| Build | CMakeLists.txt | Build system (vendored libvterm) |
| Core Elisp | claude-agent-vterm.el | Buffer management, modes, keybindings |
| Integration | claude-agent-vterm-integration.el | claude-agent session hooks |
| Shell scripts | etc/*.sh | Shell integration (directory tracking) |

** Build Strategy

- Vendor libvterm source inside the project (MIT license allows this)
- CMake builds both libvterm and the Emacs module in one step
- Auto-detect Emacs module header location
- Pre-built binaries for common platforms (macOS arm64/x86_64, Linux x86_64)

** Integration with claude-agent

- =claude-agent-vterm-open= — open a vterm buffer connected to a claude-agent
  session
- =claude-agent-vterm-send-command= — send text to the terminal programmatically
- Terminal output hooks for AI-assisted command suggestions
- Session persistence: terminal state saved/restored with claude-agent sessions
- MCP tool: expose terminal interaction as an MCP tool for the AI

* Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------+------------+--------+------------|
| libvterm upstream changes | Low | Medium | Vendor specific version, merge selectively |
| Segfault in production | Medium | High | Defensive C code, crash recovery in Elisp |
| Build breaks on new platforms | Medium | Medium | CI/CD for all target platforms |
| Performance not sufficient | Low | Medium | libvterm is proven fast; profile & optimize |
| Scope creep | High | Medium | Strict phased approach, MVP first |
