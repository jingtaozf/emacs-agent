#+TITLE: JSON Stream Backend — Business Logic and Redesign
#+DATE: 2026-03-13
#+STATUS: shipped (now agent-family of Tri-Protocol)

* Reality check (2026-04-27)
The JSON-stream / stdio backend shipped and was refined under the
*Tri-Protocol Backend Refactor* (2026-04-24, shipped 2026-04-27).  Today it
lives as the "agent-family" side: `claude-agent-claude-code-backend`,
`claude-agent-acp-opencode`, `-acp-gemini`, `-acp-codex` — all implementing
Protocol 2a (agent-wire) on top of root Protocol 1 (lifecycle).  Stream-end
detection / multi-response handling fixes from this design landed in the
same era.  See
=claude-agent-backend.org= → "Tri-Protocol Architecture" for the
authoritative architecture.

* Overview

This document captures the *current* business logic of the JSON stream backend
in =claude-agent-backend.org=, identifies concrete bugs discovered through
analysis of 651+ real session transcripts, and proposes a redesign for reliable
stream-end detection, multi-response handling, and background agent management.

* Goals

- Document the end-to-end lifecycle of a JSON stream query
- Map every decision point that determines "is the stream done?"
- Identify the exact completion signal chain and its failure modes
- *Propose a new design* for reliable completion detection
- Handle multiple responses / tool-use cycles correctly
- Handle background agents (Task tool) without hanging

* Non-Goals

- Documenting the org-mode layer (=claude-org.org=) in detail
- Changing the Claude CLI protocol (all fixes are Emacs-side)
- Persistent/bidirectional mode redesign (separate effort)

* Part 1: Current Business Logic

** Architecture: End-to-End Flow

#+begin_example
claude-agent-query(prompt, options, callbacks)
  │
  ▼
claude-agent--start-process(prompt, options, :callbacks...)
  │  Creates subprocess: claude --print --output-format stream-json
  │  Attaches filter + sentinel via process-get/process-put
  │  Stores state in claude-agent--process-state struct
  │
  ▼
CLI outputs newline-delimited JSON (JSONL)
  │
  ├─ {"type":"system","subtype":"init", ...}     ← session_id captured here
  ├─ {"type":"assistant","message":{...}}        ← tokens streamed
  ├─ {"type":"user","message":{...}}             ← tool results
  ├─ {"type":"rate_limit_event",...}             ← rate limit warnings
  ├─ {"type":"control_request",...}              ← permission/MCP requests
  └─ {"type":"result","subtype":"success",...}   ← FINAL message
  │
  ▼
Process exits → sentinel fires → on-complete callback
#+end_example

** Key Data: Process State Struct

The =claude-agent--process-state= struct holds all per-query state:

| Field | Purpose |
|-------+---------|
| =process= | The Emacs process object |
| =json-buffer= | Accumulator for partial JSON lines |
| =callback= | =on-message= callback (each parsed message) |
| =token-callback= | =on-token= callback (streaming text fragments) |
| =error-callback= | =on-error= callback |
| =complete-callback= | =on-complete= callback (fired by sentinel) |
| =got-result= | Boolean flag — set to =t= when a =result= message arrives |
| =closed= | Boolean flag — set to =t= by sentinel |
| =ready= | Boolean flag — filter ignores output when nil |
| =cancelled= | Boolean flag — set by cancel, skips complete callback |
| =session-id= | Captured from =system/init= message |
| =session-key= | Org-mode session key (for verbose logging) |
| =request-id= | Owner request ID (for background task matching) |

** Component 1: Process Filter (Data Ingestion)

=claude-agent--process-filter= is called by Emacs whenever data arrives.

*** Flow

1. Guard: skip if =state= is nil or =ready= is nil
2. Append =output= to =json-buffer=
3. Check buffer overflow (> =claude-agent-max-json-buffer-size=)
   - If overflow: clear buffer, call error callback, kill process
4. Call =claude-agent--process-json-buffer= to extract complete lines

*** JSON Buffer Processing

=claude-agent--process-json-buffer= extracts complete JSONL lines:

1. Regex match: =^\\([^\n]+\\)\n= (line ending with newline)
2. For each complete line:
   - Parse JSON via =claude-agent--try-parse-json=
   - If =type= is ="control_request"=: dispatch to =claude-agent--handle-control-request=
   - Otherwise: dispatch via =claude-agent-handle-message= (cl-defgeneric)
3. Remaining partial line stays in =json-buffer=

** Component 2: Message Dispatch (cl-defgeneric)

=claude-agent-handle-message= dispatches by message type symbol:

| Type | Handler | Extra Logic |
|------+---------+-------------|
| =assistant= | dispatch PreToolUse hooks → =process-normal-message= | Token extraction |
| =user= | dispatch PostToolUse hooks → =process-normal-message= | Tool results |
| =result= | dispatch Stop hooks → =process-normal-message= | *Sets got-result flag* |
| =rate_limit_event= | Warning message if near limit | Deduplication by type |
| (default) | =process-normal-message= | System, init, etc. |

** Component 3: Normal Message Processing

=claude-agent--process-normal-message= is the central processing function:

#+begin_example
(defun claude-agent--process-normal-message (parsed state)
  1. Extract callbacks from state
  2. Check json-error via claude-agent--extract-json-error
  3. IF is-result (type == "result"):
       → Set got-result flag to t                    ← CRITICAL
  4. IF json-error:
       → Call error-callback
  5. ELSE:
       → Call token-callback (extract tokens)
       → Parse message struct, call message-callback
       → Capture session-id from system/init
       → Set got-result again if result-message-p    ← REDUNDANT with step 3
  6. Call claude-agent--maybe-close-stdin             ← TRIGGERS SHUTDOWN
#+end_example

*Note*: =got-result= is set twice — once at the raw JSON level (step 3) and
once at the parsed struct level (step 5). This is intentional redundancy to
ensure the flag is set even if message parsing fails.

** Component 4: Stdin Close (Shutdown Signal)

=claude-agent--maybe-close-stdin= is called after every normal message.
It only acts when =type= is ="result"=.

*** Decision Tree

#+begin_example
Is type == "result"?
  │
  NO → return (do nothing)
  │
  YES
  │
  ▼
Has pending background tasks for THIS process?
  │
  YES → log "background tasks pending", return
  │
  NO
  │
  ▼
Has pending control requests?
  │
  YES → log "control requests pending", return
  │
  NO
  │
  ▼
Is claude-agent-stdin-close-delay set?
  │
  NIL → log "auto-close disabled", return
  │
  NUMBER
  │
  ▼
Is delay == 0?
  │
  YES → process-send-eof immediately
  │
  NO → run-at-time delay:
         Re-check pending work
         If clear → process-send-eof
#+end_example

*Default delay*: =claude-agent-stdin-close-delay= (0.1 seconds).

*What process-send-eof does*: Sends EOF to stdin, causing the CLI subprocess
to shut down gracefully. The process then exits, triggering the sentinel.

** Component 5: Process Sentinel (Completion)

=claude-agent--process-sentinel= fires when the process exits.

*** Flow

1. Set =closed= to =t=, =ready= to =nil=
2. Process any remaining JSON in buffer (flush)
3. Handle remaining content without trailing newline
4. Decision: is this an abnormal exit?

*** Abnormal Exit Detection

=claude-agent--is-abnormal-exit-p= returns =t= when ALL of:
- =claude-agent-auto-recovery= is enabled
- =session-id= exists (needed for resume)
- =got-result= is *NOT* set (no result message received)
- =cancelled= is *NOT* set
- Event matches "killed", "exited abnormally", or "finished"

*Key insight*: A "finished" exit *without* =got-result= is treated as abnormal.
This means the =got-result= flag is the *sole* differentiator between
normal completion and crash recovery.

*** Normal Exit Path

=claude-agent--sentinel-handle-normal-exit=:

1. Skip if =cancelled= (cancel already cleaned up)
2. If event matches "finished": call =complete-callback= with =nil= (success)
3. If event matches "exited abnormally": call =complete-callback= with error plist
4. Then: =claude-agent--sentinel-cleanup= (kill buffer, clean registry)

*** Abnormal Exit Path

=claude-agent--sentinel-handle-abnormal-exit=:

1. Insert recovery message via token-callback
2. Kill orphaned child processes
3. Minimal cleanup
4. Resume session via =claude-agent--resume-session=

** Component 6: Completion Signal Chain

The full chain from "response done" to "session cleanup":

#+begin_example
1. CLI sends {"type":"result"} as last JSONL line
       │
       ▼
2. Filter accumulates → process-json-buffer extracts line
       │
       ▼
3. handle-message dispatches to (eql 'result) method
       │
       ▼
4. process-normal-message:
       ├─ Sets got-result = t
       ├─ Calls token-callback (extracts any final tokens)
       ├─ Calls message-callback (result message struct)
       └─ Calls maybe-close-stdin
              │
              ▼
5. maybe-close-stdin:
       ├─ Checks pending work
       └─ Schedules process-send-eof (0.1s delay)
              │
              ▼
6. EOF sent → CLI shuts down → process exits
       │
       ▼
7. Sentinel fires:
       ├─ Flushes remaining JSON
       ├─ Checks is-abnormal-exit-p (NO, got-result is set)
       └─ Calls sentinel-handle-normal-exit
              │
              ▼
8. complete-callback(nil) called
       │
       ▼
9. claude-org--handle-complete:
       ├─ Stops spinner
       ├─ Inserts final newline
       ├─ Runs completion hooks
       ├─ Checks loop continuation
       └─ Resets session state (busy=nil, marker freed)
              │
              ▼
10. Queue processing: next queued block (if any) starts
#+end_example

** Component 7: Background Task Tracking

=claude-agent--background-task-tracker= runs on =claude-agent-post-tool-use-functions=.

*** Registration

| Trigger | Detection | Action |
|---------+-----------+--------|
| Task tool (async) | =(plist-get tool-use-result :isAsync)= is =t= | =puthash agentId= |
| Bash tool (bg) | =:backgroundTaskId= field present | =puthash bgTaskId= |

*** Completion

| Trigger | Detection | Action |
|---------+-----------+--------|
| TaskOutput poll | =(plist-get task :status) = "completed"= | =remhash task-id= |

*** How it blocks stdin close

=maybe-close-stdin= calls =claude-agent--has-pending-background-tasks-p= with
the process's =request-id=. If any pending task maps to that owner, stdin close
is skipped.

* Part 2: Real-World Protocol Analysis

Based on analysis of 651+ real Claude Code session transcripts.

** Message Types: Complete Taxonomy

*** =system= (init — always first)

#+begin_src json
{"type":"system","subtype":"init","session_id":"...","apiCreditsRemaining":{...}}
#+end_src

*** =assistant= (streaming tokens — same =id= across chunks)

#+begin_src json
{"type":"assistant","message":{"id":"msg_xxx","role":"assistant","model":"...","content":[
  {"type":"text","text":"..."},
  {"type":"thinking","thinking":"...","signature":"..."},
  {"type":"tool_use","id":"toolu_xxx","name":"Bash","input":{...}}
],"stop_reason":null}}
#+end_src

=stop_reason= values:
- =null= — mid-stream, more tokens coming
- ="end_turn"= — assistant finished naturally
- ="tool_use"= — pausing for tool execution
- ="stop_sequence"= — CLI-initiated interrupt (dequeue)

*** =user= (tool results — mid-stream)

#+begin_src json
{"type":"user","message":{"role":"user","content":[
  {"type":"tool_result","tool_use_id":"toolu_xxx","content":[...],"is_error":false}
]},"tool_use_result":{...}}
#+end_src

The top-level =tool_use_result= field carries extra metadata (e.g., =isAsync=,
=agentId=, =backgroundTaskId=).

*** =result= (final — always last, exactly one per CLI invocation)

#+begin_src json
{"type":"result","subtype":"success","duration_ms":3456,"is_error":false,
 "num_turns":2,"session_id":"...","total_cost_usd":0.005678,
 "usage":{"input_tokens":150,"output_tokens":45,...},"result":""}
#+end_src

=subtype= values: ="success"=, ="error"=, ="error_during_execution"=,
="invalid_request"=, ="rate_limit"=.

*** =rate_limit_event= (warning, non-fatal)

#+begin_src json
{"type":"rate_limit_event","rate_limit_info":{"status":"allowed_warning","utilization":0.85,...}}
#+end_src

*** =control_request= (bidirectional mode — permission gating)

#+begin_src json
{"type":"control_request","request_id":"req_123","request":{"subtype":"can_use_tool",...}}
#+end_src

** Typical Message Sequences

*** Simple query (no tools)

#+begin_example
system/init → assistant* (stop_reason=null) → assistant (end_turn) → result/success
#+end_example

*** Single tool cycle

#+begin_example
system/init → assistant (tool_use, stop_reason="tool_use")
            → user (tool_result)
            → assistant (end_turn) → result/success
#+end_example

*** Multi-tool turns

#+begin_example
system/init → assistant (tool_use A)
            → user (tool_result A)
            → assistant (tool_use B)
            → user (tool_result B)
            → assistant (end_turn) → result/success
#+end_example

*** Parallel tool use (common — 333 instances of 2 parallel, up to 31 parallel)

#+begin_example
system/init → assistant (tool_use A, tool_use B, tool_use C)  ← one message, 3 tools
            → user (tool_result A, tool_result B, tool_result C)
            → assistant (end_turn) → result/success
#+end_example

*** Background agent (Task tool async)

#+begin_example
system/init → assistant (tool_use Task)
            → user (tool_result: "Async agent launched successfully.\nagentId: a65b288...")
            → assistant (continues other work...)
            → [background agent runs independently]
            → [CLI injects task-notification via queue-operation]
            → assistant (acknowledges completion)
            → assistant (end_turn) → result/success
#+end_example

*** Error (rate limit)

#+begin_example
system/init → result/error (is_error=true)
#+end_example

*** Crash mid-stream

#+begin_example
system/init → assistant (partial text)
           → [process dies — no result message]
           → sentinel: got-result=nil → auto-recovery/resume
#+end_example

* Part 3: Identified Issues

** Issue 1: maybe-close-stdin Never Retries (CRITICAL)

When pending background tasks or control requests exist at the moment the
=result= message arrives, =maybe-close-stdin= logs and returns. There is *no*
retry mechanism — no timer, no watcher, no re-check. The process hangs
indefinitely.

*Impact*: The stream never completes. =on-complete= never fires. The session
stays =:busy t= forever. The user sees a spinning indicator that never stops.

*Reproduce*: Execute an AI block that spawns a background agent. The result
message arrives before the background agent completes. stdin close is blocked.
The process hangs.

** Issue 2: Background Task Tracker Is Dead Code (but harmless)

The tracker checks =(plist-get tool-use-result :isAsync)= but real Task tool
results return *plain text* (not JSON):

#+begin_example
"Async agent launched successfully.\nagentId: a65b288..."
#+end_example

The =:isAsync= field is never present because =tool_use_result= in the outer
JSON envelope is either =nil= or contains different metadata. The tracker
*never registers* real async tasks.

*Why this doesn't matter*: The CLI waits for ALL background agents to complete
before emitting the =result= message.  By the time =result= arrives, all
agent output has already been streamed to the org buffer via =on-token=.
The SDK never needed to block stdin close for background agents — the CLI
handles this internally.

*Impact*: =claude-agent--pending-background-tasks= is always empty for real
Task launches.  =maybe-close-stdin= sees no pending tasks and closes stdin
normally.  This is correct behavior (by accident).

*Recommendation*: Remove the background task blocking from =maybe-close-stdin=.
Keep the tracker for informational display only (mode-line, session manager),
but fix the detection to parse plain text agentId if we want accurate display.

** Issue 3: Completion Callback Only From Sentinel

The =on-complete= callback is *only* called from the sentinel (when process
exits). It is *never* called directly from the filter when the =result=
message is received. This means completion is tied to process lifetime, not
to protocol-level completion.

If the process stays alive (e.g., pending work blocking stdin close),
completion is indefinitely delayed.

** Issue 4: Redundant got-result Setting

The =got-result= flag is set in two places. Not harmful but indicates fragility.

** Issue 5: No Timeout / Watchdog

There is no timeout mechanism. If the CLI hangs (network issue, API hang,
internal deadlock), the process stays alive and the session stays busy forever.
The user must manually kill the process or restart Emacs.

** Issue 6: Sentinel Processes JSON After ready=nil

The sentinel calls =process-json-buffer= after setting =ready= to nil.
This bypasses the filter's ready guard — intentional but creates a window
where message processing happens after the stream is "closed".

* Part 4: Proposed Redesign

** Design Principle: Trust the =result= Message

The =result= message is the *protocol-level* signal that the CLI is done.  There
is *exactly one* =result= per CLI invocation (confirmed across 24 fixtures and
698 real sessions — zero exceptions).

*** Background agents are handled BEFORE =result=

The CLI does NOT emit =result= while background agents are still running.
The actual sequence is:

#+begin_example
assistant (launches Task async, stop_reason="tool_use")
  → user (tool_result: "Async agent launched...agentId: a65b288...")
  → assistant (may do other work while waiting)
  → [CLI waits for background agent to finish]
  → [CLI injects task-notification via queue-operation]
  → assistant (acknowledges agent result, produces more output)
  → assistant (end_turn)
  → result/success       ← ONLY emitted after ALL agents complete
#+end_example

This means:
1. All response tokens — including those generated after background agent
   completion — are streamed via =on-token= BEFORE =result= arrives
2. By the time =result= arrives, ALL content is already in the org buffer
3. The SDK does NOT need to keep the process alive for background agents
4. =result= truly means "everything is done"

*** After =result=, the only remaining work is:

1. Process any pending =control_request= responses already in flight
2. Close stdin so the process exits cleanly

** Change 1: Retry Loop for maybe-close-stdin

Replace the single-shot logic with a polling retry:

#+begin_src elisp
(defun claude-agent--maybe-close-stdin (process parsed)
  "Close stdin when result message arrives.
Retries periodically if control requests are still pending."
  (when (equal (plist-get parsed :type) "result")
    (claude-agent--schedule-stdin-close process)))

(defun claude-agent--schedule-stdin-close (process &optional attempt)
  "Try to close PROCESS stdin. Retry up to max attempts if control requests pending."
  (let ((attempt (or attempt 0))
        (max-attempts 50)   ;; 50 × 0.1s = 5s max wait
        (delay 0.1))
    (cond
     ;; Process already dead — nothing to do
     ((not (process-live-p process)) nil)
     ;; No pending control requests — close now
     ((not (claude-agent--has-pending-control-requests-p))
      (claude-agent--debug-log "Closing stdin (attempt %d)" attempt)
      (process-send-eof process))
     ;; Max attempts reached — force close
     ((>= attempt max-attempts)
      (claude-agent--debug-log "Force-closing stdin after %d attempts" attempt)
      (process-send-eof process))
     ;; Retry after delay
     (t
      (claude-agent--debug-log "Control requests pending, retry %d/%d" attempt max-attempts)
      (lexical-let ((proc process)
                    (next-attempt (1+ attempt)))
        (run-at-time delay nil
                     (lambda ()
                       (claude-agent--schedule-stdin-close proc next-attempt))))))))
#+end_src

Key changes:
- *Retries* instead of give-up-on-first-failure
- *Max attempts* (5 seconds) prevents infinite hang
- *Force close* after timeout — the process will exit, sentinel will fire
- *No background task check* — removed (see Change 2)

** Change 2: Remove Background Task Blocking from Stdin Close

The background task tracker's stdin-close guard should be removed because:

1. *The CLI waits for background agents internally* — it does NOT emit
   =result= until all agents complete. By the time we receive =result=,
   all agent output is already streamed. There is nothing to wait for.
2. *The tracker is broken anyway* — =isAsync= / =agentId= detection assumes
   JSON but real Task results are plain text
3. *Blocking would be wrong even if it worked* — keeping stdin open after
   =result= serves no purpose since the CLI has already finished

#+begin_src elisp
;; REMOVE this check from maybe-close-stdin:
;; ((and owner-req-id
;;       (claude-agent--has-pending-background-tasks-p owner-req-id))
;;  (claude-agent--debug-log "Background tasks pending..."))
#+end_src

The background task tracker can remain for informational display (mode-line,
session manager) but should NOT block process completion.

** Change 3: Watchdog Timer for Runaway Processes

Add a configurable timeout that kills the process if no =result= message
arrives within the limit:

#+begin_src elisp
(defcustom claude-agent-query-timeout 300
  "Maximum seconds to wait for a query to complete.
Set to nil to disable timeout. Default 300 seconds (5 minutes)."
  :type '(choice (const :tag "No timeout" nil)
                 (integer :tag "Seconds"))
  :group 'claude-agent)

;; In claude-agent--start-process, after creating the process:
(when claude-agent-query-timeout
  (lexical-let ((proc process)
                (req-id req-id))
    (let ((timer (run-at-time claude-agent-query-timeout nil
                              (lambda ()
                                (claude-agent--handle-query-timeout proc req-id)))))
      (setf (claude-agent--process-state-timeout-timer state) timer))))

(defun claude-agent--handle-query-timeout (process request-id)
  "Handle query timeout — kill process, trigger error completion."
  (when (process-live-p process)
    (claude-agent--debug-log "Query timeout after %ds for %s"
                             claude-agent-query-timeout request-id)
    ;; Mark as timed out so sentinel knows
    (let ((state (process-get process 'claude-agent-state)))
      (when state
        (setf (claude-agent--process-state-timed-out state) t)))
    (kill-process process)))
#+end_src

The sentinel should recognize =timed-out= and call =on-complete= with a
timeout error instead of triggering auto-recovery.

*** Timeout cancellation

The timer must be cancelled on normal completion:

#+begin_src elisp
;; In sentinel, before cleanup:
(when-let* ((timer (claude-agent--process-state-timeout-timer state)))
  (cancel-timer timer))
#+end_src

** Change 4: Protocol-Level Completion Signal

In addition to sentinel-based completion, fire a "protocol done" signal when
the =result= message arrives. This enables the org layer to:

1. Stop the spinner immediately (don't wait for process exit)
2. Update exec-status to "completing" (visual feedback)
3. Insert the final telemetry data (duration, cost, token usage)

#+begin_src elisp
;; New hook in claude-agent-backend.org:
(defvar claude-agent-result-received-functions nil
  "Hook called when a result message is received (protocol-level completion).
Each function receives (RESULT-MESSAGE STATE).
This fires BEFORE the process exits and on-complete callback.
Use for immediate visual feedback (stop spinner, update status).")

;; In handle-message for result type:
(run-hook-with-args 'claude-agent-result-received-functions message state)
#+end_src

** Change 5: Multiple Response Handling

*** Key Protocol Facts (from 698 real sessions + 24 fixtures)

1. *Exactly one =result= per CLI invocation*: Zero exceptions found.  Each
   =claude --output-format stream-json= process emits exactly one =result=
   message, at the very end.  Crashed/killed processes emit zero.

2. *Multiple assistant turns ≠ multiple results*: Tool use creates multiple
   assistant→user→assistant cycles, but they all happen WITHIN a single CLI
   invocation, ending with exactly one =result=.

3. *Background agents complete BEFORE =result=*: The CLI waits for all
   background agents internally.  Agent output is streamed to the SDK as
   regular =assistant= tokens before the =result= message.

*** Multi-turn token streaming

When the assistant uses tools and continues, the token callback receives:

1. Tokens from turn 1 (before tool use)
2. [silence during tool execution]
3. Tokens from turn 2 (after tool result)
4. ... repeat for more tool cycles
5. [if background agents launched: wait, then more tokens after completion]
6. Final tokens (=stop_reason="end_turn"=)
7. =result= message

The org layer handles this correctly — tokens stream into the response
section regardless of which turn they come from.  No changes needed.

*** Parallel tool use

The CLI can execute multiple tools in parallel (up to 31 observed in real
sessions).  All tool_result blocks arrive in a single =user= message.  The
SDK handles this correctly — each tool_result triggers PostToolUse hooks.

*** What if the CLI protocol adds multiple =result= in the future?

The current code sets =got-result= on the first =result= and schedules stdin
close.  If a second =result= arrived, =maybe-close-stdin= would fire again
(harmless — EOF is idempotent) and the sentinel would still fire once.  No
defensive code needed, but worth noting for forward compatibility.

** Summary: Completion Model Comparison

*** Current (Two-Phase, Fragile)

| Phase | Trigger | Action | Failure Mode |
|-------+---------+--------+--------------|
| 1: Protocol | =result= received | Set flag, try stdin close | Pending work blocks forever |
| 2: Process | Process exits | Call =on-complete= | Never fires if Phase 1 fails |

*** Proposed (Three-Phase, Robust)

| Phase | Trigger | Action | Failure Guard |
|-------+---------+--------+---------------|
| 1: Protocol | =result= received | Set flag, fire result-hook, schedule stdin close | — |
| 2: Stdin Close | Retry loop (up to 5s) | Close stdin when control requests clear | Force-close after max attempts |
| 3: Process | Process exits (sentinel) | Call =on-complete=, cancel watchdog | Watchdog kills after N seconds |

* Part 5: Implementation Order

1. *Add retry loop to maybe-close-stdin* — fixes the critical hang bug
2. *Remove background task blocking* — the tracker is broken for real sessions
3. *Add watchdog timer* — prevents infinite hangs from any cause
4. *Add result-received hook* — enables immediate visual feedback
5. *Add timeout-timer field + cancellation* — clean lifecycle management
6. *Tests* — mock scenarios for: pending-control-request, timeout, force-close
