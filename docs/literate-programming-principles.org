* Literate Programming Principles

These principles guide how AI agents and developers should work with literate
programming documents (org-mode files with embedded code).

** Intent Before Implementation
Explain /why/ before showing /how/. Prose explains the "why" and drives the
narrative, while code blocks illustrate the "how". Each section should begin
with explanatory prose /before/ any code block.

** Document Structure Follows Narrative Logic
Structure documents for human comprehension, not execution order. Present
concepts in the order best for understanding; let tooling (tangling) handle
mechanical reordering for execution.

** Org Hierarchy Guidelines
Suggested section levels (adapt as needed):
- Level 1 (=*=): Top-level components or modules
- Level 2 (=**=): Major features or logical groupings
- Level 3 (=***=): Specific implementations
- Level 4 (=****=): Helper functions (use sparingly)

** Block Naming Conventions
- Use =#+NAME:= for blocks that will be referenced
- Use kebab-case with domain prefixes: =db-connect=, =api-validate=
- Make names descriptive natural language phrases

** Modification Rules
When modifying literate documents:
- Preserve existing block names (they may have cross-references)
- Update surrounding prose when changing code logic
- Maintain top-to-bottom execution order

** Property Inheritance
- Use property drawers at section level for inherited configuration
- Use =#+PROPERTY= declarations at document level for globals

** One Block = One Meaningful Step
Each code block should perform one meaningful step, like paragraphs in prose.
This makes documents easier to read, understand, and maintain.

** Universal Structural Principles
- Place setup code (imports, configuration) at the top
- Documents should execute correctly top-to-bottom
- Record dependencies explicitly

** Org Files Are the Design Record — Not Chat History
Every design decision, tradeoff, open question, and "why not the other
approach" belongs in the module's `.org` file as prose. The org file is
the *only* durable record of *why* the code looks the way it does.

Chat conversations with AI agents, Slack threads, PR discussions, and
scratch notebooks are ephemeral. If the reasoning lives only there, it
is lost the next time someone asks "why is this a `cl-defstruct` and
not a `plist`?" or "why did we reject the other design?".

Concretely, for each module the `.org` file should carry:

- *Overview* — what this owns and where it fits (already required).
- *Design intent* — why this shape was chosen. A paragraph before any
  code block is usually enough. If two approaches were considered,
  record both and the reason.
- *Rejected alternatives* — one short section per major "why not" that
  would otherwise be rediscovered later. Even one sentence is worth
  keeping.
- *Open questions / TODO* — acceptable in prose, not as bare `TODO`
  comments. Future readers read the prose, not the comments.

When a design conversation happens in an agent chat or a PR review,
the *output of that conversation* must land in the relevant `.org`
file(s) before the branch is merged. If you can't point at the prose
that captures the decision, it didn't happen.

** Self-check Before Committing
For each modified `.org` file, ask:

1. Does the section heading describe a *concept*, not a phase or
   "Functions"/"Helpers"?
2. Does the prose before each code block answer *why* the code is
   shaped this way?
3. If you stripped every code block and read only the prose, would a
   human still understand the module's role?
4. Is each `defun` / `defclass` / `defmethod` accompanied by a
   docstring that's a sentence, not a label?

If any answer is "no", the file is not done — keep writing prose, not
more code.
