* Overview

This document distills actionable improvements for the emacs-cmux system
from a detailed study of the Claude Code CLI source code. The reviewed
documents cover:

- Doc 01: Project panorama -- tech stack, startup chain, module dependencies
- Doc 02: Startup optimization -- 6 strategies for millisecond-level CLI startup
- Doc 03: State management -- 3-layer state architecture bridging React and non-React
- Doc 25: Architecture pattern summary -- 7 reusable design patterns

Each finding maps a Claude Code technique to a concrete opportunity in our
Emacs-based system.

* Findings

** Finding 1: Deferred Module Loading via Autoloads

- *Source*: 01-项目全景.md, section "动态 import 的战略性使用"; 02-启动优化.md, section "快速路径"
- *Claude Code approach*: The entry point =cli.tsx= uses zero static imports
  of business modules. Every sub-command path uses =await import(...)= so
  only the code needed for the selected path is loaded. The =--version= path
  loads literally zero additional modules. The full =main.tsx= import chain
  (~135ms) is only triggered when interactive mode is needed.
- *Our current state*: =claude-code.el= calls =literate-elisp-load= on all
  14 modules unconditionally at require-time. Every =(require 'claude-code)=
  pays the full cost: parsing 14 org files, tangling elisp, and evaluating
  all defuns. A user who only wants =claude-agent-chat= still loads cmux,
  workspace-bridge, scheduled execution, the MCP server, and the IDE server.
- *Opportunity*: Introduce Emacs autoloads for the public entry points.
  Instead of loading everything eagerly, =claude-code.el= should:
  1. Always load the bottom layers (trace, backend, agent) -- these are the
     core SDK needed by all paths.
  2. Use =autoload= declarations for org-mode integration functions
     (=claude-org-mode=, =claude-org-execute=). The autoload triggers
     loading of =claude-org.org= and its sub-modules on first use.
  3. Use =autoload= for =emacs-mcp-server= -- only load when the MCP
     server is actually started.
  4. Use =autoload= for =claude-org-cmux= -- only load when cmux backend
     is needed.
  This mirrors Claude Code's "waterfall fast-path" pattern: pay only for
  what you use. The key insight is that literate-elisp files can be
  autoloaded just like regular elisp -- the autoload cookie triggers
  =literate-elisp-load= instead of =load=.
- *Effort*: M (need autoload-compatible loader, test all entry paths)
- *Impact*: high (startup time reduction for non-org-mode users, reduced
  memory footprint for simple use cases like =claude-agent-chat=)

** Finding 2: Side-Effect Hoisting for I/O During Load

- *Source*: 02-启动优化.md, section "侧效果前置"; 01-项目全景.md, section "main.tsx 的前 20 行"
- *Claude Code approach*: In =main.tsx=, the first 20 lines interleave
  =import= statements with =startMdmRawRead()= and =startKeychainPrefetch()=.
  These fire async subprocesses *before* the remaining ~135ms of module
  imports. By the time the Commander =preAction= hook awaits these results,
  the subprocesses have already finished -- effectively zero additional wait.
  This converts ~65ms of serial macOS Keychain blocking into ~0ms overhead.
- *Our current state*: We do not do any parallel I/O during module loading.
  When =claude-code.el= loads, all 14 modules are parsed and evaluated
  sequentially. Operations like CLI path detection (=claude-agent-cli-path=
  search through multiple paths), Docker readiness checks, and MCP server
  configuration all happen synchronously at first use.
- *Opportunity*: During the load sequence in =claude-code.el=, after loading
  the backend module (which defines =claude-agent-cli-search-paths=), start
  an async process to locate the CLI binary:
  #+begin_example
  ;; Fire CLI detection async while remaining modules load
  (claude-code--load-module "claude-agent-backend")
  (claude-agent--start-cli-detection-async)  ; non-blocking
  ;; Continue loading remaining modules...
  (claude-code--load-module "claude-agent-permission")
  ;; ...
  ;; By the time user executes a query, CLI path is cached
  #+end_example
  Similarly, cmux socket detection (checking =/tmp/cmux-*.sock= files) could
  be started early and awaited lazily. This is the "fire-and-forget then
  await-later" pattern.
- *Effort*: S (small wrapper around =start-process= with a cached result)
- *Impact*: low-medium (CLI detection is fast, but the pattern establishes
  infrastructure for future async optimizations)

** Finding 3: Centralized State Change Notifications via onChange

- *Source*: 03-状态管理.md, section "onChangeAppState"; 25-架构模式总结.md, pattern 2
- *Claude Code approach*: The 35-line Store accepts an =onChange= callback at
  creation time. Every =setState= call triggers this callback with both old
  and new state, enabling centralized side-effect processing: persisting model
  choice to settings.json, notifying external systems of permission mode
  changes, clearing credential caches. The code comment notes that previously
  "mode changes were relayed to CCR by only 2 of 8+ mutation paths" -- the
  centralized =onChange= eliminated this class of bugs entirely.
- *Our current state*: Session state changes go through =claude-org--session-put=,
  which is a direct setter on the session-state struct. There is no notification
  mechanism. Side effects (mode-line updates, spinner timer management,
  org property persistence) are manually triggered at each call site. For
  example, when =:busy= changes to =t=, the caller must also remember to
  start the spinner timer and update the mode-line. When =:busy= changes to
  =nil=, the caller must stop the spinner and persist timing data to org
  properties. These are scattered across claude-org.org, claude-org-response.org,
  and claude-org-cmux.org.
- *Opportunity*: Add an optional watch/notification layer to
  =claude-org--session-put=. When certain fields change, automatically
  trigger registered side effects:
  - =:busy= t -> nil: stop spinner timer, update mode-line, record elapsed time
  - =:busy= nil -> t: start spinner timer, update mode-line
  - =:marker= changes: validate the new marker
  - =:recovering= changes: update mode-line indicator
  This could be implemented as a simple alist of =(field . hook-list)= pairs
  checked in =claude-org--session-state-set=. The pattern eliminates the class
  of bugs where a new code path changes =:busy= but forgets to update the
  mode-line. This directly maps to Claude Code's insight: "any setState call
  导致的变更都会被集中处理，零遗漏."
- *Effort*: M (add notification dispatch to session-put, migrate existing
  scattered side effects)
- *Impact*: high (eliminates a proven class of state-sync bugs, reduces code
  duplication across modules)

** Finding 4: Three-Layer State Architecture

- *Source*: 03-状态管理.md, sections on bootstrap/state.ts, AppState Store,
  and ToolUseContext; 25-架构模式总结.md, pattern 2
- *Claude Code approach*: State is organized in 3 layers with strict
  dependency direction (lower layers never import higher layers):
  1. *Bootstrap/state* (process-level): session ID, CWD, cost counters --
     module-level singleton with getter/setter, zero dependencies, DAG leaf node
  2. *AppState Store* (REPL-level): UI state, permissions, MCP, plugins --
     35-line reactive Store with subscribe/notify, DeepImmutable wrapper
  3. *ToolUseContext* (per-interaction): runtime context for tool execution --
     references AppState getter/setter, not the Store itself
  The bootstrap layer is explicitly documented with "DO NOT ADD MORE STATE
  HERE - BE JUDICIOUS WITH GLOBAL STATE" and "THINK THRICE BEFORE MODIFYING".
- *Our current state*: We have 2 layers:
  1. *Emacs customization variables* (defcustom/defvar): CLI path, debug flag,
     recovery settings -- global, set once
  2. *Session hash table* (buffer-local): All per-session state in
     =claude-org--sessions= keyed by session-key, with typed sub-structs
     (lifecycle, render, loop, identity) plus an =extras= plist for overflow
  We lack a middle layer equivalent to AppState -- things like "which backend
  is the current buffer using", "what is the current permission mode", and
  "what MCP connections are active" are either computed on-the-fly or stored
  inconsistently across buffer-locals and global vars.
- *Opportunity*: Formalize a buffer-level "workspace state" layer between
  global customizations and per-session state:
  - Buffer-local struct holding: active backend type, cmux workspace ID,
    permission mode, MCP server status, bridge process status
  - This workspace state is set once when =claude-org-mode= activates and
    read by all sessions in the buffer
  - Sessions reference workspace state through their =:backend= field but
    never own it (prevents the current pattern of each session independently
    discovering the backend)
  This mirrors the Claude Code pattern where bootstrap/state is the "safe to
  import from anywhere" leaf, AppState is the "shared UI context", and
  ToolUseContext is the per-execution slice.
- *Effort*: L (new struct, migrate scattered buffer-locals, update all
  session creation paths)
- *Impact*: medium (cleaner separation, prevents redundant backend detection,
  but current system works)

** Finding 5: DAG-Leaf State Module for Safe Cross-Module Access

- *Source*: 03-状态管理.md, section "为什么不用 Store" and DAG constraints;
  25-架构模式总结.md, pattern 2
- *Claude Code approach*: =bootstrap/state.ts= is deliberately kept at the
  bottom of the import dependency graph. It imports almost nothing, so any
  module can safely import it without risk of circular dependencies. The
  comments explicitly state: "bootstrap can't import listeners directly
  (DAG leaf), so callers register themselves." This makes the most fundamental
  state (session ID, CWD, cost) universally accessible.
- *Our current state*: Our module load order is carefully documented in
  ARCHITECTURE.org and enforced by =claude-code.el=. The bottom layer is
  =claude-agent-trace.org= (zero deps) and =claude-agent-backend.org=
  (depends only on cl-lib, json, subr-x). However, =claude-agent-backend.org=
  is large (~200+ headings) and mixes pure data definitions (options, structs)
  with process management code that has more dependencies. Session state
  (=claude-org--sessions=) lives in =claude-org-session.org= at position 5
  in the load order, meaning modules 0-4 cannot access session state.
- *Opportunity*: Extract a thin "definitions-only" module from
  =claude-agent-backend.org= containing only: data struct definitions
  (options plist, backend struct), error conditions, and customization
  variables. This module would have zero functional dependencies and serve
  as the DAG leaf -- loadable by any module including trace and permission.
  The current =claude-agent-backend.org= is already the heaviest module; this
  decomposition would make it clearer which parts are safe to import from
  anywhere. This is analogous to splitting Claude Code's
  =bootstrap/state.ts= from the rest of the application logic.
- *Effort*: M (extract definitions into a new org module, update load order)
- *Impact*: medium (better module hygiene, prevents future circular deps as
  system grows)

** Finding 6: Immutable State with Functional Updates

- *Source*: 03-状态管理.md, section on AppState DeepImmutable wrapper and
  setState updater pattern; 25-架构模式总结.md, pattern 2
- *Claude Code approach*: All AppState is wrapped in =DeepImmutable<T>=,
  making every property recursively =readonly=. Updates go through
  =setState(updater: (prev: T) => T)= -- a function that receives the
  previous state and returns a new state. This prevents stale-snapshot bugs
  in async code: each updater always sees the latest state. Additionally,
  =Object.is= equality checking skips notifications when the state has not
  actually changed.
- *Our current state*: Session state is mutable. =claude-org--session-put=
  directly mutates struct fields via =setf=. There is no protection against
  concurrent modifications from process filters and timers that run
  interleaved with normal code. While Emacs is single-threaded, process
  filters can fire between any two elisp forms when the event loop yields
  (e.g., during =accept-process-output= or =sit-for=). A filter that sets
  =:busy nil= while the main code assumes =:busy t= can cause subtle bugs.
- *Opportunity*: For critical session fields (=:busy=, =:recovering=,
  =:marker=), introduce a "compare-and-swap" style accessor that checks
  the expected current value before setting:
  #+begin_example
  (claude-org--session-cas session-key :busy t nil)
  ;; Returns t and sets :busy to nil only if current value is t
  ;; Returns nil and does nothing if :busy is already nil
  #+end_example
  This is lighter than full immutability (which does not map well to Emacs
  Lisp) but captures the key benefit: preventing stale-state mutations in
  process filters and timer callbacks. Claude Code's =Object.is= check is
  the same idea -- skip the update if nothing actually changed.
- *Effort*: S (a small wrapper function, update a few critical call sites)
- *Impact*: medium (prevents a known class of race conditions in process
  filter / timer interactions)

** Finding 7: Startup Profiling Infrastructure

- *Source*: 02-启动优化.md, section "启动性能度量 profileCheckpoint()";
  25-架构模式总结.md (referenced as supporting infra for pattern 1)
- *Claude Code approach*: =profileCheckpoint(name)= records timestamps at
  key points in the startup sequence. It has dual modes: (1) detailed local
  profiling via =CLAUDE_CODE_PROFILE_STARTUP=1= env var, and (2) sampled
  telemetry (0.5% of external users) reporting to Statsig. Phase definitions
  like =import_time=, =init_time=, =total_time= track the metrics the team
  cares about. For unsampled users, the function returns immediately (zero
  overhead after JIT).
- *Our current state*: We have no startup profiling. We do not know how long
  =literate-elisp-load= takes per module, or what the total =(require
  'claude-code)= cost is. When users report "Emacs hangs on startup with
  claude-code", we have no data to diagnose which module is slow.
- *Opportunity*: Add lightweight load-time instrumentation:
  #+begin_example
  (defvar claude-code--load-profile nil
    "When non-nil, record module load times.")

  (defun claude-code--load-module (name)
    "Load Claude Code module NAME from org file."
    (let* ((file (expand-file-name (concat name ".org") claude-code-directory))
           (start (when claude-code--load-profile (float-time))))
      (literate-elisp-load file)
      (when start
        (push (cons name (- (float-time) start))
              claude-code--load-profile))))
  #+end_example
  Enable with =(setq claude-code--load-profile t)= before =(require
  'claude-code)=. After loading, =claude-code--load-profile= contains a
  list of =(module-name . seconds)= pairs for diagnosis. This is the Emacs
  equivalent of Claude Code's =profileCheckpoint()=, scoped to our concern
  (org file parse/eval time).
- *Effort*: S (a few lines in claude-code.el)
- *Impact*: medium (essential for diagnosing startup regressions, enables
  data-driven optimization decisions)

** Finding 8: Memoized Initialization Functions

- *Source*: 02-启动优化.md, section "memoize 防重复初始化";
  01-项目全景.md, section on init.ts memoize wrapper
- *Claude Code approach*: The =init()= function is wrapped with lodash
  =memoize=, ensuring it executes only once regardless of how many code paths
  call it. This is important because in a complex startup with multiple entry
  points (Commander preAction, subcommand handlers, error recovery paths),
  each path may need to "ensure initialization" without tracking whether it
  already happened. The memoized function returns the same Promise, so
  concurrent callers share the same initialization work.
- *Our current state*: Several initialization paths in our system do ad-hoc
  "already done?" checks. For example, the session hash table uses
  =(unless (local-variable-p 'claude-org--sessions) ...)=, CLI path detection
  caches the result in =claude-agent-cli-path=, and the MCP server checks a
  running flag. Each module invents its own memoization pattern.
- *Opportunity*: Create a =claude-code--defonce= macro (analogous to Clojure's
  =defonce= or lodash =memoize=) that wraps a function to execute only once
  and cache the result:
  #+begin_example
  (defmacro claude-code--defonce (name arglist &rest body)
    "Define NAME as a function that runs BODY only once, caching the result."
    (let ((cache-var (intern (format "%s--cache" name))))
      `(progn
         (defvar ,cache-var :unset)
         (defun ,name ,arglist
           (when (eq ,cache-var :unset)
             (setq ,cache-var (progn ,@body)))
           ,cache-var))))
  #+end_example
  Use for: CLI path detection, cmux socket detection, Docker readiness,
  MCP server initialization. This standardizes the pattern and makes
  the "only once" guarantee explicit in the API.
- *Effort*: S (small macro, refactor a few existing patterns)
- *Impact*: low (reduces boilerplate, makes intent clearer, but existing
  ad-hoc checks work correctly)

** Finding 9: Agent Isolation via Context Clone

- *Source*: 03-状态管理.md, section "createSubagentContext";
  25-架构模式总结.md, pattern 6
- *Claude Code approach*: When a parent agent spawns a child agent,
  =createSubagentContext()= creates a copy of the execution context with
  "default full isolation + explicit opt-in sharing":
  - =readFileState=: cloned (prevents cache pollution)
  - =abortController=: new child linked to parent (parent abort propagates)
  - =setAppState=: default no-op (child cannot affect parent's UI)
  - =setAppStateForTasks=: always pierces through to root Store (task
    registration must reach root to prevent zombie processes)
  The key insight is that infrastructure-level operations (process cleanup)
  must always reach the root, even when application-level state is isolated.
- *Our current state*: Each AI block execution in a buffer shares the same
  session hash table (=claude-org--sessions=). The queuing system
  (=claude-org-queue.org=) serializes block execution within a session.
  There is no concept of isolated sub-contexts. When one block's process
  filter modifies session state, all code referencing that session sees the
  change immediately. For the cmux backend, workspaces provide some isolation
  (each workspace has its own tab), but the Emacs-side session state is
  shared.
- *Opportunity*: As we add more concurrent execution patterns (scheduled
  blocks, loop iterations, multi-workspace orchestration), consider the
  Claude Code isolation model. Specifically:
  - When a scheduled block runs, it should get a snapshot of the session
    state, not share the live state with interactive blocks
  - When loop iterations overlap (fast interval), each iteration should
    have its own render state (marker, spinner) while sharing identity state
  - Process cleanup (sentinel functions) should always reach the session
    registry regardless of isolation level
  This is not urgent today because our execution is largely serial, but it
  is the right pattern to adopt before adding concurrency.
- *Effort*: L (design context isolation model, refactor session creation)
- *Impact*: low now, high later (prevents state corruption when concurrency
  is added)

** Finding 10: Single-Source Tool/Module Registry with Layered Filtering

- *Source*: 25-架构模式总结.md, pattern 3 "工具注册表"; 01-项目全景.md,
  section on tools.ts
- *Claude Code approach*: All tools register through a single
  =getAllBaseTools()= function. This is the *only* registration point. On top
  of it, 3 layers of filtering are applied: (1) compile-time DCE via
  =feature()=, (2) load-time env var checks, (3) runtime =isEnabled()=
  checks. Then =assembleToolPool()= merges built-in tools with MCP tools,
  sorted by name for prompt cache stability. The =buildTool()= builder
  provides safe defaults (not concurrency-safe, not read-only) that new
  tools inherit automatically.
- *Our current state*: Backend registration happens through =cl-defgeneric=
  and =cl-defmethod= dispatch in =claude-agent-backend.org=. MCP tool
  registration uses =emacs-mcp-server-register-tool= from individual modules.
  There is no single listing of all registered backends or all available MCP
  tools. To understand "what tools does the system offer?", you must grep
  across all org files for =register-tool= calls.
- *Opportunity*: Create a =claude-code--registry= pattern:
  - A central defvar listing all known modules with their metadata
    (name, load-file, optional predicate, category)
  - At load time, iterate the registry, check predicates, load modules
    that are enabled
  - For MCP tools, gather registrations through the registry rather than
    scattered =register-tool= calls
  This makes it easy to answer "what does this system contain?" by reading
  one data structure, and to add/remove modules by editing one list.
  The ARCHITECTURE.org load order table already serves as documentation for
  this -- the opportunity is to make it executable.
- *Effort*: M (create registry data structure, refactor load sequence)
- *Impact*: medium (better discoverability, enables conditional loading,
  simplifies adding new modules)

** Finding 11: Conservative Defaults in Builder Patterns

- *Source*: 25-架构模式总结.md, pattern 3, section "Builder 模式：安全默认值"
- *Claude Code approach*: =buildTool()= applies =TOOL_DEFAULTS= that are
  deliberately conservative: =isConcurrencySafe= defaults to =false= (new
  tools execute serially unless they opt in), =isReadOnly= defaults to
  =false= (new tools are assumed to have side effects). This "safe by
  default, opt-in to power" philosophy means a hastily written tool cannot
  accidentally bypass safety measures.
- *Our current state*: The backend protocol (=cl-defgeneric=) requires each
  backend to implement all methods. There are no defaults for safety-relevant
  properties. When adding a new backend, the author must remember to implement
  permission checks, process cleanup, error handling in sentinels, etc. The
  ARCHITECTURE.org invariants list ("process filters/sentinels wrapped in
  condition-case") documents these requirements, and the structural test
  suite (=test-structural.el=) catches some violations, but there is no
  default-providing builder.
- *Opportunity*: Create a backend builder or mixin that provides safe defaults:
  - Default sentinel wraps cleanup in =condition-case=
  - Default filter validates JSON before dispatch
  - Default error callback logs and resets session state
  New backends need only override the methods specific to their protocol.
  This reduces the "things you must remember" burden documented in
  ARCHITECTURE.org from a checklist to a single builder call.
- *Effort*: S-M (define a base backend with default methods, refactor
  existing backends to inherit)
- *Impact*: medium (prevents defect class where new backends miss safety
  requirements)

** Finding 12: Prompt Segment Caching with Cache-Break Awareness

- *Source*: 25-架构模式总结.md, pattern 4 "Prompt 分段缓存"
- *Claude Code approach*: System prompt sections are registered via two APIs:
  =systemPromptSection(name, compute)= for sections that are computed once
  per session and cached until =/clear= or =/compact=, and
  =DANGEROUS_uncachedSystemPromptSection(name, compute, reason)= for sections
  that must be recomputed every turn. The =DANGEROUS_= prefix is itself a
  design decision -- it makes developers think twice before creating a
  cache-breaking section. The =reason= parameter (unused at runtime) forces
  documentation of why the cache break is necessary.
- *Our current state*: System prompts are constructed in the workspace bridge
  Python layer and in Emacs-side options construction. There is no structured
  distinction between "stable per session" and "changes per turn" prompt
  segments. When we construct options for =claude-agent-query=, the system
  prompt is built fresh each time.
- *Opportunity*: When constructing system prompts for Claude Code via the
  workspace bridge or direct SDK calls, separate the prompt into:
  1. *Static segments*: tool descriptions, behavioral rules, CLAUDE.md content
     -- computed once when the session starts
  2. *Session-cached segments*: project context, file tree summary --
     computed once per session, invalidated on =/clear=
  3. *Per-turn segments*: current buffer state, cursor position -- always fresh
  Cache the first two categories in the session state struct. The naming
  convention (=DANGEROUS_uncached=) is worth adopting even in Emacs Lisp
  as a documentation pattern for functions that have performance implications.
- *Effort*: M (restructure prompt assembly, add caching to session state)
- *Impact*: medium (reduces redundant computation, aligns with Anthropic's
  prompt caching for cost reduction)

* Key Architectural Lessons

** Lesson 1: State Layering Prevents Dependency Tangles

Claude Code's 3-layer state architecture (bootstrap -> AppState -> ToolUseContext)
enforces a strict "downward dependency" rule. The bottom layer has zero
dependencies and can be imported by anyone. This prevents the circular
dependency problem that plagues growing codebases.

Our system should adopt this discipline: define a clear "leaf layer" of pure
data definitions that any module can import, a "workspace layer" of buffer-
scoped state, and a "session layer" of per-execution state.

** Lesson 2: Centralized Side Effects Beat Scattered Notifications

The =onChange= callback on the Store is arguably the most impactful pattern
in the entire Claude Code state system. It replaced 8+ scattered notification
paths with 1 centralized handler, eliminating an entire class of "forgot to
notify external system" bugs.

Our equivalent is session state side effects (mode-line, spinner, properties).
The migration path is clear: add a dispatch table to =claude-org--session-put=.

** Lesson 3: Measure Before Optimizing

Claude Code's =profileCheckpoint()= infrastructure is tiny (a few dozen lines)
but provides the data needed to make informed optimization decisions. Without
it, startup optimization would be guesswork.

We should add load-time profiling before attempting any of the startup
optimizations (Finding 1, Finding 2).

** Lesson 4: Module Decomposition is Load-Order Driven

Both Claude Code and our system face the same challenge: a monolithic entry
point that must load modules in dependency order. Claude Code's solution
(dynamic import) works because JavaScript supports async module loading.
Emacs Lisp's solution is autoloads, which achieve the same effect: defer
loading until first use, controlled by declarations in the entry point.

The key insight from Claude Code is that the entry point file should be
*tiny* -- just enough to set up fast paths and declare autoloads. All
substance lives in lazily-loaded modules.
