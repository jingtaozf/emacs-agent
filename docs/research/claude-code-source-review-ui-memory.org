* Findings

** Finding 1: Semantic Face System (No Custom Faces Defined)

- *Source*: 22-设计系统.md, Section 1 (Theme System, 80+ Semantic Tokens)
- *Claude Code approach*: Defines a ~Theme~ type with 80+ semantic color
  tokens (~success~, ~error~, ~permission~, ~diffAdded~, etc.) separated from
  raw color values. Uses "screaming" names (~red_FOR_SUBAGENTS_ONLY~) to
  constrain usage at the type level. Six themes span dark/light, daltonized
  (color-blind friendly), and ANSI-only fallbacks.
- *Our current state*: The header-line and response rendering use raw
  ~font-lock-*-face~ faces throughout (~font-lock-constant-face~,
  ~font-lock-type-face~, ~font-lock-warning-face~, ~font-lock-keyword-face~,
  ~font-lock-string-face~, ~font-lock-comment-face~). No ~defface~ declarations
  exist anywhere in the codebase. This means: (a) colors depend on the user's
  theme for font-lock faces, which may produce poor contrast; (b) there is no
  way for users to customize Claude-specific colors without affecting all of
  Emacs; (c) semantic intent is lost -- ~font-lock-warning-face~ for permission
  mode badge does not communicate "permission" to a reader of the code.
- *Opportunity*: Define a set of ~defface~ declarations in a new ~claude-org-faces~
  section: ~claude-org-face-session-section~, ~claude-org-face-session-file~,
  ~claude-org-face-permission~, ~claude-org-face-activity~,
  ~claude-org-face-project~, ~claude-org-face-ide-context~,
  ~claude-org-face-workspace~, ~claude-org-face-story~,
  ~claude-org-face-success~, ~claude-org-face-error~. Each face inherits from
  a reasonable font-lock face by default but can be customized independently.
  This also enables future theme packages (e.g., a high-contrast or
  daltonized theme for claude-org).
- *Effort*: S
- *Impact*: medium -- improves code clarity, enables user customization,
  and lays groundwork for accessibility.

** Finding 2: Debounced Rendering with Frame Throttling

- *Source*: 21-Ink框架深度定制.md, Section 4.1 (Double Buffering + Frame Throttle)
- *Claude Code approach*: Maintains front/back frame buffers with ~throttle~
  at ~16ms (60fps). Uses ~queueMicrotask~ to delay rendering past layout
  effects. The ~charCache~ caches tokenize + grapheme clustering results
  so unchanged lines skip re-computation. Blit optimization copies
  unchanged screen regions as TypedArray blocks rather than re-rendering.
- *Our current state*: We have ~claude-org-fontlock-delay~ (0.05s) that
  debounces ~font-lock-ensure~ after token insertion. The header-line
  refreshes on a 0.2s timer (200ms). Cursor-position header updates also
  debounce at 0.2s. These are reasonable but ad-hoc -- the font-lock delay
  and header timer are independent mechanisms with different cadences.
- *Opportunity*: (1) Consider batching token insertion and font-lock into a
  single "render frame" mechanism -- accumulate tokens during streaming and
  flush once per frame interval, rather than calling ~font-lock-ensure~ per
  token batch. (2) The header-line 200ms timer is reasonable but could be
  made adaptive -- run faster (100ms) when sessions are active, slower
  (500ms) or off when idle. The current timer runs even when nothing changes.
  (3) The ~Ratchet~ pattern (monotonically increasing height) could translate
  to preventing org-section height oscillation during streaming by deferring
  fold/visibility changes until streaming completes.
- *Effort*: M
- *Impact*: medium -- reduces CPU cost during long streaming sessions,
  smoother visual experience.

** Finding 3: Five-Layer Memory Architecture vs. Our Two Layers

- *Source*: 23-Memory系统.md, Full document (Layers 1-5)
- *Claude Code approach*: Five distinct memory layers:
  1. CLAUDE.md -- static human-authored instructions, hierarchical discovery
     from CWD upward, ~@include~ directive support, loaded once per session
  2. Auto Memory (memdir) -- AI-generated topic files under
     ~~/.claude/projects/<slug>/memory/~, four-type taxonomy
     (user/feedback/project/reference), MEMORY.md index (200 lines max),
     background extraction agent with main-agent mutual exclusion
  3. Session Memory -- structured 10-section template (~summary.md~),
     dual-threshold trigger (10K tokens init, 5K growth + 3 tool calls),
     used as compact summary to avoid extra API calls
  4. Agent Memory -- per-agent persistent knowledge in three scopes
     (user/project/local)
  5. Relevant Memories -- async prefetch via side-query (Sonnet) selecting
     top-5 relevant files per user turn, injected as Attachment, session-level
     deduplication, pre-computed freshness labels for cache stability
- *Our current state*: We have exactly two layers:
  1. CLAUDE.md -- loaded by Claude Code CLI, we pass it through
  2. Session state in org properties (CLAUDE_SESSION_ID, CLAUDE_CLI_SESSION,
     backend type) -- purely mechanical session tracking, no knowledge
     accumulation
  There is no auto-memory (learning from corrections), no session summary
  (compact resilience), no per-workspace knowledge accumulation, no
  relevant-memory retrieval.
- *Opportunity*: The biggest gap. Three concrete steps, in priority order:
  (a) *Session Summary*: After each AI block execution, auto-append a
  condensed summary to an org property or a sibling section under the
  workspace heading. When context compaction happens, this summary is
  available without extra API calls. This maps to Claude Code's Session
  Memory layer. Effort: M.
  (b) *Workspace Knowledge Accumulation*: Store learned corrections and
  preferences as org sections (e.g., a ~:LEARNINGS:~ drawer under each
  workspace heading). When Claude corrects a mistake and the user confirms,
  auto-append the lesson. This maps to the ~feedback~ type in Auto Memory.
  Effort: M.
  (c) *Relevant Memory Injection*: Before sending a query, scan workspace
  learnings and recent session summaries, select relevant ones, and inject
  them as context. This maps to Relevant Memories but can be simpler --
  org-mode's property inheritance and tag filtering can replace the
  side-query selection. Effort: L.
- *Effort*: L (overall, phased)
- *Impact*: high -- directly improves AI accuracy over time within a project.

** Finding 4: Background Memory Extraction Pattern

- *Source*: 23-Memory系统.md, Section 3 (Background Extract Memories)
- *Claude Code approach*: A fire-and-forget background agent runs after each
  conversation turn, extracts memories from the dialogue using a forked
  agent with strict permission sandbox (read-only except for memdir writes).
  Uses closure-scoped state with mutual exclusion (if main agent already
  wrote memories, extraction skips and advances cursor). Pending requests
  are merged -- only the latest context is kept, not a queue.
- *Our current state*: No background extraction. When the user types
  corrections ("no, use X instead of Y"), the correction is in the org
  buffer but never systematically captured for future sessions.
- *Opportunity*: After an AI block completes, scan the response and the
  preceding user message for correction patterns (negation + instruction).
  Append to a ~:FEEDBACK:~ drawer under the workspace heading. This could
  be done with a simple regexp scan in Emacs Lisp (no API call needed) for
  the most common patterns ("don't", "instead use", "actually", "please
  remember"). More sophisticated extraction could use a lightweight API
  call as a post-execution hook.
- *Effort*: M
- *Impact*: medium -- prevents repeated mistakes within a workspace.

** Finding 5: Skill Directory Structure (SKILL.md Not Discovered)

- *Source*: 24-Skill-Plugin开发实战.md, Section 1 (Skill Discovery)
- *Claude Code approach*: Skills live in ~.claude/skills/<name>/SKILL.md~
  with YAML frontmatter (name, description, allowed-tools, when_to_use,
  model, effort, context: fork/inline, paths for conditional activation).
  Discovery scans five sources: managed policy, user-level, project-level
  (CWD upward traversal), add-dir, and legacy commands. Dynamic discovery
  activates skills when files matching ~paths~ globs are touched.
- *Our current state*: We discover slash commands from three sources:
  (1) built-in list of 8 commands, (2) ~.claude/commands/*.md~ files
  (user + project), (3) plugin commands from ~~/.claude/plugins/~.
  We do NOT discover ~.claude/skills/~ directories at all -- the new
  Skill format with ~SKILL.md~ is completely missing. We also don't read
  frontmatter from skill files, so we cannot show descriptions,
  ~when_to_use~ hints, or argument hints in the company-mode completion.
- *Opportunity*: Extend ~claude-org--discover-slash-commands~ to also scan
  ~.claude/skills/~ directories (user and project level). For each
  ~<name>/SKILL.md~ found, register ~/name~ as a slash command. Parse
  YAML frontmatter to extract ~description~ and ~argument-hint~ for richer
  company-mode annotations (use ~company-doc-buffer~ or annotation).
  This brings our completion into parity with Claude Code's skill discovery.
- *Effort*: S
- *Impact*: high -- users who define skills via the new format get zero
  completion support today; this unblocks skill-based workflows.

** Finding 6: Conditional Skill Activation by File Path

- *Source*: 24-Skill-Plugin开发实战.md, Section 1.5 (paths filtering)
- *Claude Code approach*: Skills with ~paths: "**/*.proto"~ frontmatter
  are registered but dormant. They activate only when the model operates
  on files matching the glob. ~activateConditionalSkillsForPaths()~ uses
  gitignore-style matching. Monorepo sub-packages can have their own
  ~.claude/skills/~ discovered dynamically.
- *Our current state*: All slash commands are always available. There is
  no concept of conditional activation based on file context.
- *Opportunity*: Not urgent for emacs-cmux since the activation happens
  inside the Claude Code CLI, not in our completion layer. However, we
  could surface path-conditional skills differently in company-mode
  (e.g., dimmed annotation "[conditional]") to set user expectations.
- *Effort*: S
- *Impact*: low -- informational only in our UI layer.

** Finding 7: Skill Execution Modes (Inline vs Fork)

- *Source*: 24-Skill-Plugin开发实战.md, Section 1.3 (Inline vs Fork)
- *Claude Code approach*: ~context: fork~ creates a sub-agent with
  independent token budget via ~runAgent()~. Default inline mode injects
  skill content as a user message in the current conversation. Fork mode
  is recommended for complex multi-tool-call tasks to avoid polluting the
  main conversation context.
- *Our current state*: We pass slash commands as-is to the Claude Code CLI.
  The CLI handles execution mode internally. Our UI does not distinguish
  between inline and fork skills -- both look the same in the AI block.
- *Opportunity*: When a fork-mode skill is executing, the header-line could
  show a sub-agent indicator (e.g., "[agent: review]") since fork mode
  runs independently. This would require parsing the stream-json events
  for sub-agent creation/completion. Claude Code's stream-json already
  emits ~subagent~ events that we could listen for.
- *Effort*: M
- *Impact*: medium -- gives users visibility into what is running.

** Finding 8: Agent Definition Files (.claude/agents/)

- *Source*: 24-Skill-Plugin开发实战.md, Section 2 (Custom Agents)
- *Claude Code approach*: Agent definitions in ~.claude/agents/<name>.md~
  with rich frontmatter: tools whitelist/blacklist, model override,
  maxTurns, color for visual distinction, background mode, memory scope,
  worktree isolation, MCP server declarations, skill injection, and
  initialPrompt. Agents have persistent memory (three scopes) and
  six-level override priority.
- *Our current state*: We do not discover or surface ~.claude/agents/~
  definitions at all. Agent invocation happens through the CLI's ~/agent~
  slash command or the ~AgentTool~, but we have no completion or
  visualization for it.
- *Opportunity*: Add ~/agent~ to ~claude-org-builtin-slash-commands~ and
  provide company-mode completion for agent names by scanning
  ~.claude/agents/*.md~. Show the agent ~color~ in the header-line or
  response section when a sub-agent is running.
- *Effort*: S
- *Impact*: medium -- enables agent-aware workflows in the org UI.

** Finding 9: Prompt-Code Coordination for Memory Directories

- *Source*: 23-Memory系统.md, Section 2.5 (DIR_EXISTS_GUIDANCE)
- *Claude Code approach*: The memory system ensures the directory exists
  via ~ensureMemoryDirExists()~ in code, then tells the AI "this directory
  already exists -- write directly" in the prompt. This saves 1-2 tool
  calls per memory write. The pattern: code guarantees the precondition,
  prompt informs the AI the precondition holds.
- *Our current state*: Our system prompts (in ~prompts/system/~) do not
  include this kind of precondition-assertion pattern. When AI needs to
  create files or directories as part of a workflow, it typically checks
  first.
- *Opportunity*: In our system prompts, assert directory states that we
  guarantee in code. For example, if we create a project's output
  directory before execution, we can add to the system prompt:
  "The project directory and output paths already exist. Write directly
  without checking." This is a general pattern applicable to any
  frequently-used path in SDD workflows.
- *Effort*: S
- *Impact*: low-medium -- saves tool calls in repetitive workflows.

** Finding 10: Session Memory as Compact Substitute

- *Source*: 23-Memory系统.md, Section 4 (Session Memory)
- *Claude Code approach*: Session Memory uses a fixed 10-section template
  (Current State, Task Specification, Files and Functions, Workflow,
  Errors and Corrections, etc.). It is incrementally maintained by a
  background forked agent. The key value: when auto-compact triggers,
  Session Memory is used as the compact summary -- avoiding an extra API
  call to re-summarize the conversation. Each section is capped at 2000
  tokens, total at 12000.
- *Our current state*: We have no structured session summary. When a
  Claude Code session is resumed (~--resume~), the CLI's internal compact
  handles context reduction. We have no influence over what gets preserved.
- *Opportunity*: Maintain a structured summary as an org drawer or subtree
  under the workspace heading. After each AI block execution, update a
  ~:SESSION_SUMMARY:~ property or a dedicated org section with the current
  task state, key files, and recent errors. When starting a new session
  in the same workspace, inject this summary as preamble context. This
  gives us compact resilience independent of the CLI's internal mechanism.
  The 10-section template from Claude Code is a good starting point but
  can be simplified for our use case (5-6 sections covering: current state,
  task, key files, errors, learnings).
- *Effort*: M
- *Impact*: high -- directly improves session continuity after context
  compaction or session restart.

** Finding 11: Memory Taxonomy and "What NOT to Save"

- *Source*: 23-Memory系统.md, Section 2.2 (Four-Type Taxonomy)
- *Claude Code approach*: Four strict memory types: user (role/preferences),
  feedback (corrections + confirmations), project (decisions/background),
  reference (external system pointers). Critically, defines "what NOT to
  save": code patterns (derivable from codebase), git history (derivable
  from ~git log~), debug solutions (transient), CLAUDE.md content (already
  loaded), temporary task state. Even when the user asks to save something,
  the AI is instructed to ask "what was surprising or non-obvious about it?"
- *Our current state*: We have no memory taxonomy. The ~CLAUDE.md~ and
  ~.claude/rules/~ files serve as static instructions. The
  ~tasks/lessons.md~ file (per project instruction) captures some feedback
  manually, but there is no structured classification or exclusion rules.
- *Opportunity*: If we implement workspace-level knowledge accumulation
  (Finding 3b), adopt the taxonomy: separate ~:USER_PREFS:~,
  ~:FEEDBACK:~, ~:PROJECT_CONTEXT:~, and ~:REFERENCES:~ drawers. More
  importantly, encode "what not to save" in the prompt template that
  guides automatic extraction -- exclude anything derivable from the
  current codebase or git history.
- *Effort*: S (design), M (implementation)
- *Impact*: medium -- prevents memory bloat, keeps accumulated knowledge
  high-signal.

** Finding 12: Relevant Memory Retrieval with Freshness

- *Source*: 23-Memory系统.md, Section 6 (Relevant Memories)
- *Claude Code approach*: Two-phase retrieval: (1) scan memory files,
  read first 30 lines of frontmatter, sort by mtime descending, cap at
  200; (2) side-query with Sonnet to select top-5 relevant files.
  Pre-compute freshness labels ("today", "yesterday", "3 days ago") to
  maintain prompt cache stability. Session-level deduplication prevents
  re-injecting the same memory. After compact, deduplication resets so
  important memories can be re-injected.
- *Our current state*: No relevant memory retrieval. Each AI block
  execution starts with whatever context the CLI provides plus our
  system prompts.
- *Opportunity*: A lightweight version using org-mode's native
  capabilities: before sending a query, search for ~:FEEDBACK:~ and
  ~:LEARNINGS:~ drawers in the current workspace subtree, extract entries
  modified within the last 7 days (using file-level mtime or an org
  timestamp property), and inject as context. No side-query needed --
  org's property search is fast enough for 50-100 entries. The freshness
  label pattern (pre-compute and cache) is directly applicable.
- *Effort*: M
- *Impact*: medium -- enables learning from past corrections without
  manual context management.

** Finding 13: Plugin Variable Substitution Pattern

- *Source*: 24-Skill-Plugin开发实战.md, Section 1.4 (Variable Substitution)
- *Claude Code approach*: Skill content supports ~$1~, ~${CLAUDE_SKILL_DIR}~,
  ~${CLAUDE_SESSION_ID}~, and named arguments. Shell command embedding
  via ~!`command`~ syntax executes at skill load time. MCP-sourced skills
  skip shell execution for security.
- *Our current state*: We pass slash command names to the CLI verbatim.
  We do not perform any variable substitution or shell embedding in our
  layer. The CLI handles all of this internally.
- *Opportunity*: Not needed in our layer -- the CLI handles substitution.
  However, for our own prompt templates (in ~prompts/~), we could adopt
  a similar variable substitution pattern. Currently our prompts use
  Emacs Lisp ~format~ calls scattered in code. A centralized
  ~claude-org--substitute-prompt-vars~ function that replaces
  ~${PROJECT_ROOT}~, ~${WORKSPACE_NAME}~, ~${SESSION_ID}~ in template
  files would make prompt templates more maintainable.
- *Effort*: S
- *Impact*: low -- code hygiene improvement.

** Finding 14: Auto Dream (Memory Consolidation)

- *Source*: 23-Memory系统.md, Section 7 (Auto Dream)
- *Claude Code approach*: After accumulating 5+ sessions over 24+ hours,
  a background consolidation process (~Auto Dream~) runs the ~/dream~
  skill to reorganize and optimize memories. Triple gating: time, session
  count, and file lock. Failed consolidation rolls back the lock mtime
  so the next session retries.
- *Our current state*: No consolidation mechanism. If we implement
  workspace-level knowledge accumulation, entries will grow unbounded.
- *Opportunity*: Deferred until memory accumulation is implemented. When
  it is, a periodic cleanup could merge redundant feedback entries,
  remove stale references, and compress learnings. This could run as an
  Emacs idle timer or a post-session hook rather than a separate agent.
- *Effort*: L
- *Impact*: medium (but only relevant after Finding 3 is implemented).

** Finding 15: Hook System Integration Points

- *Source*: 24-Skill-Plugin开发实战.md, Section 4 (Hook Scripts)
- *Claude Code approach*: Four hook types (command, prompt, agent, http)
  triggered at seven+ event points (PreToolUse, PostToolUse, Stop,
  SessionStart, UserPromptSubmit, etc.). Shell hooks receive JSON via
  stdin with full context. Exit code 2 has event-specific semantics
  (block tool call, continue conversation, block prompt).
- *Our current state*: We have Emacs-side hooks (~claude-org-pre-execute-hook~,
  ~claude-org-post-execute-hook~, sentinel functions) but these are
  Emacs Lisp hooks, not the CLI's hook system. The CLI's hook system
  runs independently.
- *Opportunity*: Bridge the two hook systems. When the CLI emits hook
  events in the stream-json output (e.g., tool permission requests),
  fire corresponding Emacs hooks. This would enable Emacs-side automation
  like: auto-approve file reads, log tool usage, or trigger org-mode
  actions on specific tool completions. The stream-json protocol already
  carries tool-use events.
- *Effort*: M
- *Impact*: medium -- enables power-user automation workflows.

* Recommended First Sprint

Three items that deliver high value with manageable effort:

1. *F5 (Skill Discovery)*: Add ~.claude/skills/~ scanning to
   ~claude-org--discover-slash-commands~. Parse SKILL.md frontmatter for
   description. Under 100 lines of Elisp.

2. *F1 (Semantic Faces)*: Define 8-10 ~defface~ declarations, replace all
   ~font-lock-*-face~ references in header-line and response rendering.
   Under 50 lines.

3. *F3a (Session Summary)*: After each AI block execution, auto-update a
   ~:SESSION_SUMMARY:~ property on the workspace heading with task state,
   key files, and recent errors. Inject as context on session resume.
   Under 150 lines.

Total estimated effort: 2-3 days. These three changes address the largest
gaps identified in this review (skill parity, visual identity, and memory
continuity).
