* Overview

This research investigates integrating =claude-code.el= (by Stephen Molitor) as a
native interactive backend for our claude-agent system, enabling users to open a
persistent terminal buffer for direct Claude Code interaction within the SDD workflow.

** Architecture

claude-code.el is a terminal-wrapper package. It spawns the =claude= CLI inside an
Emacs terminal emulator (eat or vterm), provides keybindings for interaction, and
manages multiple instances per directory.

*** Terminal Backend Abstraction

Uses =cl-defgeneric= for two terminal implementations:

| Generic Method | Purpose |
|----------------+---------|
| =term-make= | Create terminal buffer |
| =term-send-string= | Send text to terminal |
| =term-kill-process= | Kill terminal process |
| =term-read-only-mode= | Enter text selection mode |
| =term-interactive-mode= | Return to terminal input |
| =term-configure= | Post-creation setup |
| =term-setup-keymap= | Bind keys |

Default backend: =eat= (lighter weight, better Emacs integration).
Alternative: =vterm= (full terminal emulation, requires C compilation).

*** Process Lifecycle

1. Determine directory: project root → file directory → default-directory
2. Check for existing instances in that directory
3. Generate buffer name: =*claude:/path/to/dir:instance-name*=
4. Set environment variables via =claude-code-process-environment-functions= hook
5. Create terminal with backend-specific =term-make=
6. Configure keys, faces, display
7. Run =claude-code-start-hook=

*** Session Management

- Sessions controlled by Claude CLI, not by Emacs
- =--continue= flag resumes previous conversation
- =--resume= flag selects specific past session
- Multiple instances per directory via custom names
- Instance registry: =claude-code--directory-buffer-map= (hash table)

*** System Prompt Handling

*IMPORTANT*: claude-code.el does NOT support =--system-prompt= natively in its UI.
It passes arguments through:
- =claude-code-program-switches= (defcustom, list of strings)
- Extra switches to =claude-code--start=
- Environment variables via =claude-code-process-environment-functions=

The =--system-prompt= flag would need to be added to switches programmatically.

*** Hook System (CLI Event Integration)

- Entry point: =claude-code-handle-hook= receives events from =emacsclient --eval=
- Reads JSON from =server-eval-args-left=
- Runs =claude-code-event-hook= (abnormal hook)
- Handles: notifications, tool use, session events
- Different from our hook system (ours uses shell scripts + =emacsclient=)

** Current Backend Implementations

*** 1. JSON Stream Backend (=claude-agent-json-backend=)

- Default backend
- One-shot subprocess: =claude --print --output-format stream-json=
- Pipe-based I/O (not PTY)
- Structured JSON messages (parsed into message structs)
- Supports: =:streaming-tokens=, =:structured-messages=, =:tool-use=, =:session-resume=

*** 2. Claude CLI Backend (=claude-agent-claude-backend=)

- Interactive terminal via =eat= package
- Long-lived process with persistent session
- Uses bracketed paste to send prompts
- Detects prompt-ready via =❯= character search
- Hook-based event handling (SessionStart, Stop, PreToolUse, PostToolUse)
- Supports: =:streaming-tokens=, =:session-resume=, =:interactive-input=, =:persistent-client=

* Comparison: claude-code.el vs Our claude-cli Backend

| Feature | claude-code.el | Our claude-cli backend |
|---------+----------------+----------------------|
| Terminal emulator | eat or vterm (configurable) | eat only |
| System prompt | Via switches (manual) | Via =--system-prompt= flag (automatic) |
| Session management | CLI-controlled (--continue/--resume) | Hook-based (SessionStart/Stop) |
| Permission handling | Claude Code's native UI | Emacs permission functions via hooks |
| Hook system | =emacsclient --eval= with JSON events | Shell script + =emacsclient --eval= |
| Buffer naming | =*claude:/path:name*= | =*claude-cli<session-key>*= |
| Multi-instance | Per-directory with names | Per-session-key |
| Response delivery | User reads terminal directly | Captured via Stop hook → on-token callback |
| Window management | Dedicated display functions | No special handling |
| Transient menus | Full transient command map | None |
| Minor mode | =claude-code-mode= | None |
| Keybindings | Rich command map (send, toggle, etc.) | Minimal |

* Key Findings

** 1. We Already Have 90% of the Terminal Backend

Our =claude-agent-claude-backend= already implements everything claude-code.el does
at the backend level: =eat= terminal, =--system-prompt= passing, hook-based event
handling, session persistence. The main things claude-code.el adds are /UX polish/:
transient menus, keybindings, window management, and the minor mode.

** 2. The User's Request Is Different from Both

The user wants a *standalone interactive terminal buffer* where they:
- See Claude's TUI directly (not captured/streamed into org)
- Type commands manually
- Use it as a complement to the org-based workflow
- Keep the buffer alive across multiple queries

This is closer to claude-code.el's UX model but with our system prompt integration.

** 3. Migration Is Not Needed — Integration Is

Rather than migrating claude-code.el code into our codebase:
- *Option A*: Add a new =CLAUDE_BACKEND= type "native" that opens a visible
  terminal buffer using our existing =claude-agent-claude-backend= infrastructure
  but skips the response-capture mechanism
- *Option B*: Use claude-code.el directly by wrapping =claude-code--start= with
  our system prompt and project root injection
- *Option C*: Create a thin adapter that uses claude-code.el's terminal management
  but plugs into our backend protocol for system prompt assembly

** 4. System Prompt Integration Is the Key Value-Add

The main reason to integrate (vs just using =claude-code= standalone) is automatic
system prompt injection from the org file's =:system_prompt:= sections and SDD
behavior prompts. This gives the interactive terminal the same context as the
org-based workflow.

** 5. Two Distinct Use Modes

| Mode | Backend | Response Goes To | Buffer |
|------+---------+------------------+--------|
| Org-embedded | json-stream | Org buffer (streamed text) | Hidden process buffer |
| Org-embedded (CLI) | claude-cli | Org buffer (via Stop hook) | Hidden eat buffer |
| Interactive (NEW) | native | Terminal buffer (user reads directly) | Visible eat/vterm buffer |

The "native" mode is fundamentally different: the user interacts in the terminal,
not in the org file. The org file just provides the /launch context/ (system prompt,
project root, session key).

* Recommendation

*Option A is the best path*: extend our existing =claude-agent-claude-backend= to
support a "visible/interactive" mode. This avoids:
- Adding a dependency on claude-code.el
- Duplicating terminal management code
- Maintaining two parallel hook systems

The key changes needed:
1. A new =CLAUDE_BACKEND= value (e.g., "native") that creates the eat buffer
   but shows it to the user instead of hiding it
2. Skip response capture (no =on-token= callback from Stop hook)
3. Use our existing system prompt assembly pipeline
4. Add basic UX: window display, keybindings for common actions
5. Optionally borrow some UX ideas from claude-code.el (transient menu, mode-line)
