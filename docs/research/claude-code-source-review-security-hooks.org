#+TITLE: Security Audit: Claude Code Source Review -- Permission, Hooks, Settings, Error Recovery
#+DATE: 2026-04-08

* Overview

Security and engineering analysis of Claude Code's internal architecture
(docs 16--20 of the source study series) mapped against our emacs-cmux
integration.  Each finding identifies a specific pattern in Claude Code,
compares it to our current implementation, and proposes a concrete improvement.

Source documents:
- =16-权限系统.md= -- Permission pipeline, rule chains, AI classifier
- =17-Settings-系统.md= -- 6-layer config merge, MDM, hot reload
- =18-Hooks系统.md= -- 27 lifecycle events, execution engine, security controls
- =19-Feature-Flag与编译期优化.md= -- Build-time DCE, runtime flags
- =20-API调用与错误恢复.md= -- Retry with backoff, streaming fallback

* Findings

** Finding 1: MCP Server Has No Authentication
- *Source*: Our =emacs-mcp-server.org=, MCP client in =mcp_client.py=
- *Claude Code approach*: Claude Code's hook system uses stdin/stdout JSON
  protocol (no network exposure).  MCP servers in Claude Code require
  explicit =allowedMcpServers= whitelist in settings (doc 17, =SettingsSchema=).
  The internal hook trust model requires workspace trust dialog acceptance
  before any hook runs (doc 18, =shouldSkipHookDueToTrust()=).
- *Our current state*: The MCP server binds to =127.0.0.1:9999= (HTTP, no TLS,
  no authentication).  Any local process can send JSON-RPC to =/mcp= and
  execute arbitrary elisp via =evalElisp=.  The =McpClient= in Python has no
  auth token, no session validation.  The only protection is localhost binding.
- *Opportunity*: Add a per-session bearer token generated at MCP server startup,
  passed to Claude CLI via =--plugin-dir= environment variables.  The Python
  =workspace_bridge= would include this token in HTTP headers.  The MCP server
  rejects requests without a valid token.  This prevents rogue local processes
  (other user sessions, compromised build scripts, browser-exploitable
  localhost requests) from executing arbitrary elisp.
- *Effort*: S
- *Impact*: high
- *Security relevance*: CRITICAL -- =evalElisp= without auth is equivalent to
  arbitrary code execution.  Any process on the same host can read/write any
  file, execute shell commands, and exfiltrate credentials through Emacs.
  Localhost binding is insufficient (CVE-2018-4878 class: browser-based
  localhost exploitation via DNS rebinding or CORS misconfiguration).

** Finding 2: evalElisp Has No Input Sanitization or Sandboxing
- *Source*: Doc 16 (path validation, TOCTOU prevention); our =emacs-mcp-server.org= line 386--451
- *Claude Code approach*: Claude Code validates all tool inputs through
  Zod schemas before execution.  File paths go through =validatePath()= with
  UNC path blocking, tilde variant rejection, shell expansion syntax detection,
  and glob pattern restrictions for write operations.  The permission pipeline
  has 7 steps of checks before any tool runs.
- *Our current state*: =evalElisp= accepts a =code= string and evaluates it
  directly with =(eval form t)=.  There is a timeout (default 10s) and
  =condition-case= for errors, but no validation of the code content.  The
  tool description warns about single-threaded blocking, but there is no
  restriction on what elisp can be evaluated (=delete-file=, =shell-command=,
  =url-retrieve= to exfiltrate data, =(kill-emacs)=, etc.).
- *Opportunity*: While full sandboxing of elisp is impractical, we should:
  (1) Add a configurable allowlist of callable functions (defense-in-depth).
  (2) Block known-dangerous functions like =shell-command=, =call-process=,
      =delete-file=, =kill-emacs= unless the caller provides elevated auth.
  (3) Add rate limiting (max N calls per minute) to limit blast radius.
  (4) Log all evalElisp calls with caller identity and code content for
      audit trail (currently only logs to =*MCP Server Log*= buffer when
      =emacs-mcp-server-verbose= is non-nil).
- *Effort*: M
- *Impact*: high
- *Security relevance*: HIGH -- Combined with Finding 1 (no auth), any local
  process can execute arbitrary code in the user's Emacs session.  Even with
  auth, evalElisp should have defense-in-depth controls.

** Finding 3: Permission System Lacks Rule Chains and Content-Level Matching
- *Source*: Doc 16, sections 2.1--2.4 (rule data structure, shell matching)
- *Claude Code approach*: Permissions use a 3-part rule model:
  =source + behavior (allow/deny/ask) + ruleValue (toolName + ruleContent)=.
  Rules are loaded from 8 sources with defined priority.  Shell commands support
  3 matching modes (exact, prefix, wildcard).  The 7-step decision pipeline
  checks deny rules, tool-internal permissions, content-level ask rules, and
  safety checks -- all *before* mode-level bypass is considered.  Critically,
  =safety checks survive bypass mode=.
- *Our current state*: We have =claude-org-allowed-tools= (a flat list of tool
  pattern strings like ="Read"=, ="Bash(git *)"=) and
  =emacs-mcp-server-allowed-tools= (="mcp__emacs__*"=).  Permission mode is
  a single org property (=CLAUDE_PERMISSION_MODE=) mapped to CLI values.
  There are no deny rules, no content-level matching in our layer, no safety
  checks for dangerous paths.  We delegate entirely to Claude Code's built-in
  permission system.
- *Opportunity*: Since Claude Code already implements the full permission
  pipeline, our delegation is actually correct for security.  However, we
  should:
  (1) Support deny patterns in =claude-org-allowed-tools= (prefix =-= for deny).
  (2) Add a =claude-org-denied-tools= defcustom for explicit deny rules.
  (3) Pass deny rules to CLI via =--disallowedTools= flag.
  (4) Consider adding safety checks for =.git/= and =.claude/= paths in our
      PreToolUse hook (doc 16, section 5.2 path safety).
- *Effort*: S
- *Impact*: medium
- *Security relevance*: MEDIUM -- Claude Code's internal permission system
  handles most cases, but our hook layer could add defense-in-depth.

** Finding 4: Hook System Lacks Error Isolation
- *Source*: Doc 18, section 3.2 (trust check), section 4.4 (exit code semantics),
  section 8 (three-level controls)
- *Claude Code approach*: Hooks are executed with strict error isolation:
  =Promise.allSettled()= ensures one hook failure does not affect others.
  Exit code semantics are well-defined (0=success, 2=blocking, other=non-blocking).
  Three security levels control hook execution: normal, managedOnly, disableAll.
  Workspace trust is checked before any hook runs.  Hook configs are captured
  as snapshots at startup, preventing mid-session injection.
- *Our current state*: =hooks.json= defines 6 hook entries with 5--10s timeouts.
  The Python =workspace_bridge.py= catches =McpConnectionError= and
  =McpElispError= in each handler, but uses bare =except Exception: pass= in
  some places (e.g., =handle_session_start= line 194).  There is no
  trust-checking mechanism -- hooks run unconditionally.  If the MCP server is
  unreachable, hooks silently fail (soft-fail with =sys.exit(0)=).  There is no
  equivalent to Claude Code's =shouldSkipHookDueToTrust()= check.
- *Opportunity*:
  (1) Add explicit error categories: distinguish between
      "MCP unreachable" (warn once, continue),
      "elisp error" (log and report back to Claude),
      "timeout" (kill and report).
  (2) Use exit code 2 for blocking errors in the permission hook -- currently
      handle_permission returns JSON to stdout but does not use exit codes
      for error signaling to Claude Code.
  (3) Add a trust verification step: verify the MCP server token (from Finding 1)
      before executing any hook logic.
  (4) Add hook execution metrics (count, latency, error rate) for observability.
- *Effort*: M
- *Impact*: medium
- *Security relevance*: MEDIUM -- Silent failures in hooks could mask security-
  relevant events (e.g., a permission hook failing silently allows unreviewed
  tool use).

** Finding 5: Settings Layering is Flat Compared to Claude Code's 6-Layer System
- *Source*: Doc 17, sections 1--3 (5+1 layers, merge algorithm, Zod validation)
- *Claude Code approach*: Settings come from 5 formal sources plus 1 plugin base
  layer, merged with clear priority (user < project < local < flag < policy).
  Policy settings use "first source wins" internally with remote API > MDM >
  file > registry.  Arrays are merged by concatenation+dedup, not replacement.
  Every config file is validated with Zod schemas before merging.  Invalid rules
  are filtered individually rather than rejecting the whole file.  Three-level
  caching (file parse, per-source, merged result) avoids redundant I/O.
- *Our current state*: Settings come from 3 flat sources:
  (a) =defcustom= variables (global Emacs config),
  (b) org file-level =#+PROPERTY:= keywords,
  (c) section-level property drawers.
  Priority is: section > file > defcustom.
  =claude-org-setting-sources= controls which Claude Code sources to use
  (default: =("user")=).  There is no validation of property values, no
  caching, no hot-reload detection.  Setting sources are passed to CLI via
  =--setting-sources= flag.
- *Opportunity*:
  (1) Add validation for =CLAUDE_PERMISSION_MODE= values -- currently any
      string is accepted; invalid values silently fall through to ="default"=.
  (2) Support project-level settings: automatically add ="project"= to
      =--setting-sources= when a =.claude/settings.json= exists in the project.
  (3) Consider caching org property lookups -- repeated =org-entry-get= with
      inheritance is O(n) in heading depth per call.
  (4) Add a "policy" equivalent: a site-wide Emacs config that cannot be
      overridden by per-file properties (useful for enterprise Emacs deployments).
- *Effort*: M
- *Impact*: medium
- *Security relevance*: LOW-MEDIUM -- Missing validation could allow unexpected
  behavior but security is primarily enforced by Claude Code's pipeline.

** Finding 6: No Retry or Error Recovery for MCP Communication
- *Source*: Doc 20, sections 1--3 (withRetry, exponential backoff, shouldRetry)
- *Claude Code approach*: API calls use =withRetry= with AsyncGenerator for
  intermediate status.  Up to 10 retries with exponential backoff
  (500ms base, 32s cap, 25% jitter).  529 errors trigger model fallback after
  3 consecutive failures.  Background requests immediately drop on 529 to avoid
  amplifying capacity cascades.  Auth errors (401) auto-refresh tokens.
  Context overflow errors auto-adjust max_tokens.  Streaming failures fall back
  to non-streaming mode.
- *Our current state*: The =McpClient= in Python makes a single HTTP request
  with =connect_timeout=3.0= and =read_timeout=10.0=.  No retry on failure.
  No backoff.  No distinction between transient and permanent errors.  If the
  MCP server is briefly unreachable (Emacs garbage collection pause, buffer
  switch), the hook fails permanently.  The =claude-agent.org= core has only
  one =condition-case= retry pattern (click-to-retry overlay for usage errors).
- *Opportunity*:
  (1) Add retry with exponential backoff to =McpClient.eval_elisp()= for
      connection errors (=URLError=, =TimeoutError=): 2--3 attempts with
      500ms/1s/2s delays.  Do NOT retry on =McpElispError= (application-level
      error, not transient).
  (2) Add jitter (10--25%) to prevent thundering herd when multiple hooks
      trigger simultaneously.
  (3) Log retry attempts with attempt count and delay for observability.
  (4) Consider a circuit breaker: after N consecutive MCP failures, stop
      attempting for M seconds and log a warning.
- *Effort*: S
- *Impact*: high
- *Security relevance*: LOW -- This is primarily a reliability improvement, but
  transient MCP failures causing hook bypasses could have security implications
  if the permission hook silently fails.

** Finding 7: Hook Timeout Values May Be Too Short for Complex Operations
- *Source*: Doc 18, section 4.2 (env var injection), section 5 (async hooks)
- *Claude Code approach*: Hook timeouts are configurable per-hook.  Shell hooks
  support async mode (=hook.async = true=) for long-running operations.
  =asyncRewake= mode allows background execution with model notification on
  exit code 2.  The system distinguishes between sync hooks (must complete
  before tool executes) and async hooks (fire-and-forget with optional callback).
- *Our current state*: =hooks.json= uses fixed timeouts: 5s for session-start,
  permission, permission-clear, tool; 10s for prompt and response (Stop).
  The response handler reads transcript files, calls MCP to insert text, and
  runs completion hooks -- all within the 10s timeout.  For large transcripts
  (long Claude conversations), 10s may be insufficient.  There is no async
  hook support.
- *Opportunity*:
  (1) Increase the Stop hook timeout to 30s for large transcript processing.
  (2) Add async support for the response insertion hook: return
      ={"async": true}= immediately, then process the transcript in background.
      Use exit code 2 + stderr to notify Claude if insertion fails.
  (3) Make timeouts configurable via org properties or environment variables
      rather than hardcoded in =hooks.json=.
  (4) Add latency metrics to identify which hooks are timing out in practice.
- *Effort*: S
- *Impact*: medium
- *Security relevance*: LOW -- Timeout issues are reliability concerns, not
  directly security-relevant.

** Finding 8: No Denial Tracking or Circuit Breaker for Permission Decisions
- *Source*: Doc 16, section 4.2 (denial tracking), section 4.3 (classifier unavailable)
- *Claude Code approach*: =DenialTrackingState= counts consecutive and total
  denials.  After 3 consecutive or 20 total denials, the system falls back to
  user prompting (interactive) or aborts entirely (headless).  When the AI
  classifier is unavailable, a feature flag controls fail-closed vs fail-open
  behavior.  This prevents infinite "try-deny-retry" loops that waste tokens.
- *Our current state*: Our PreToolUse hook (=handle_permission=) only handles
  =AskUserQuestion= and =ExitPlanMode= tools.  For all other tools, it
  produces no output (passthrough).  There is no denial tracking, no circuit
  breaker, no monitoring of how many tools are being denied.  If Claude Code's
  internal classifier keeps denying operations, the agent loops indefinitely.
- *Opportunity*:
  (1) Track tool denial counts in the workspace bridge (write to status files).
  (2) After N consecutive denials, notify Emacs via MCP so the user sees a
      warning in the mode line or =*Messages*= buffer.
  (3) Consider exposing denial metrics through the OTel bridge for monitoring.
  (4) Add a "force-stop" mechanism that aborts the Claude session if denial
      count exceeds a threshold (configurable via org property).
- *Effort*: M
- *Impact*: medium
- *Security relevance*: MEDIUM -- Denial tracking prevents resource waste and
  helps identify misbehaving agents early.

** Finding 9: Hook Permission Handler Does Not Use Exit Code 2 Protocol
- *Source*: Doc 18, section 4.4 (exit code semantics), section 7 (permission
  decision protocol)
- *Claude Code approach*: Hooks use a structured exit code protocol:
  - Exit 0: success, stdout as message
  - Exit 2: blocking error, stderr fed back to model, operation blocked
  - Other: non-blocking error, stderr shown to user, operation continues
  PreToolUse hooks can return JSON with =permissionDecision= field
  (approve/block) and =updatedInput= to modify tool inputs.
  Priority is =deny > ask > allow > passthrough=.
- *Our current state*: =handle_permission= in =workspace_bridge.py= outputs
  JSON to stdout for interactive tools (=AskUserQuestion=, =ExitPlanMode=)
  with =permissionDecision: "ask"=.  For all other tools, it outputs nothing
  (implicitly passthrough).  It never uses exit code 2 for blocking.  It never
  returns =deny= or =approve= decisions.  It does not use =updatedInput= to
  modify tool parameters.
- *Opportunity*:
  (1) Use exit code 2 + stderr message when the permission hook detects a
      dangerous operation that should be blocked (e.g., file operations in
      protected paths defined by the user).
  (2) Add configurable deny patterns in the workspace bridge: read from an
      org property or environment variable, match against tool_name + tool_input,
      return ={"hookSpecificOutput": {"permissionDecision": "block"}}= with
      exit code 2.
  (3) Use =updatedInput= to sanitize tool inputs when appropriate (e.g., strip
      dangerous flags from Bash commands).
- *Effort*: M
- *Impact*: medium
- *Security relevance*: HIGH -- The permission hook is our primary security
  gate for the workspace bridge.  Without block/deny capability, it cannot
  prevent dangerous operations even when configured to do so.

** Finding 10: No Config Snapshot Isolation for Hook Definitions
- *Source*: Doc 18, section 8.2 (snapshot isolation)
- *Claude Code approach*: Hook configurations are captured as immutable
  snapshots at session setup time via =captureHooksConfigSnapshot()=.  They
  are only refreshed at defined safe points (worktree switch, explicit settings
  change).  This prevents an attacker who gains file-write access from injecting
  malicious hooks mid-session by modifying =settings.json=.
- *Our current state*: Our =hooks.json= is loaded by Claude Code at session
  start via =--plugin-dir=.  Claude Code's built-in snapshot mechanism protects
  this file.  However, our Python workspace bridge reads environment variables
  (=WORKSPACE_ORG_FILE=, =WORKSPACE_SESSION_ID=, =EMACS_MCP_URL=) at every
  invocation.  If an attacker can modify these environment variables mid-session
  (unlikely in the hook context, since they are set by Claude Code), they could
  redirect MCP calls to a different server.
- *Opportunity*:
  (1) Validate =EMACS_MCP_URL= format in the workspace bridge -- reject URLs
      that are not =http://127.0.0.1:PORT/mcp= or =http://localhost:PORT/mcp=.
      This prevents SSRF if env vars are somehow manipulated.
  (2) Pin the MCP port at session start and reject connections to different ports.
  (3) Verify that =WORKSPACE_ORG_FILE= exists and is within the project root.
- *Effort*: S
- *Impact*: medium
- *Security relevance*: MEDIUM -- Defense-in-depth against env var manipulation.

** Finding 11: No Streaming Fallback or Watchdog in JSON Stream Parser
- *Source*: Doc 20, sections 4.2--4.4 (stream idle watchdog, stall detection,
  non-streaming fallback)
- *Claude Code approach*: Stream processing includes: (a) optional idle
  watchdog (90s timeout, reset on each chunk), (b) stall detection (30s
  threshold between events, logged for telemetry), (c) automatic fallback to
  non-streaming mode when streaming fails, (d) explicit resource release
  for TLS/socket buffers held outside V8 heap.
- *Our current state*: The =claude-agent.org= JSON stream parser processes
  newline-delimited JSON from the Claude CLI subprocess.  Process filter errors
  are wrapped in =condition-case= to avoid killing the process.  There is no
  idle watchdog (if the CLI hangs, we wait indefinitely), no stall detection,
  no fallback mode.  The process sentinel handles cleanup on exit.
- *Opportunity*:
  (1) Add a watchdog timer that fires if no JSON output is received for
      configurable duration (default 120s).  On timeout, kill the process
      and report an error.
  (2) Track inter-event latency for stall detection.  Log warnings when
      gaps exceed 30s.
  (3) Add the watchdog timer reset to the process filter (each chunk resets it).
  (4) Expose stall/timeout metrics through OTel for monitoring.
- *Effort*: M
- *Impact*: medium
- *Security relevance*: LOW -- Primarily reliability/observability improvement.

** Finding 12: Elisp String Escaping in Workspace Bridge is Security-Critical
- *Source*: Doc 16, section 5.2 (TOCTOU, shell expansion prevention); our
  =workspace_bridge.py= line 91--100
- *Claude Code approach*: All tool inputs are validated through Zod schemas.
  Path inputs go through =validatePath()= which blocks shell expansion syntax
  (=$VAR=, =$(cmd)=, =%VAR%=), UNC paths, and tilde variants.
- *Our current state*: =_escape_elisp_string()= handles backslash, double-quote,
  newline, carriage return, tab, and null bytes.  This string is then
  interpolated into elisp s-expressions like:
  =(claude-org-workspace-bridge-insert-response "FILE" "SID" "RESPONSE" "CID")=.
  The escaping is adequate for double-quoted elisp strings but does not handle
  all edge cases.  Specifically:
  - Backslash sequences like =\x00=, =\u0000= in elisp are NOT handled
    (elisp does interpret =\x=, =\u=, =\U= escape sequences in strings)
  - If =response= text contains =")= followed by malicious elisp, the
    escaping handles the double-quote but the string could contain elisp
    reader macros like =#'= or =?\\= that interact with the outer form
- *Opportunity*:
  (1) Add escaping for elisp-specific escape sequences: =\x=, =\u=, =\U=
      should be escaped to =\\x=, =\\u=, =\\U=.
  (2) Consider using =prin1-to-string= on the Emacs side to generate safe
      string literals rather than manual Python-side escaping.
  (3) Add a fuzzing test that sends pathological strings through the bridge
      to verify escaping correctness.
  (4) For the highest security, pass data via temp files or structured JSON
      rather than string interpolation into elisp forms.
- *Effort*: S
- *Impact*: high
- *Security relevance*: HIGH -- Incorrect escaping in string interpolation
  into =eval= is a classic injection vulnerability.  A malicious response from
  Claude could potentially inject arbitrary elisp.

** Finding 13: Background Request Priority Missing
- *Source*: Doc 20, section 1.4 (background 529 handling)
- *Claude Code approach*: Background requests (summaries, title extraction,
  classifier calls) are immediately dropped on 529 errors rather than retried.
  This is explicitly to avoid amplifying capacity cascades -- "each retry is
  3-10x gateway amplification."  Foreground requests (user queries, SDK calls)
  get full retry budgets.
- *Our current state*: Title auto-generation (=claude-org-auto-generate-title=)
  spawns a separate Claude process for title generation.  This is effectively
  a background request but has the same retry/timeout behavior as foreground
  requests.  If the API is under load, title generation retries compete with
  the main query for capacity.
- *Opportunity*:
  (1) Mark title generation queries with a lower priority flag or reduced
      retry budget.
  (2) Skip title generation entirely when the main query encounters rate
      limiting (429/529).
  (3) Add a "background query" abstraction that automatically drops on
      capacity errors.
- *Effort*: S
- *Impact*: low
- *Security relevance*: NONE -- This is a reliability/efficiency improvement.

* Recommended Implementation Order

1. *Finding 1* (MCP auth token) -- highest security impact, smallest effort.
   Generate a random token at MCP server start, pass via env to hooks, validate
   in HTTP handler.  Blocks the most critical attack vector.

2. *Finding 12* (elisp string escaping) -- high security, small effort.
   Add =\x=, =\u=, =\U= escaping.  Add a fuzz test.  Prevents injection.

3. *Finding 6* (MCP retry) -- high reliability impact, small effort.
   Add 2-retry with backoff to =McpClient=.  Prevents transient failures from
   causing data loss (missed response insertions).

4. *Finding 9* (exit code 2 protocol) -- enables the permission hook to
   actually block dangerous operations.  Required before we can implement
   any deny-pattern logic in the workspace bridge.

5. *Finding 2* (evalElisp hardening) -- medium effort but critical for
   defense-in-depth.  Can be incremental: start with audit logging, then
   add rate limiting, then optional function blocklist.

6. *Findings 3, 4, 8, 10* -- medium effort improvements that add
   defense-in-depth layers.  Implement as time allows.

7. *Findings 5, 7, 11, 13* -- lower priority reliability/observability
   improvements.  Nice to have but not security-critical.

* Appendix: Claude Code Architecture Patterns Worth Adopting

** Pattern A: Defense-in-Depth Permission Pipeline

Claude Code's 7-step permission pipeline ensures that safety checks survive
even =bypassPermissions= mode.  Key insight: separate "configurable trust
levels" (which users can control) from "invariant safety checks" (which
always apply).  Our system currently delegates entirely to Claude Code's
pipeline, which is correct -- but we should add our own invariant checks
in the workspace bridge layer.

** Pattern B: Graceful Degradation in Config Parsing

Claude Code filters invalid permission rules individually rather than
rejecting the entire config file.  =SettingsSchema= uses =.catch(undefined)=
to degrade unknown values to undefined rather than failing validation.
Our org property parsing should adopt this: invalid =CLAUDE_PERMISSION_MODE=
values should log a warning and fall through to the default, not silently
produce unexpected behavior.

** Pattern C: Snapshot + Controlled Refresh

Hook configs are captured as snapshots at startup, refreshed only at
defined safe points.  This prevents mid-session config injection attacks.
We should verify that our =hooks.json= path cannot be modified after Claude
Code has loaded it (it cannot, since Claude Code snapshots it -- but we
should document this guarantee).

** Pattern D: Exit Code Semantic Protocol

The 0/2/other exit code convention is elegant and minimal.  Our workspace
bridge should adopt this for all hook handlers, not just permission hooks.
This gives Claude Code structured error information without requiring
JSON parsing of stderr.

** Pattern E: Background Request Shedding

Immediately dropping background requests during capacity issues (rather
than retrying) is counterintuitive but critical for system stability.
Each retry amplifies load 3-10x.  Our title generation should adopt this
pattern.
