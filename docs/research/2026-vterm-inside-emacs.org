#+TITLE: Research: VTerm Inside Emacs
#+DATE: 2026-03-12
#+STATUS: complete

* Executive Summary

This research surveys the landscape of terminal emulation solutions for Emacs
and external terminal emulator projects whose code could be adapted for an
Emacs-native vterm implementation. Key findings:

1. *emacs-libvterm* is the gold standard (~1.7K stars) but requires C dynamic
   modules, has no Windows support, and suffers from crashes and build complexity
2. *EAT* (Emulate A Terminal) is a pure-Elisp alternative — zero build deps,
   but performance trades off against vterm for heavy output
3. *libvterm* (the C library) is small (~7K LOC), battle-tested (used by Neovim),
   and is the most practical terminal engine to embed
4. Among standalone terminals, *st (suckless)* has the smallest codebase (~5K LOC)
   and *alacritty_terminal* / *termwiz* Rust crates offer well-separated terminal
   state machines
5. The Emacs dynamic module API is the right bridge for performance-critical
   terminal emulation — it's stable, cross-platform (Linux/macOS), and proven

** emacs-libvterm (The Gold Standard)

- *Repository*: https://github.com/akermu/emacs-libvterm
- *Stars*: ~1,700 | *Contributors*: ~90 | *Status*: Alpha (actively developed)
- *License*: GPL-2.0+

*** Architecture
#+begin_example
  Shell process (bash/zsh/fish)
       ↓ (pty)
  libvterm (C library) — parses VT escape sequences, maintains screen state
       ↓ (Emacs module API)
  vterm-module.so — C bridge: reads libvterm screen, writes to Emacs buffer
       ↓ (elisp calls)
  vterm.el — buffer management, keybindings, copy mode, session tracking
#+end_example

*** Codebase Breakdown

| File | Size (bytes) | Purpose |
|------+--------------+---------|
| vterm-module.c | 51,459 | Core C module (~1,500 LOC): scrollback, rendering, input, OSC handling |
| vterm-module.h | 5,689 | Header file |
| elisp.c | 6,702 | Emacs module API helper functions |
| elisp.h | 3,727 | Header file |
| utf8.c | 2,198 | UTF-8 encoding utilities |
| utf8.h | 308 | Header file |
| vterm.el | 74,265 | Elisp frontend (~2,500 LOC): buffer setup, keybindings, modes |
| CMakeLists.txt | 3,602 | Build system |
| etc/*.sh | ~7K | Shell integration scripts (bash, zsh, fish) |

*Total*: ~4,000 LOC C + ~2,500 LOC Elisp ≈ *6,500 LOC*

*** Key Design Decisions
- Uses libvterm as the terminal state machine (delegates all VT parsing)
- Scrollback managed in C (ring buffer with memory recycling)
- Screen refresh: reads cell-by-cell from libvterm, applies face properties
- Input: translates Emacs key events → libvterm keyboard input
- OSC callbacks enable directory tracking, clipboard, and elisp execution
- Shell integration via sourced scripts (bash/zsh/fish)

*** Dependencies
- *Build*: CMake, C compiler, libvterm (vendored or system)
- *Runtime*: Emacs 25.1+ compiled with =--with-modules=
- *NOT supported*: Windows, Emacs without module support

*** Known Issues and Limitations
1. *No text rewrap on resize* — the #1 community complaint
2. *Crashes possible* — low-level C code can segfault
3. *Apple Silicon build issues* — x86_64 vs arm64 module mismatch
4. *No Windows support* — pty-based, Unix-only
5. *Evil-mode not supported* — must use shell-level vi emulation
6. *Alpha status* — public API may change
7. *fzf display garbled* — some TUI apps don't render correctly
8. *No session management* — no built-in multi-session support

*** Pros
- Best performance for heavy terminal output
- Full xterm-256color compatibility
- Battle-tested libvterm engine (also used by Neovim)
- Active community and maintenance
- Shell integration (directory/prompt tracking)

*** Cons
- Complex build (CMake + C compiler + libvterm)
- Segfault risk from C module bugs
- No Windows support
- No rewrap on resize
- Requires Emacs compiled with module support

** EAT (Emulate A Terminal)

- *Repository*: https://codeberg.org/akib/emacs-eat
- *Stars*: ~700 | *Status*: Active development
- *License*: GPL-3.0+

*** Architecture
#+begin_example
  Shell process (bash/zsh/fish)
       ↓ (pty via make-process)
  eat.el — Pure Elisp VT parser + screen state machine
       ↓ (direct buffer manipulation)
  Emacs buffer — text properties for colors, cursor, etc.
#+end_example

*** Codebase
- Single file: =eat.el= — estimated *~10,000+ LOC*
- Implements full VT100/VT220/xterm escape sequence parser in Elisp
- Includes terminfo database entries for proper terminal identification

*** Key Design Decisions
- *Pure Elisp* — no dynamic modules, no C code, no build step
- Escape sequence parser is a hand-coded state machine
- Uses Emacs text properties extensively for terminal attributes
- Integrates with Eshell in addition to standalone terminal mode
- Supports line wrapping on resize (unlike vterm)

*** Performance Optimization Techniques
- Chunked output processing to avoid blocking Emacs event loop
- Efficient text property application (batch operations)
- Careful use of buffer-local variables
- Avoidance of regexp for escape sequence parsing (character-by-character)

*** Pros
- Zero build dependencies — pure Elisp, works everywhere Emacs runs
- Supports text rewrap on resize
- Eshell integration
- No crash risk from C modules
- Potentially works on Windows (with suitable pty layer)

*** Cons
- Slower for high-throughput output (Elisp vs C parsing)
- Very large single file — harder to maintain
- Less mature than vterm ecosystem
- Some TUI applications may have rendering differences

** term.el / ansi-term (Built-in)

- *Built into Emacs since Emacs 21*
- Pure Elisp terminal emulation
- Two modes: line mode (editable) and char mode (raw terminal)

*** Limitations
- Very basic VT100 emulation — many escape sequences unsupported
- No true color (24-bit) support
- Poor performance with large output
- Mouse support is minimal
- Many TUI applications don't work correctly
- Maintained but rarely improved

** eshell (Built-in)

- Not a terminal emulator — it's a shell written in Elisp
- Cannot run TUI applications (htop, vim, etc.)
- Excellent Emacs integration (elisp interop, tramp, etc.)
- Good for basic shell commands, not for our vterm use case

** shell-mode (Built-in)

- Simply captures process output into a buffer
- No terminal emulation at all
- No escape sequence handling
- Not suitable for interactive terminal use

** st (Simple Terminal) — Suckless

- *Source*: https://git.suckless.org/st/
- *Language*: C | *LOC*: ~5,000 (very small)
- *License*: MIT

*** Analysis
- Extremely minimal terminal emulator for X11
- Single main file (st.c) + x.c for X11 rendering
- VT100/VT220/xterm escape sequence handling in ~2,000 lines
- 256 colors + true color support, UTF-8, selection
- X11 rendering is mixed with terminal logic (not cleanly separable)
- Patch ecosystem: community extends via diff patches
- *Migration potential*: Terminal parsing logic is small enough to port to Elisp
  or adapt as a C module, but would need significant refactoring to decouple
  from X11

** foot — Wayland Terminal

- *Source*: https://codeberg.org/dnkl/foot
- *Language*: C | *LOC*: ~25,000
- *License*: MIT

*** Analysis
- Fast, lightweight Wayland terminal emulator
- Software rendering (no GPU), damage tracking, threaded rendering
- Server mode: one process hosts multiple windows
- Custom dependencies: tllist (typed linked list), fcft (font rendering)
- Terminal logic tightly coupled with Wayland compositor interface
- *Migration potential*: Low — too many custom dependencies, Wayland-specific

** alacritty — GPU-Accelerated Terminal

- *Source*: https://github.com/alacritty/alacritty
- *Language*: Rust | *Stars*: ~57K | *LOC*: ~50,000+
- *License*: Apache-2.0

*** Analysis
- Separable =alacritty_terminal= crate (458K+ downloads on crates.io)
- Terminal emulation logic is cleanly separated from rendering
- Workspace structure: alacritty (binary) + alacritty_terminal (library)
- Good API design for external use
- *Migration potential*: High for Rust-based approach — could wrap
  =alacritty_terminal= in a dynamic module. But Rust → Emacs module bridge
  adds complexity vs C.

** wezterm — termwiz Crate

- *Source*: https://github.com/wezterm/wezterm
- *Language*: Rust | *Stars*: ~18K
- *License*: MIT

*** Analysis
- =termwiz= crate: standalone terminal library (3.3M downloads)
- Handles: escape parsing, terminal attributes, true color, sixel, hyperlinks
- Cross-platform including Windows
- =wezterm-term= crate: full terminal state machine
- *Migration potential*: High — termwiz/term crate is well-designed for library
  use. MIT license compatible. Could be wrapped as Emacs dynamic module via
  Rust FFI. But adds Rust toolchain requirement.

** xterm.js — Browser Terminal

- *Source*: https://github.com/xtermjs/xterm.js
- *Language*: TypeScript | *Stars*: ~17K
- *License*: MIT

*** Analysis
- Powers VS Code's terminal, extremely well-tested
- Parser is cleanly separated in =xterm-parser= module
- State machine approach to escape sequence parsing
- *Migration potential*: The parsing logic could inform an Elisp or C
  implementation. Not directly usable (JavaScript), but the design patterns
  and test suites are invaluable reference material.

** libvterm — The C Library

- *Source*: https://www.leonerd.org.uk/code/libvterm/ (Launchpad/CPAN)
- *Maintainer*: Paul "LeoNerd" Evans
- *Language*: C | *LOC*: ~7,000
- *License*: MIT
- *Users*: Neovim, emacs-libvterm, pangoterm

*** Architecture
#+begin_example
  Input bytes → Parser (VT state machine) → Screen callbacks
                                           → Scrollback callbacks
                                           → Cursor callbacks

  Output: Screen cells with attributes, cursor position, scrollback
#+end_example

*** API Design
- Clean separation: parser → state → screen → user callbacks
- =VTermScreen= object manages full terminal state
- Cell-by-cell access: =vterm_screen_get_cell()=
- Resize handling: =vterm_set_size()=
- Input: =vterm_keyboard_key()=, =vterm_keyboard_unichar()=
- Full VT100/VT220/xterm compatibility
- Supports: 256 color, true color, mouse, Unicode, bold/italic/underline

*** Why It's the Best Engine Choice
1. Already proven in emacs-libvterm and Neovim
2. Tiny codebase (~7K LOC) — easy to audit and maintain
3. Clean C API — straightforward to wrap in Emacs module
4. MIT license — compatible with GPL
5. Active maintenance by original author
6. No dependencies beyond C standard library

* Emacs Dynamic Module System

** How It Works

Emacs dynamic modules (since Emacs 25.1) allow loading shared libraries (.so/.dylib)
that extend Emacs with C/Rust/etc. code.

*** Key API Points
- Module must export =emacs_module_init()= function
- Receives =emacs_env= struct with function pointers for Emacs interaction
- Can create/manipulate Emacs values, call Elisp functions, define new functions
- Uses reference counting for GC safety

*** Requirements
- Emacs compiled with =--with-modules= (default since Emacs 27)
- C compiler + build system (CMake/Make)
- Platform-specific shared library format (.so on Linux, .dylib on macOS)

*** Performance Characteristics
- Function call overhead: minimal (~nanoseconds per call)
- Data marshaling: string/integer conversion between C and Elisp
- Bulk operations: much faster to process in C and push results to Emacs buffer
- *Key insight*: Terminal rendering is perfect for dynamic modules — heavy parsing
  in C, lightweight buffer updates via module API

*** Cross-Platform Support

| Platform | Status | Notes |
|----------+--------+-------|
| Linux (x86_64, aarch64) | ✓ Full support | Default in most distros |
| macOS (Intel) | ✓ Full support | Homebrew Emacs includes modules |
| macOS (Apple Silicon) | ✓ Works | Must match architecture (arm64) |
| Windows | ✓ DLL support | Emacs for Windows supports .dll modules |
| *BSDs | ✓ Generally works | May need gmake |

** How emacs-libvterm Uses It

1. =vterm-module.c= calls =emacs_module_init()= to register C functions
2. =elisp.c= wraps common Emacs module API patterns (make_string, funcall, etc.)
3. C functions exposed to Elisp: =vterm-new=, =vterm-update=, =vterm-redraw=, etc.
4. Data flow: libvterm callbacks → C struct → Emacs buffer text + properties
5. Screen refresh: iterates cells, builds text with face properties, inserts into buffer

* Community Insights

** Top Pain Points with Current vterm

1. *No text rewrap on terminal resize* — universally cited as most annoying
2. *Build complexity* — CMake + libvterm + architecture matching
3. *Segfaults* — C module bugs crash entire Emacs
4. *macOS Apple Silicon issues* — architecture mismatch in compiled module
5. *Evil-mode incompatibility* — must use shell-level vi mode
6. *No built-in multi-session* — requires third-party multi-vterm
7. *Some TUI apps broken* — fzf rendering issues, cursor positioning bugs

** EAT vs vterm Community Consensus

| Aspect | vterm | eat |
|--------+-------+-----|
| Performance (heavy output) | Winner | Slower |
| Installation ease | Complex (C build) | Easy (pure Elisp) |
| Text rewrap | No | Yes |
| Crash risk | Segfaults possible | None |
| Eshell integration | No | Yes |
| Emacs integration feel | Good | Better |
| TUI app support | Better | Good |
| Cross-platform | Unix only | Wider |

** Use Cases for Improved vterm in claude-agent

1. *Running Claude Code CLI* in an Emacs buffer with full TUI support
2. *Interactive debugging* — run programs with terminal UI inside Emacs
3. *Shell sessions* — integrated terminal without leaving Emacs
4. *Build monitoring* — watch compilation with ANSI color output
5. *SSH/Docker* — remote terminal sessions in Emacs buffers

* Conclusions and Recommendations

** Best Engine: libvterm

libvterm is the clear winner for the terminal emulation engine:
- Smallest codebase (~7K LOC) of any proven solution
- Battle-tested in Neovim and emacs-libvterm
- Clean C API perfectly suited for Emacs dynamic module wrapping
- MIT license, active maintenance
- Full terminal protocol support (true color, Unicode, mouse, OSC)

** Best Approach: Fork/Improve emacs-libvterm

Rather than building from scratch, the most practical approach is to fork
emacs-libvterm and improve it:

1. The ~6,500 LOC codebase is small and auditable
2. The architecture (libvterm → C module → Elisp) is sound
3. Known issues (rewrap, crashes, build) can be addressed incrementally
4. Community knowledge and shell integration scripts are reusable

** Alternative: Pure Elisp (EAT-inspired)

If avoiding C dependencies is paramount:
- Study EAT's approach to pure-Elisp terminal emulation
- ~10K LOC Elisp is manageable but harder to maintain than C engine
- Performance will always be worse than C for heavy output
- Better Emacs integration and no crash risk

** Hybrid Approach

The ideal solution combines:
1. libvterm as the C engine (proven, fast, small)
2. Improved Emacs module wrapper (fix rewrap, stability)
3. Better Elisp frontend (multi-session, evil support, AI integration)
4. Optionally, pure-Elisp fallback for environments without module support
