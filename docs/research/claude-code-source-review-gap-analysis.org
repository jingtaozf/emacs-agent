* Executive Summary

This document synthesizes findings from the 25-part Claude Code source study
against our emacs-cmux codebase. Claude Code is a ~1900-file TypeScript
application with deep investments in terminal UI, multi-agent orchestration,
prompt caching, and enterprise security. Our system takes a fundamentally
different approach: org-mode literate programming, persistent workspace
state, and cmux terminal multiplexing.

The analysis reveals that many of Claude Code's sophistications (Ink UI,
React reconciler, 60fps rendering, Yoga layout) are irrelevant to us because
our "UI" is Emacs itself. However, several core architectural patterns in
the AI interaction layer represent genuine gaps worth addressing.

* Methodology

Sources analyzed:
- Claude Code source study docs 01-25 (Chinese, ~50K words total)
- Our codebase: ARCHITECTURE.org, CLAUDE.md, all .org modules
- Cross-reference of feature coverage by functional domain

* Priority 1: Quick Wins (S effort, high impact)

** 1.1 Context Compaction / Auto-Compact

*** What Claude Code does
Claude Code implements a multi-tier context compression system (doc 06):
- Token budget management with =getEffectiveContextWindowSize()=
- Auto-compact threshold triggering (context window minus 33K buffer)
- Microcompact: lightweight cleanup of tool results between API calls
- Full compact: model-generated conversation summary via a dedicated prompt
- Cached microcompact: preserves prompt cache stability during cleanup
- Warning states: warning / error / blocking / auto-compact

*** Why it matters for emacs-cmux
Our system uses =--resume= with CLI session IDs and relies entirely on
Claude Code CLI's own compaction when running inside cmux. But when we
use the JSON stream backend directly (=claude-agent-query=), there is
no automatic context management. Long sessions silently degrade as
context fills up, and users have no visibility into token budget status.

*** Gap assessment: MEDIUM
We delegate context management to the CLI subprocess, which handles its
own compaction. However, we lack:
1. Mode-line display of token usage / context pressure
2. Ability to trigger =/compact= from Emacs when using cmux backend
3. Session-level token cost tracking displayed in org properties

*** Concrete first step
Add a mode-line segment showing approximate token usage from the CLI's
stream-json =usage= events. The data is already available in our JSON
stream parser; we just discard it.

*** Files that would change
- =claude-agent-backend.org= (parse and store usage events)
- =claude-agent.org= (mode-line display section)
- =claude-org-session.org= (add token-usage field to session state)

** 1.2 Error Recovery and Retry Logic

*** What Claude Code does
Claude Code implements a 3-layer defense (doc 20):
- =withRetry= as an AsyncGenerator for streaming retry status to UI
- Exponential backoff with jitter (base 500ms, max 32s)
- Retry-After header respect
- 529 overload: max 3 retries then model downgrade to fallback
- Context overflow: automatic output token reduction
- Token expiry: re-authentication mid-session
- Partial streaming: resume from last complete tool call

*** Why it matters for emacs-cmux
Our =claude-agent-auto-recovery= handles process crashes by resuming
sessions, but we have no retry logic for transient API errors. When the
CLI subprocess hits a 529 or network timeout, it exits and our sentinel
sees a non-zero exit code. We treat all abnormal exits the same way:
insert a warning and optionally resume. We lack:
1. Distinction between retryable vs fatal errors
2. Display of retry progress to the user
3. Graceful degradation (e.g., model fallback)

*** Gap assessment: SMALL (CLI handles most retries internally)
Since we primarily use Claude Code CLI as a subprocess, and the CLI has
its own internal retry logic, this gap is smaller than it appears. The
main improvement would be better error classification in our sentinel.

*** Concrete first step
Parse the CLI's exit code and last JSON message to classify exits into
categories: =api-overload=, =context-overflow=, =auth-expired=, =crash=.
Display appropriate messages and auto-resume only for transient errors.

*** Files that would change
- =claude-agent-backend.org= (sentinel error classification)
- =claude-org.org= (user-facing error messages)

** 1.3 Slash Command Integration

*** What Claude Code does
Claude Code has a unified command system (doc 11) with 6 sources:
- Built-in commands (=/clear=, =/compact=, =/cost=, =/config=)
- User skills (=.claude/skills/=)
- Plugin commands
- Bundled skills
- MCP skills
- Workflow commands

All unified under =CommandBase= type with =PromptCommand=, =LocalCommand=,
and =LocalJSXCommand= execution models.

*** Why it matters for emacs-cmux
Our =claude-org= has =claude-org-slash-commands= (customization variable)
and file-based prompt templates (=prompts/tags/=). But we lack:
1. Dynamic discovery of =.claude/skills/= directory
2. Completion/typeahead for available commands
3. Ability for users to define new commands via markdown files

*** Concrete first step
Implement completion for our existing slash commands in =claude-org-execute=.
Currently commands are plain strings; add a completing-read interface.

*** Files that would change
- =claude-org.org= (slash command section, prompt template loader)

* Priority 2: Strategic Investments (M effort, high impact)

** 2.1 Multi-Agent / Subagent Architecture

*** What Claude Code does
Claude Code has a sophisticated agent system (docs 12-14):
- =AgentDefinition= with 3 types: built-in, custom, plugin
- =runAgent()= lifecycle: spawn subprocess, manage context, collect result
- =createSubagentContext()= for state isolation
- 6 built-in agents: General-purpose, Explore, Plan, Guide, Verification
- Agent memory with 3 scopes: user, project, local
- Concurrent task system with 7 task types
- Context isolation: clone mutable state, share infrastructure

*** Why it matters for emacs-cmux
Our system runs one Claude Code instance per cmux workspace, with one
active query per session. For complex tasks, users manually create
multiple org sections. We lack:
1. Ability to spawn subagents from within a running session
2. Explore-style read-only agents for codebase navigation
3. Verification agents that check work without modifying files
4. Parallel agent execution for independent subtasks

*** Gap assessment: LARGE
This is the biggest architectural gap. Claude Code's multi-agent system
enables division of labor, context isolation, and parallel exploration.
Our org-mode structure partially compensates (separate sections act as
separate contexts), but we have no programmatic subagent spawning.

*** Concrete first step
Design an =agent-dispatch= mechanism where an AI block can contain a
tag like =:agent explore= that spawns a separate Claude Code process
with restricted tool access and returns results as a nested org section.
The dispatch could reuse our existing cmux workspace infrastructure.

*** Files that would change
- =claude-org.org= (new agent dispatch in execution flow)
- =claude-org-cmux.org= (spawn agent in new tab/pane)
- =claude-org-session.org= (track agent parent-child relationships)
- New: =claude-org-agent.org= (agent definition, lifecycle)

** 2.2 Hooks / Lifecycle Events System

*** What Claude Code does
Claude Code defines 27 lifecycle events (doc 18):
- Tool lifecycle: =PreToolUse=, =PostToolUse=, =PostToolUseFailure=
- Session lifecycle: =SessionStart=, =SessionEnd=, =Stop=
- Agent collaboration: =SubagentStart=, =SubagentStop=
- Context management: =PreCompact=, =PostCompact=
- Environment: =FileChanged=, =CwdChanged=, =ConfigChange=

Users configure hooks in =settings.json= with event/matcher/command triples.
Hooks execute shell commands and can influence AI behavior (e.g., inject
linting results after file writes).

*** Why it matters for emacs-cmux
Our system has Emacs hooks (=claude-org-pre-execute-hook=,
=claude-org-post-execute-hook=, etc.) but they are Elisp hooks, not
shell command hooks. We have no way to:
1. Run shell commands before/after tool use
2. Inject automated checks (lint, format) after file modifications
3. Trigger custom actions on session lifecycle events
4. Configure hooks via settings files (our hooks require Elisp)

*** Gap assessment: MEDIUM
Emacs hooks are actually more powerful than shell command hooks for
Emacs users. But the ability to configure hooks declaratively (without
writing Elisp) is valuable for team-shared configurations. The
=settings.json= approach of Claude Code allows non-Emacs-experts to
add project-level automation.

*** Concrete first step
Bridge our Emacs hooks to also support =.claude/settings.json= hook
configurations. When we launch a Claude Code subprocess, pass through
the hook settings so the CLI handles them natively.

*** Files that would change
- =claude-org.org= (hook bridge, settings loading)
- =claude-org-cmux.org= (pass hook config to workspace)

** 2.3 Prompt Cache Optimization

*** What Claude Code does
Prompt caching is a cross-cutting concern (doc 07):
- System prompt split into static/dynamic segments
- =SYSTEM_PROMPT_DYNAMIC_BOUNDARY= marker separates cacheable prefix
- =cache_control= with =global= and =org= scopes
- Tool schemas sorted by name for byte stability
- Messages: cache breakpoint on last N user messages
- Fork agents share cache parameters (=CacheSafeParams=)
- =DANGEROUS_uncachedSystemPromptSection()= for volatile content

*** Why it matters for emacs-cmux
When we use the JSON stream backend (direct API), we construct system
prompts from behavior tags, context, and user instructions. We do not
optimize for prompt cache stability:
1. Tool lists may be in different order between calls
2. Dynamic context (timestamps, git status) is mixed with static rules
3. No =cache_control= markers in our API calls

*** Gap assessment: MEDIUM-LOW (mostly relevant for direct API usage)
When using cmux with Claude Code CLI, the CLI handles its own prompt
caching. This gap matters only for our JSON stream backend path. But
as we build more features on the direct API path, this will matter.

*** Concrete first step
When constructing system prompts for JSON stream queries, separate
static sections (behavior tags, tool descriptions) from dynamic
sections (timestamps, file context), and mark the boundary.

*** Files that would change
- =claude-org.org= (system prompt assembly in behavior prompts section)
- =claude-agent-backend.org= (API request construction)

** 2.4 Memory System Architecture

*** What Claude Code does
Five-layer memory architecture (doc 23):
1. =CLAUDE.md= instruction files (static, hierarchical discovery)
2. Auto Memory (=memdir=): AI auto-extracts persistent knowledge
3. Session Memory: structured notes for current session
4. Agent Memory: per-agent persistent storage (3 scopes)
5. Relevant Memories: per-turn injection via similarity search

Key features:
- =CLAUDE.md= traversal from CWD upward to root
- =@include= directive for modular instruction files
- Auto-memory uses AI to extract lessons from conversations
- Session memory survives compact operations

*** Why it matters for emacs-cmux
Our system has =CLAUDE.md= support (via Claude Code CLI) and Emacs MEMORY.md
(via =~/.claude/projects/= structure). But we lack:
1. Per-session memory that survives context compaction
2. AI-driven auto-extraction of lessons from sessions
3. Memory injection based on relevance to current query
4. Per-agent memory scopes

*** Gap assessment: MEDIUM
We partially compensate via org properties (=CLAUDE_SESSION_ID=,
=CLAUDE_CLI_SESSION=) which persist session identity. The org file
itself is a form of persistent memory. But automated knowledge
extraction from sessions would be valuable.

*** Concrete first step
After session completion, offer to append key learnings to the project's
=tasks/lessons.md= file (we already have this convention). Automate
the extraction by passing the session transcript to a summarization query.

*** Files that would change
- =claude-org.org= (post-session hook for lesson extraction)
- =claude-org-session.org= (session transcript collection)

* Priority 3: Nice-to-Have (any effort, medium impact)

** 3.1 Thinking/Effort Control

*** What Claude Code does
Four-level effort control (doc 08):
- =ThinkingConfig=: =adaptive= / =enabled + budgetTokens= / =disabled=
- Effort levels: =low= / =medium= / =high= / =max=
- =ultrathink= keyword triggers maximum thinking
- Per-agent effort configuration

*** Why it matters for emacs-cmux
We pass =--thinking= flag to Claude Code CLI but have no granular
control. Users cannot adjust effort level per-block or per-session.

*** Concrete first step
Add an org property =THINKING_EFFORT= (low/medium/high/max) that maps
to the appropriate CLI flags or API parameters.

*** Files that would change
- =claude-org.org= (property reading, CLI arg construction)

** 3.2 Permission Mode Cycling

*** What Claude Code does
Seven permission modes with Shift+Tab cycling (doc 16):
=default= / =plan= / =acceptEdits= / =bypassPermissions= / =dontAsk=
plus internal =auto= and =bubble= modes.

7-step permission decision pipeline with deny-first semantics,
bypass-immune safety checks, and denial tracking with circuit breaker.

*** Why it matters for emacs-cmux
We have =claude-org-permission-mode= and =claude-agent-permission.org=
with pattern-based allow/deny. But we lack:
1. Easy mode cycling from within an AI block
2. Per-block permission mode override
3. Circuit breaker for repeated denials

*** Concrete first step
Add an org property =PERMISSION_MODE= that overrides the session default.
Add a keybinding in =claude-org-mode-map= to cycle modes.

*** Files that would change
- =claude-org.org= (property reading, permission mode dispatch)
- =claude-agent-permission.org= (circuit breaker logic)

** 3.3 Multi-Layer Settings System

*** What Claude Code does
5+1 layer settings with clear priority chain (doc 17):
Plugin base -> User -> Project -> Local -> Flag -> Policy (highest)
With security boundaries: project-level settings untrusted for
high-risk operations (env var injection).

*** Why it matters for emacs-cmux
Our configuration is via Emacs =defcustom= variables. We lack:
1. Project-level settings (=.claude/settings.json= reading)
2. Priority merge across configuration layers
3. Enterprise policy enforcement

*** Concrete first step
Read =.claude/settings.json= from the project root and apply relevant
settings (allowed-tools, permission-mode, system-prompt additions) to
the current session.

*** Files that would change
- =claude-org.org= (settings file discovery and loading)

** 3.4 Token Usage and Cost Display

*** What Claude Code does
Tracks and displays (doc 03, state management):
- =totalCostUSD=: running cost for the session
- =totalAPIDuration=: cumulative API call time
- =modelUsage=: per-model token consumption
- =/cost= command to show session costs

*** Why it matters for emacs-cmux
We have no cost visibility. Users cannot see how much a session costs
or how many tokens have been consumed.

*** Concrete first step
Parse token usage from CLI stream events (=usage= field in JSON stream
messages) and display in the Emacs mode-line or as an org property.

*** Files that would change
- =claude-agent-backend.org= (usage event parsing)
- =claude-agent.org= (mode-line section)
- =claude-org-session.org= (token-usage tracking)

** 3.5 Task / Background Agent System

*** What Claude Code does
Unified task framework (doc 14):
- 7 task types: LocalShell, LocalAgent, RemoteAgent, Dream, Workflow...
- =registerTask=, =updateTaskState=, =pollTasks=, =evictTerminalTask=
- Disk-based task output (=DiskTaskOutput=, =appendTaskOutput=)
- Status tracking: pending -> running -> completed/failed/killed
- UI integration: status bar showing active background tasks

*** Why it matters for emacs-cmux
Our cmux workspaces can have multiple tabs, but we have no formal
task tracking. We cannot display "2 agents running, 1 shell task"
in the mode-line.

*** Concrete first step
Track active cmux tabs per workspace and display count in mode-line.
Use cmux CLI =tree= command to enumerate active sessions.

*** Files that would change
- =claude-org-cmux.org= (workspace state querying)
- =claude-agent.org= (mode-line display)

* Priority 4: Future Consideration (L effort, any impact)

** 4.1 Tool System with Builder Pattern

Claude Code's =buildTool()= pattern with 30+ interface methods, Zod
schema validation, and ToolSearch lazy loading (doc 09) is deeply tied
to their TypeScript/React architecture. Our MCP server (=emacs-mcp-server.org=)
provides tool registration via =emacs-mcp-server-register-tool=, which
is simpler but sufficient for our use case.

** 4.2 Terminal UI Framework (Ink/React)

Claude Code's forked Ink framework with custom reconciler, Yoga layout,
double-buffered rendering, virtual scrolling, and mouse events (docs 21-22)
is irrelevant to us. Emacs IS our UI framework, and it is far more
capable than any terminal UI library.

** 4.3 Startup Optimization (Fast Paths, DCE)

Claude Code's multi-layer startup optimization (doc 02) with fast paths,
side-effect hoisting, and dead code elimination is specific to their
TypeScript/Bun toolchain. Our startup is Emacs loading literate-elisp
files, which is a fundamentally different paradigm. =autoload= and
=eval-after-load= are our equivalents.

** 4.4 Feature Flags / A-B Testing

Claude Code uses compile-time =feature()= for product variants and
GrowthBook for runtime A/B testing (doc 19). We have no equivalent,
but we also do not ship multiple product variants. If needed, Emacs
=defcustom= with feature-gating is our approach.

** 4.5 Design System / Theme

Claude Code's 80+ semantic color tokens, 6 themes, and Agent color
palette (doc 22) serve their terminal UI. Our theming is handled by
Emacs faces and org-mode fontification, which users customize via
their Emacs theme.

** 4.6 Coordinator / Multi-Worker Mode

Claude Code has an experimental Coordinator mode where a lead agent
dispatches work to multiple Worker agents running in parallel, possibly
in separate worktrees or remote machines. This is a large-scale feature
that could eventually be interesting for distributed Emacs-based agent
workflows, but is premature for our current scale.

* Things We Do Better

** Persistent Workspace State

Our org-mode structure provides something Claude Code completely lacks:
*persistent, structured, human-readable workspace state*. Every AI
interaction is recorded in the org file with properties, timestamps,
and hierarchical context. Claude Code's session state is ephemeral
(in-memory =AppState= plus JSON session files). Our approach means:
- Sessions are resumable by construction (just re-read the org file)
- History is navigable with standard org-mode folding
- Multiple sessions coexist in a single document with clear boundaries
- Human annotations interleave naturally with AI responses

** Literate Programming Architecture

Our entire codebase is literate org files. This means:
- Code and documentation are always in sync
- Module boundaries are enforced by org headings
- The reading order IS the dependency order
- New contributors can read the system as a narrative
- Claude Code's =main.tsx= (4683 lines) would be unthinkable in our style

** cmux Workspace Multiplexing

Our cmux backend provides genuine terminal workspace multiplexing that
Claude Code does not offer to end users:
- Multiple named workspaces with persistent tabs
- Each workspace has its own Claude Code session, file context, terminal
- Workspaces survive Emacs restarts (state in cmux process)
- Per-workspace agent type selection (Claude, Copilot, custom)
- Sidebar API for workspace management

** MCP Server as First-Class Citizen

Our =emacs-mcp-server.org= runs as a genuine HTTP MCP server inside
Emacs, exposing =evalElisp= and registered tools to Claude Code. This
means Claude Code can read Emacs state, navigate buffers, execute Elisp,
and inspect variables. Claude Code's own MCP implementation is
client-only; it consumes MCP servers but does not itself expose tools
to other agents in the same way.

** Backend Protocol Abstraction

Our =claude-agent-backend.org= defines a =cl-defgeneric= protocol for
backend communication. We currently have two backends (JSON stream, CLI
terminal) and can add more without touching the core. Claude Code's
=query.ts= is monolithic and tightly coupled to the Anthropic API client.

** OpenTelemetry Tracing

Our =claude-agent-trace.org= provides OTel tracing for every AI block
execution, with spans visible in Phoenix UI. This gives us observability
into the full execution lifecycle. While Claude Code has analytics and
telemetry, its tracing is oriented toward internal metrics rather than
user-visible debugging.

** Org Property Configuration

Our per-section org properties (=CLAUDE_BACKEND=, =PERMISSION_MODE=,
=CLAUDE_SESSION_ID=, =AGENT_TYPE=, =CMUX_VERSION=, =SYSTEM_PROMPT=)
provide fine-grained per-block configuration that Claude Code handles
only at the session level. A single org file can have blocks with
different backends, models, permission modes, and agent types.

** Queue and Concurrent Block Execution

Our =claude-org-queue.org= implements a block execution queue where
multiple AI blocks can be queued and executed sequentially without user
intervention. Claude Code's REPL is single-threaded in its user
interaction model.
