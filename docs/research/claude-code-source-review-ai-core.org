* Overview

This document distills actionable improvements for the emacs-cmux system
from a detailed study of the Claude Code CLI source code. The reviewed
documents cover:

- Doc 04: System Prompt engineering -- segmented construction, static/dynamic boundary, cache-aware design
- Doc 05: Conversation loop -- AsyncGenerator query loop, message preprocessing pipeline, error recovery
- Doc 06: Context management -- token budgets, multi-level compaction (microcompact, full compact), file state cache
- Doc 07: Prompt cache -- cache_control placement, CacheSafeParams for fork agents, byte-exact prompt threading
- Doc 08: Thinking and reasoning control -- ThinkingConfig modes, effort levels, ultrathink keyword, advisor tool

Each finding maps a Claude Code technique to a concrete opportunity in our
Emacs-based system, where we use Claude Code CLI as the AI backend (not the
direct API).

** Our Architecture Context

Our system does not call the Anthropic API directly. Instead:

1. Emacs builds a system prompt from =prompts/system/*.org= files plus
   =:system_prompt:= tagged org sections, appending line-width and
   elisp-reload hints.
2. The combined prompt is passed as =--system-prompt= to Claude Code CLI.
3. IDE context (current buffer, selection, open files) is prepended to
   the user prompt as a system-reminder block.
4. Claude Code CLI owns the full conversation loop, context management,
   prompt caching, and thinking configuration internally.

This means many of Claude Code's internal mechanisms (token budgets,
microcompact, cache_control placement) operate transparently beneath us.
Our leverage points are: the system prompt we construct, the CLI flags and
environment variables we set, and the UX patterns we implement on top.

* Findings

** Finding 1: Segmented System Prompt with Stable Prefix Ordering

- *Source*: 04-System-Prompt-工程.md, section 一 "整体架构：分段组装的 System Prompt"
- *Claude Code approach*: =getSystemPrompt()= returns a =string[]= array,
  not a single string. The array is split into a *static segment*
  (identity, safety, tool usage, tone -- identical for all users) and a
  *dynamic segment* (environment info, MCP instructions, language
  preferences) separated by =SYSTEM_PROMPT_DYNAMIC_BOUNDARY=. The static
  prefix gets =cacheScope: 'global'=, enabling cross-user cache sharing.
  Within each segment, sections are ordered by stability: the most stable
  content (identity definition, security instructions) comes first, and
  the most volatile (MCP instructions -- the only =DANGEROUS_uncached=
  section) comes last.
- *Our current state*: =claude-org--build-system-prompt= concatenates all
  prompt parts into a single string with =string-join=. The ordering is:
  1. File prompts from =prompts/system/*.org= (=00-base.org=, =10-links.org=,
     =20-literate-elisp.org=)
  2. Org =:system_prompt:= sections from the current file
  3. Line-width hint (dynamic -- depends on =claude-org-line-width=)
  4. Elisp reload hint (static)
  The static elisp reload hint comes after the dynamic line-width hint,
  which is suboptimal for cache stability.
- *Opportunity*: Reorder our system prompt segments by stability.
  Move the elisp reload hint (always identical) into =prompts/system/=
  as a numbered file (e.g., =05-elisp-reload.org=) so it stays in the
  stable prefix. The line-width hint should come after all static content
  since it varies per user. This costs nothing but improves prompt cache
  hit rates inside Claude Code CLI because the stable prefix is longer.
  Consider also numbering the current =:system_prompt:= org sections
  after all file prompts so the file-based static content forms a
  predictable, cacheable prefix.
- *Effort*: S
- *Impact*: medium (longer stable prefix means better prompt cache hits
  inside Claude Code, reducing API cost and latency)

** Finding 2: IDE Context as User Message, Not System Prompt

- *Source*: 04-System-Prompt-工程.md, section 三 "Context 层"; 07-Prompt-Cache.md, section 四
- *Claude Code approach*: Claude Code splits context injection into two
  layers. =systemContext= (git status, agent rules) is appended to the
  system prompt. =userContext= (CLAUDE.md content, current date) is
  prepended to the user message, deliberately kept out of the system
  prompt. The rationale: CLAUDE.md content is long and varies per project,
  putting it in the system prompt would destroy cache hit rates. By
  injecting it as the first user message, the system prompt prefix stays
  cacheable.
- *Our current state*: We build an IDE context reminder (current file,
  open files, selection, cwd) via =claude-agent-build-system-reminder= and
  prepend it directly to the user prompt string in
  =claude-org--build-full-prompt=. This is conceptually correct -- it goes
  into the user message, not the system prompt. However, we also inject
  =:system_prompt:= org sections (which are per-file dynamic content) into
  the system prompt string itself, before the line-width hint.
- *Opportunity*: Evaluate whether per-file =:system_prompt:= content
  should be moved from the =--system-prompt= CLI flag to being prepended
  to the user prompt (like IDE context). Per-file system prompts change
  every time the user opens a different org file, which destabilizes the
  system prompt prefix inside Claude Code. Moving them to user-message
  context would preserve system prompt cache hits across files.
  Counterargument: system prompts carry stronger instruction-following
  weight when placed in the system prompt position. This is a tradeoff
  worth testing with A/B measurement of cache hit rates.
- *Effort*: M (requires measuring cache hit impact, may need split-prompt
  approach)
- *Impact*: medium (potentially large cost savings for multi-file workflows)

** Finding 3: Environment Variables for Context Window Tuning

- *Source*: 06-上下文管理.md, section 一 "Token 预算管理"
- *Claude Code approach*: Three env vars control context management:
  - =CLAUDE_CODE_AUTO_COMPACT_WINDOW= -- override effective context window
    size (useful for testing, or forcing earlier compaction)
  - =CLAUDE_AUTOCOMPACT_PCT_OVERRIDE= -- set auto-compact threshold as a
    percentage of effective window
  - =CLAUDE_CODE_UNATTENDED_RETRY= -- enable infinite retry mode with
    5-minute max backoff for unattended sessions
  Auto-compact triggers at =effectiveWindow - 13K= tokens by default.
  When triggered, Claude Code uses either Session Memory (if available,
  zero API cost) or a full model-driven compact (one API call for a
  structured 9-dimension summary).
- *Our current state*: We pass no environment variables related to context
  window management. Long org-mode sessions with many ai blocks rely
  entirely on Claude Code's defaults for when compaction triggers.
- *Opportunity*: Expose context management controls as org properties or
  defcustom variables:
  1. =CLAUDE_COMPACT_WINDOW= org property mapped to
     =CLAUDE_CODE_AUTO_COMPACT_WINDOW= env var -- lets users with smaller
     models or cost-sensitive workflows trigger compaction earlier.
  2. For SDD (story-driven development) sessions that run unattended,
     set =CLAUDE_CODE_UNATTENDED_RETRY=1= in the =:env= plist passed to
     =claude-agent-options=. This prevents 429/529 errors from killing
     automated workflows.
  3. Consider adding a =claude-org-compact-threshold= defcustom that
     translates to =CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=, defaulting to nil
     (use CLI defaults).
- *Effort*: S (just passing env vars through existing =:env= mechanism)
- *Impact*: medium (prevents session failures in long-running workflows,
  gives users control over cost/context tradeoff)

** Finding 4: Thinking and Effort Control via CLI Flags

- *Source*: 08-Thinking-与推理控制.md, sections 一-三
- *Claude Code approach*: Three independent control surfaces for reasoning:
  1. *ThinkingConfig*: =--thinking adaptive|enabled|disabled= CLI flag,
     or =MAX_THINKING_TOKENS= env var. Adaptive (default for 4.6+) lets
     the model decide how much to think. Enabled with budget forces a
     fixed thinking token allocation.
  2. *Effort*: =low|medium|high|max= levels via =/effort= command or
     =CLAUDE_CODE_EFFORT_LEVEL= env var. Controls model reasoning depth
     independently of thinking. =max= only works on Opus 4.6.
  3. *Ultrathink*: When user types "ultrathink" anywhere in their prompt,
     effort is bumped to =high= for that turn via an attachment mechanism.
     Default effort with ultrathink enabled is =medium=, so ultrathink
     keyword provides a per-turn override.
  Key design: thinking and effort are *independent* API parameters.
  Thinking controls the Extended Thinking feature (chain-of-thought
  reasoning blocks). Effort controls how much computational effort the
  model invests per response. Both can be set simultaneously.
- *Our current state*: We pass no thinking or effort flags to Claude Code
  CLI. The CLI's defaults apply: thinking enabled (adaptive for 4.6+
  models), effort determined by model defaults.
- *Opportunity*: Add per-block and per-session reasoning control:
  1. Support an =:effort:= org property at the workspace or story level
     that maps to =CLAUDE_CODE_EFFORT_LEVEL= env var. This lets users mark
     architectural stories as =high= effort and routine tasks as =low=.
  2. Support =#+begin_src ai :effort high= block-level header args that
     temporarily set the effort env var for that single query. This
     mirrors Claude Code's per-turn ultrathink but with explicit control.
  3. Consider supporting =:thinking:= property (=adaptive=, =disabled=,
     or a numeric budget) that maps to =--thinking= CLI flag or
     =MAX_THINKING_TOKENS= env var. Disabling thinking for quick
     questions can significantly reduce latency and cost.
  4. Detect the word "ultrathink" in ai block content and display a
     visual indicator (e.g., mode-line flash or echo area message) to
     mirror Claude Code's UX feedback.
- *Effort*: M (need header-arg parsing, env var injection, UX feedback)
- *Impact*: high (direct control over latency/cost/quality tradeoff per
  task; key differentiator for power users)

** Finding 5: Multi-Level Compaction Strategy Awareness

- *Source*: 06-上下文管理.md, sections 二-三
- *Claude Code approach*: Context management uses a pressure gradient with
  5 levels, from cheapest to most expensive:
  1. *Time-based microcompact*: When cache is cold (>5 min idle), replace
     old tool results with =[cleared]= text. Zero API cost.
  2. *Cached microcompact*: When cache is warm, use =cache_edits= API to
     delete tool results server-side without modifying local messages.
  3. *Session Memory compact*: Use asynchronously-extracted session memory
     as the summary. Zero API cost (memory was already being extracted).
  4. *Full compact*: Call model to generate a structured 9-dimension
     summary using =<analysis>= + =<summary>= chain-of-thought-then-strip
     technique. One API call.
  5. *Blocking*: Refuse new queries, require manual =/compact=.
  Circuit breaker: 3 consecutive compact failures triggers a fuse that
  stops all compact attempts (saves 250K API calls/day globally).
  Post-compact recovery: restores up to 5 recently-read files (max 5K
  tokens each) and active plan/skill attachments.
- *Our current state*: We rely entirely on Claude Code CLI's internal
  compaction. We have no visibility into when compaction occurs or what
  was lost. After a compact, the model may lose awareness of our org file
  structure, current heading hierarchy, or session-specific context that
  was in the conversation but not in the system prompt.
- *Opportunity*: Add post-compact context recovery at the Emacs layer:
  1. Listen for compact events in the Claude Code streaming output (the
     CLI emits system messages when compaction occurs). When detected,
     re-inject critical context in the next query: current org heading
     path, active session properties, recently referenced custom-IDs.
  2. Ensure that truly critical context lives in the =:system_prompt:=
     sections (which survive compaction because they are re-sent with
     every query), not just in conversation history. Audit what
     information is in the system prompt vs. what is only in the
     conversation.
  3. Consider implementing a "session memory" org section that
     accumulates key decisions and facts during a session, analogous to
     Claude Code's Session Memory system. This section could be
     maintained via a post-turn hook that asks the model to update it.
- *Effort*: L (compact event detection needs streaming protocol analysis;
  session memory is a significant feature)
- *Impact*: high (context loss after compaction is the #1 cause of
  degraded responses in long sessions)

** Finding 6: Structured Compact Summary Prompt Design

- *Source*: 06-上下文管理.md, section 三.4 "Compact Prompt"
- *Claude Code approach*: The compact prompt requires the model to
  summarize along 9 structured dimensions: Primary Request and Intent,
  Key Technical Concepts, Files and Code Sections, Errors and Fixes,
  Problem Solving, All User Messages, Pending Tasks, Current Work, and
  Optional Next Step. The model first writes an =<analysis>= section
  (chain-of-thought draft), then a =<summary>= section. Post-processing
  strips the =<analysis>= to save tokens. A forceful =NO_TOOLS_PREAMBLE=
  prevents the model from attempting tool calls during compaction (failure
  rate rose from 0.01% to 2.79% with Sonnet 4.6).
- *Our current state*: We have no compact prompt customization. Claude
  Code's internal compact prompt is designed for general coding tasks.
  It does not know about our org-mode structure, SDD workflow phases,
  or literate programming conventions.
- *Opportunity*: If/when Claude Code CLI supports compact prompt
  customization (via env var or config), inject org-specific summary
  dimensions. For now, the actionable item is to ensure critical org
  context (current heading path, session ID, active story) is placed in
  the system prompt so it is automatically included in the compact
  prompt context. Claude Code's compact prompt receives the full system
  prompt as part of its input, so anything in our system prompt will
  inform the summary.
- *Effort*: S (audit system prompt content; compact customization is a
  future CLI feature dependency)
- *Impact*: medium (better compact summaries reduce context-loss-related
  errors)

** Finding 7: Prompt Cache Optimization Through Stable System Prompt

- *Source*: 07-Prompt-Cache.md, sections 一-二; 04-System-Prompt-工程.md, section 二
- *Claude Code approach*: Prompt cache is the single most important cost
  optimization. Key design choices:
  1. *Single cache_control marker per request*: Only the last message gets
     =cache_control= -- multiple markers waste KV cache pages.
  2. *Static/dynamic boundary*: =SYSTEM_PROMPT_DYNAMIC_BOUNDARY= splits
     the system prompt so static content gets global cache scope.
  3. *DANGEROUS_ naming convention*: Any section that breaks cache must
     use =DANGEROUS_uncachedSystemPromptSection()= with a mandatory
     reason string. Only one such section exists (MCP instructions).
  4. *Latch pattern for TTL*: Cache TTL eligibility is latched per
     session to prevent mid-session TTL flips that would invalidate
     cached content.
  5. *Byte-exact fork prompt threading*: Fork subagents reuse the
     parent's already-rendered system prompt bytes rather than
     regenerating, to guarantee identical cache keys.
- *Our current state*: Our system prompt is a single concatenated string
  passed via =--system-prompt= to the CLI. Every query in a session gets
  the same system prompt (it is built once per =claude-org--send-request=
  call). However, if =claude-org-line-width= or =:system_prompt:=
  content changes between queries, the system prompt changes and cache
  is busted.
- *Opportunity*: Maximize system prompt stability:
  1. *Cache the built system prompt per session* rather than rebuilding
     every query. Store it in the session state on first build, reuse for
     subsequent queries in the same session. Only rebuild on =/clear= or
     explicit user action.
  2. *Order by stability*: Move all static content (base prompt, links,
     literate-elisp, elisp-reload hint) before all dynamic content
     (per-file system_prompt sections, line-width). This is essentially
     Finding 1 applied from the cache perspective.
  3. *Avoid unnecessary rebuilds*: The line-width hint should only be
     included if it actually changed from the default. Similarly, the
     elisp reload hint is always the same string -- consider inlining it
     into =00-base.org= to reduce concatenation overhead.
- *Effort*: S (reorder + session-level cache of built prompt)
- *Impact*: high (prompt cache is 90% cost reduction on repeated prefixes;
  every instability in our system prompt costs real money)

** Finding 8: Conversation Loop Error Recovery Patterns

- *Source*: 05-对话循环.md, sections 五
- *Claude Code approach*: The conversation loop implements 7 layers of
  error recovery:
  1. *Fallback model*: After 3 consecutive 529 (overloaded) errors, switch
     to a fallback model. Strip thinking signature blocks to prevent
     cross-model 400 errors.
  2. *Prompt-too-long 3-level recovery*: (a) drain context collapse
     summaries, (b) reactive compact, (c) surface error.
  3. *Max-output-tokens 2-phase recovery*: (a) escalate from 8K to 64K
     limit, (b) inject "resume directly -- no apology, no recap" message
     and retry up to 3 times.
  4. *Withholding*: Recoverable errors are withheld from the caller until
     recovery is attempted. If recovery succeeds, the caller never sees
     the error.
  5. *Persistent retry mode*: For unattended sessions, 429/529 errors
     retry indefinitely with exponential backoff up to 5 minutes, with
     30-second heartbeat messages.
- *Our current state*: We handle errors at the Emacs layer: the
  =:on-error= callback receives errors from the CLI and displays them.
  We have no automatic recovery logic -- if the CLI reports an error,
  the session stops. We do have query queuing (block B waits for block A),
  but no retry or fallback mechanisms.
- *Opportunity*: Implement lightweight recovery at the Emacs layer:
  1. *Auto-retry on transient errors*: When =:on-error= receives a
     rate-limit or overload error, wait with exponential backoff and
     retry the query automatically (configurable max retries via
     defcustom). Display a mode-line indicator during retry wait.
  2. *Output truncation recovery*: When the response appears truncated
     (ends mid-sentence without a natural stopping point), auto-send a
     follow-up "continue" query. This is simpler than Claude Code's
     internal mechanism but achieves the same user-facing result.
  3. *Error withholding*: Buffer the first error from a query. If a
     retry succeeds within the timeout, discard the error. Only surface
     errors to the user after all recovery attempts fail.
  Note: Many of these recoveries happen inside the CLI already. The key
  question is which errors escape the CLI and reach us. Testing with
  artificially small context windows (=CLAUDE_CODE_AUTO_COMPACT_WINDOW=)
  would reveal which error paths we need to handle.
- *Effort*: M (retry logic, mode-line indicators, error buffering)
- *Impact*: medium (reduces user-visible errors, especially in long
  sessions and high-load periods)

** Finding 9: Message Preprocessing Pipeline Ordering

- *Source*: 05-对话循环.md, section 三 "消息预处理管线"
- *Claude Code approach*: Before each API call, messages pass through a
  5-stage preprocessing pipeline in strict order:
  1. =applyToolResultBudget()= -- clip oversized tool results
  2. =snipCompact= -- trim old history
  3. =microcompact= -- clear old tool results (cheapest)
  4. =contextCollapse= -- collapse sections of history (moderate)
  5. =autocompact= -- full model-driven compact (expensive)
  The ordering principle: cheapest operations first, so expensive
  compaction only triggers when cheaper methods are insufficient. Each
  stage can short-circuit the need for later stages.
- *Our current state*: We send full prompts to the CLI without any
  preprocessing. The CLI handles its own pipeline internally. Our only
  "preprocessing" is building the system reminder from IDE context, which
  adds a few hundred tokens per query.
- *Opportunity*: Implement a lightweight prompt-side preprocessing:
  1. *IDE context budget*: Cap the IDE context reminder (open files list,
     selection text) to a token budget. If a user has 50 open buffers or
     selects 500 lines of code, the context can become very large. Set
     =claude-org-ide-context-max-tokens= (default: 2000) and truncate
     open-files list and selection text to fit.
  2. *History-aware context*: When resuming a long session (many queries
     in the same org file), the conversation history already contains
     the org file structure. Avoid re-sending redundant context (like
     the full list of open files) if it hasn't changed since the last
     query.
  3. *Prompt size estimation*: Before sending, estimate the prompt size
     (rough character count / 4 as token approximation). If the prompt
     plus estimated system prompt exceeds a configurable threshold, warn
     the user in the echo area.
- *Effort*: S-M (context budgeting is straightforward; history awareness
  requires tracking previous context state)
- *Impact*: low-medium (prevents pathological cases where large IDE
  context wastes context window budget)

** Finding 10: Structured System Prompt Sections Pattern

- *Source*: 04-System-Prompt-工程.md, sections 四.1-四.4
- *Claude Code approach*: The system prompt encodes specific behavioral
  guidance through distinct, purpose-built sections:
  1. *Security*: 4-layer defense (cyber risk instruction, URL generation
     limits, prompt injection detection, operational safety guidelines)
  2. *Anti-over-engineering*: Explicit instructions against unnecessary
     refactoring, excessive error handling, premature abstraction, and
     over-commenting
  3. *Tool priority*: "Use FileRead instead of cat, FileEdit instead of
     sed" -- prefer purpose-built tools over BashTool
  4. *False-claim mitigation*: "Report outcomes faithfully; never claim
     all tests pass when output shows failures" (added when Capybara v8
     false-claim rate rose from 16.7% to 29-30%)
  5. *Output efficiency*: Inverted pyramid structure, assume reader may
     have left, write for cold pickup
- *Our current state*: Our =00-base.org= system prompt covers org-mode
  formatting, sandbox vs host access, and response format. It does not
  include anti-over-engineering guidance, false-claim mitigation, or
  output efficiency directives. We rely on CLAUDE.md for project-specific
  behavioral guidance, but CLAUDE.md is injected by the CLI itself, not
  by our system prompt.
- *Opportunity*: Add behavioral guidance sections to our system prompt
  that complement what Claude Code already provides:
  1. *Org-mode specific anti-patterns*: "Do not generate markdown code
     fences in responses. Do not use ** for bold (use * in org). Do not
     create headings without a space after asterisks." Our base prompt
     already covers some of this, but could be more assertive (Claude
     Code uses "IMPORTANT" and repetition for high-violation-rate rules).
  2. *Literate programming guidance*: "When editing .org literate files,
     verify code is inside #+BEGIN_SRC blocks. Do not insert code between
     #+END_SRC and the next #+BEGIN_SRC." This is partially in
     =20-literate-elisp.org= but could be strengthened with Claude Code's
     proven pattern of explicit anti-examples.
  3. *Verification guidance*: Add a false-claim mitigation instruction
     similar to Claude Code's: "After claiming a fix works, verify by
     running =make test-smoke= via Bash. Do not claim tests pass without
     showing output."
- *Effort*: S (adding text to existing prompt files)
- *Impact*: medium (reduces common failure modes that waste human review
  time)

** Finding 11: Advisor-Style Escalation for Complex Tasks

- *Source*: 08-Thinking-与推理控制.md, section 五 "Advisor"
- *Claude Code approach*: The advisor tool is a server-side mechanism that
  forwards the conversation to a stronger reviewer model. Key design:
  - Advisor is a *server-side tool* -- the main model calls =advisor()=
    like any other tool, and the API server handles forwarding
  - The prompt instructs: "Call advisor BEFORE substantive work -- before
    writing code, before committing to an interpretation"
  - Conflict resolution protocol: "If you have evidence for A and advisor
    says B, initiate a mediation call"
  - Persistence: "Make your deliverable durable before calling advisor --
    write the file, stage the change -- because the call takes time and
    the session may end"
  Currently limited to Opus 4.6 and Sonnet 4.6 models.
- *Our current state*: We have no escalation mechanism. All queries go
  to the same model via the same CLI invocation.
- *Opportunity*: Implement a lightweight advisor pattern at the Emacs
  layer:
  1. *Review block*: Support =#+begin_src ai :review t= header arg that,
     after the main query completes, automatically sends the response to
     a second query with a review prompt: "Review the above response for
     correctness, completeness, and adherence to project conventions."
  2. *Model escalation*: Support =#+begin_src ai :model opus= to use a
     different model for specific blocks, allowing users to escalate
     complex architectural decisions to a stronger model.
  3. *Pre-commit review*: Before =claude-org= marks a session as
     complete (TODO state transition), optionally run a review pass that
     checks for common issues (unclosed code blocks, missing test
     verification, heading format violations).
  These are Emacs-layer patterns that work regardless of whether the CLI
  supports the advisor tool natively.
- *Effort*: L (review block requires second query orchestration; model
  switching needs CLI flag support investigation)
- *Impact*: medium-high (catches errors before they reach the user, but
  doubles API cost for reviewed blocks)

** Finding 12: System Prompt Caching Within Session

- *Source*: 04-System-Prompt-工程.md, section 1.2 "Section 缓存系统"
- *Claude Code approach*: =systemPromptSection()= creates sections that
  are computed once and cached for the entire session. The cache is only
  cleared on =/clear= or =/compact=. =DANGEROUS_uncachedSystemPromptSection=
  forces recomputation every turn (only used for MCP instructions that
  may change between turns due to server connect/disconnect).
  =resolveSystemPromptSections()= checks the cache first and only calls
  =compute()= on cache miss.
- *Our current state*: =claude-org--build-system-prompt= rebuilds the
  entire system prompt on every query (every =claude-org--send-request=
  call). This means:
  - =claude-org--load-system-prompts= re-reads all =prompts/system/*.org=
    files from disk on every query
  - =claude-org--collect-system-prompts= re-scans the buffer for
    =:system_prompt:= tags on every query
  - The result is concatenated fresh each time
  Since the prompt files rarely change during a session, this is wasted
  I/O and string manipulation.
- *Opportunity*: Cache the built system prompt in session state:
  1. On first query in a session, build and store the system prompt in
     the session hash table under =:cached-system-prompt=.
  2. On subsequent queries, return the cached version.
  3. Provide =claude-org-refresh-system-prompt= command (and call it
     automatically after buffer modifications to =:system_prompt:=
     sections) to invalidate the cache.
  4. Clear the cache on session restart or new session creation.
  This is a pure optimization with no behavioral change.
- *Effort*: S (add one hash-table lookup and store)
- *Impact*: low (saves negligible time per query, but establishes the
  right pattern for when system prompt construction becomes more complex)

** Finding 13: Pre-Query Prefetching Pattern

- *Source*: 04-System-Prompt-工程.md, section 七 "预取策略"
- *Claude Code approach*: =startDeferredPrefetches()= fires immediately
  when the REPL renders, before the user types anything. It prefetches
  CLAUDE.md content (=getUserContext()=) and git status
  (=getSystemContext()=) in parallel. By the time the user sends their
  first message, both are already cached.
- *Our current state*: We build system prompt and IDE context lazily at
  query time (inside =claude-org--send-request=). The first query in a
  session pays the full cost of: reading all prompt files, scanning the
  buffer for system_prompt tags, collecting IDE context (buffer list,
  current file), and getting project root.
- *Opportunity*: Prefetch context when the user enters an ai block:
  1. On =org-edit-src-code= or when point enters a =#+begin_src ai=
     block, start prefetching system prompt and IDE context in the
     background using =run-with-idle-timer= or =run-at-time=.
  2. Store prefetched results in buffer-local variables with a timestamp.
  3. At query time, use prefetched results if they are less than 5
     seconds old; otherwise rebuild.
  This mirrors Claude Code's "prefetch while user types" pattern,
  adapted to Emacs's event model.
- *Effort*: M (idle-timer prefetch, staleness checking, buffer-local
  caching)
- *Impact*: low (first-query latency reduction; most of the latency is
  in the CLI startup and API call, not prompt construction)

** Finding 14: Thinking Control via --thinking CLI Flag

- *Source*: 08-Thinking-与推理控制.md, section 1.3
- *Claude Code approach*: The CLI accepts =--thinking adaptive|enabled|disabled=
  and =--max-thinking-tokens N= flags. These directly control the API's
  Extended Thinking feature. For 4.6+ models, =adaptive= is the default
  and recommended mode. Setting =MAX_THINKING_TOKENS=0= disables thinking
  entirely.
  Key insight: =--thinking enabled= actually creates =type: 'adaptive'=
  config internally because adaptive is the superset of enabled for new
  models. The env var =CLAUDE_CODE_DISABLE_THINKING= acts as a kill switch.
- *Our current state*: We do not pass any thinking-related flags or env
  vars to the CLI. We always get the CLI's default thinking behavior.
- *Opportunity*: Add thinking control to our options:
  1. Support =:thinking:= org property at workspace/story level:
     =adaptive= (default), =disabled= (for quick lookups that don't need
     extended reasoning), or a numeric value for token budget.
  2. Map to =MAX_THINKING_TOKENS= env var (0 for disabled, N for budget)
     since this is the simplest env-var-based control.
  3. For quick question patterns (title generation, translation,
     formatting), automatically set =MAX_THINKING_TOKENS=0= to skip
     thinking and reduce latency by 30-50%.
  4. Display thinking status in the mode-line or response header so
     users know when extended thinking is active.
- *Effort*: S (env var passthrough via existing =:env= mechanism)
- *Impact*: medium (significant latency reduction for simple tasks when
  thinking is disabled; cost savings for high-volume automated workflows)

** Recommended Implementation Order

The quickest wins are the S-effort/high-impact items that require only
configuration changes, not code architecture:

1. *Phase 1 -- CLI flag/env var passthrough* (Findings 3, 14, 4):
   Add =:effort=, =:thinking=, and context window properties that map to
   env vars. This unlocks user control over reasoning depth and context
   management with minimal code changes.

2. *Phase 2 -- System prompt optimization* (Findings 1, 7, 12):
   Reorder prompt segments by stability, cache the built prompt per
   session, and inline the elisp reload hint into the base prompt file.

3. *Phase 3 -- Behavioral hardening* (Findings 10, 6, 8):
   Add anti-pattern instructions, verification guidance, and lightweight
   error recovery to reduce failure modes in long sessions.

4. *Phase 4 -- Advanced features* (Findings 5, 11, 2):
   Post-compact context recovery, advisor-style review blocks, and
   IDE context placement optimization. These require deeper integration
   work and should be informed by usage data from Phases 1-3.
