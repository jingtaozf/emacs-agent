#+TITLE: Claude Code Source Review: Tools, Agents & Tasks (Docs 09-15)
#+AUTHOR: Architecture Review
#+DATE: 2026-04-08

* Overview

Analysis of Claude Code internal architecture (docs 09-15) against our
emacs-cmux system.  Each finding identifies a specific pattern from Claude
Code, compares it to our current implementation, and proposes a concrete
improvement.

Scope: tool system design, BashTool security, command/skill extensibility,
agent system, task system, and MCP protocol implementation.

* Findings

** Finding 1: Tool Interface with Fail-Closed Security Defaults

- *Source*: doc 09, section "buildTool() -- Builder Pattern"
- *Claude Code approach*: Every tool implements a 30+ method =Tool= interface.
  =buildTool()= provides safe defaults: =isReadOnly= defaults to =false=
  (assume writes), =isConcurrencySafe= defaults to =false= (assume unsafe).
  Tool authors cannot accidentally leave security holes by forgetting to declare
  a property -- the default is always the most conservative option.
- *Our current state*: =emacs-mcp-server--builtin-tools= is a flat alist with
  name, description, handler, and inputSchema.  There is no metadata for
  read-only, concurrency safety, or destructiveness.  The =evalElisp= tool has
  no formal security classification -- it can do anything.
- *Opportunity*: Add a =build-mcp-tool= constructor that auto-fills security
  metadata.  Each registered tool should declare =:read-only=, =:concurrency-safe=,
  and =:destructive= properties.  The MCP server can use these to make decisions
  about parallel execution and permission checks.  Even if =evalElisp= stays as
  the single tool, future tools (file-read, org-navigate) would benefit from
  structured metadata.
- *Effort*: S
- *Impact*: medium -- establishes the right pattern for when we add more tools

** Finding 2: Command Semantic Classification for evalElisp

- *Source*: doc 10, section "Command Semantics" (BashTool)
- *Claude Code approach*: BashTool classifies commands into search, read, list,
  silent, and destructive categories.  Each category gets different UI treatment
  and security posture.  Exit code semantics (grep returns 1 for "no match",
  not error) prevent the AI from misinterpreting results.
- *Our current state*: =evalElisp= is a single undifferentiated tool.  The AI
  sends arbitrary elisp with no semantic classification.  We have no way to
  distinguish a read-only =buffer-string= call from a destructive
  =(delete-file)= call.
- *Opportunity*: Introduce a lightweight classification layer in the MCP server
  that inspects the top-level form of evalElisp code.  Forms starting with
  =buffer-string=, =point=, =org-entry-get= could be classified as read-only
  and auto-approved.  Forms calling =delete-file=, =kill-buffer=, =save-buffer=
  could be flagged as write operations.  This is not about building a full AST
  analyzer -- a simple prefix/symbol check on the outermost sexp covers the
  80% case for permission auto-approval.
- *Effort*: M
- *Impact*: high -- enables safe auto-approval of read-only elisp, reducing
  permission fatigue

** Finding 3: Multi-Source Command Aggregation with Priority

- *Source*: doc 11, section "Six-Source Aggregation"
- *Claude Code approach*: Commands come from 6+ sources (built-in, user skills,
  plugin skills, MCP skills, bundled skills, workflows) and are merged with
  explicit priority ordering: managed > project > user > plugin > built-in.
  A =loadAllCommands()= function does parallel loading and memoization.
  User-defined skills can override built-in commands.
- *Our current state*: Slash command completion in ai blocks uses company-mode
  with a fixed list.  There is no mechanism for user-defined skills, project-level
  skill directories, or dynamic skill discovery.  The slash commands available
  are whatever Claude Code itself provides -- we do not inject our own.
- *Opportunity*: Create a =.claude/skills/= directory convention at project
  level.  When the MCP server starts, scan for =SKILL.md= files and register
  them as available prompts via the MCP =prompts/list= response (currently
  unused in our server).  The AI would see these as available skills and could
  invoke them.  This leverages the existing MCP prompts capability that our
  server already has a stub for.
- *Effort*: M
- *Impact*: medium -- enables project-specific AI workflows without modifying
  the core codebase

** Finding 4: Agent Context Isolation via createSubagentContext

- *Source*: doc 12, section "Context Isolation" (createSubagentContext)
- *Claude Code approach*: When a parent agent spawns a sub-agent, all mutable
  state is cloned by default.  Only specific state is explicitly shared
  (abort controller, task registration).  The principle is "default isolated,
  opt-in shared."  Key insight: =setAppState= can be a no-op for sub-agents,
  but =setAppStateForTasks= always punches through to the root store (to prevent
  orphaned processes).
- *Our current state*: We run one Claude Code instance per cmux workspace.
  There is no sub-agent spawning from Emacs -- each AI block execution is a
  single agent interaction.  Session state (=claude-org--sessions= hash table)
  is per-buffer, not per-agent.  If Claude Code internally spawns sub-agents
  (via the Agent tool), those run inside the cmux terminal and we have no
  visibility into them.
- *Opportunity*: When we implement multi-workspace orchestration (one org file
  driving multiple cmux workspaces in parallel), adopt the "default isolated"
  pattern for workspace-level state.  Each workspace should have its own copy
  of streaming state, surface IDs, and session keys.  Shared state (like the
  org buffer insertion point, workspace-to-surface mapping) should be explicitly
  marked as shared with appropriate locking.  Concretely: refactor
  =claude-org-cmux--workspace-to-surface= and =claude-org-cmux--workspace-to-cmux-id=
  into a per-workspace state struct instead of global hash tables.
- *Effort*: L
- *Impact*: high -- prerequisite for reliable multi-workspace parallel execution

** Finding 5: Agent Profile System with Tool Constraints

- *Source*: doc 12, sections "BaseAgentDefinition" and "Tool Resolution";
  doc 13, section "Three Tool Constraint Strategies"
- *Claude Code approach*: Agent definitions include =tools= (whitelist),
  =disallowedTools= (blacklist), =permissionMode=, =model=, =maxTurns=, and
  =omitClaudeMd=.  Three strategies exist: whitelist (=tools: [Read, Grep]=),
  blacklist (=disallowedTools: [Edit, Write]=), and wildcard (=tools: ['*']=).
  Each agent can have its own permission mode and model.
- *Our current state*: =claude-org-cmux--agent-profile= struct has =name=,
  =launch-fn=, =ready-patterns=, =busy-patterns=, =cancel-keys=, and boolean
  flags for resume/IDE/system-prompt support.  It describes how to launch and
  detect agent state, but has no concept of tool constraints, permission modes,
  or model selection.  Tool access is entirely controlled by whatever
  =--permission-mode= and =--allowed-tools= flags are passed at launch.
- *Opportunity*: Extend =claude-org-cmux--agent-profile= with:
  - =allowed-tools=: list of MCP tool patterns to pass as =--allowedTools=
  - =permission-mode=: one of =default/plan/acceptEdits/bypassPermissions=
  - =model=: model override or ='inherit=
  - =max-turns=: conversation turn limit

  These fields would be read by =claude-org-cmux--build-*-launch-command= and
  translated into CLI flags.  This lets us define profiles like "read-only
  researcher" (plan mode, no edit tools) or "autonomous implementer" (bypass
  mode, all tools) without changing launch logic.
- *Effort*: S
- *Impact*: high -- enables differentiated agent behaviors from org properties

** Finding 6: Verification Agent Anti-Evasion Prompt Design

- *Source*: doc 13, section "Verification Agent"
- *Claude Code approach*: The Verification Agent uses "meta-cognitive prompting"
  -- it tells the AI about its own common failure modes ("you will feel the
  urge to skip checks") and explicitly debunks rationalizations.  It uses
  =criticalSystemReminder_EXPERIMENTAL= to re-inject constraints on every user
  turn, preventing long-context forgetting.  Output is structured with a
  mandatory VERDICT: PASS/FAIL/PARTIAL format.
- *Our current state*: We pass system prompts to Claude Code via
  =--system-prompt= flag or the SDD workflow hooks.  There is no mechanism to
  re-inject constraints on every turn or to enforce structured output formats.
- *Opportunity*: For verification-style workflows (code review, test validation),
  create a system prompt template that uses the anti-evasion pattern:
  1. State the agent's tendency to rationalize
  2. List specific rationalizations and rebuttals
  3. Require structured output (VERDICT: PASS/FAIL)

  The re-injection can be achieved by adding a =criticalReminder= field to
  the agent profile that gets prepended to every prompt in loop mode.  In
  =claude-org-cmux--loop-send=, if =criticalReminder= is set, prepend it to
  the prompt text.
- *Effort*: S
- *Impact*: medium -- directly improves AI verification quality for SDD workflows

** Finding 7: Task System with Unified Lifecycle

- *Source*: doc 14, sections "Task Interface" and "TaskState"
- *Claude Code approach*: All async work (shell commands, sub-agents, remote
  agents, "dream" memory consolidation) goes through a unified task system
  with 5 states: pending, running, completed, failed, killed.  Tasks are
  registered in AppState, have kill methods, and use a priority message queue
  for notifications.  The Task interface is intentionally minimal -- only
  =kill()= is polymorphic.
- *Our current state*: We have a queue system for AI blocks
  (=claude-org--session-get :queue=) that serializes block execution within a
  workspace.  There is no formal task state machine.  Response text is
  delivered by the =Stop= hook (=workspace_bridge.handle_response=), and live
  terminal echo is available via the async verbose mirror
  (=claude-org-cmux--start-verbose=).  (/Note:/ the ad-hoc
  =claude-org-cmux--stream-tick= timer this review originally critiqued was
  removed in commit 01b4143 — its insertion marker was never wired up.)
  Task lifecycle is tracked implicitly via =:busy= flag and =:query-completed=
  callback.  There is no unified way to cancel, inspect, or get notifications
  from background tasks.
- *Opportunity*: Introduce a lightweight task state machine:

  #+begin_src elisp
  (cl-defstruct claude-org-task
    id                ; unique string
    type              ; 'ai-block, 'loop-iteration, 'background-query
    status            ; 'pending, 'running, 'completed, 'failed, 'cancelled
    workspace-id      ; cmux workspace session ID
    session-key       ; org session key
    start-time        ; timestamp
    cancel-fn)        ; function to call for cancellation
  #+end_src

  Track tasks in a global hash table.  =claude-org-cmux-cancel= becomes
  a lookup by workspace -> find running task -> call cancel-fn.  This
  also enables a future "task dashboard" buffer showing all active AI work
  across workspaces.
- *Effort*: M
- *Impact*: high -- enables reliable cancellation, status reporting, and
  multi-workspace task management

** Finding 8: MCP Tool Proxy with Annotations

- *Source*: doc 15, section "Tool Discovery and Proxy"
- *Claude Code approach*: MCP tools are discovered via =tools/list= and
  wrapped into the native Tool interface.  Tool annotations
  (=readOnlyHint=, =destructiveHint=) from the MCP protocol are mapped
  to =isReadOnly()= and =isDestructive()= methods.  Tool descriptions are
  truncated to 2048 chars to prevent context bloat.  Tool names follow
  =mcp__serverName__toolName= convention.
- *Our current state*: Our MCP server exposes tools to Claude Code (we are
  the server, not the client).  We do not consume external MCP servers.
  Our tool descriptions are hardcoded in =emacs-mcp-server--builtin-tools=.
  We do not use MCP annotations.
- *Opportunity*: Add MCP annotations to our tool definitions:
  - =evalElisp=: =readOnlyHint: false=, =destructiveHint: false= (conservative
    defaults since it can do anything)
  - =report_invocation=: =readOnlyHint: true=

  When we add specialized tools (e.g., a read-only =org-read= tool), set
  =readOnlyHint: true= so Claude Code can auto-approve and parallelize them.
  Also: truncate our tool descriptions to stay under the 2048-char recommendation.
- *Effort*: S
- *Impact*: low -- marginal improvement but aligns with MCP best practices

** Finding 9: Concurrency-Safe Tool Partitioning

- *Source*: doc 09, section "Concurrent Safety Partitioning"
- *Claude Code approach*: When the model returns multiple tool_use calls,
  =partitionToolCalls()= groups consecutive concurrency-safe tools into
  parallel batches and executes unsafe tools serially.  The default is
  =isConcurrencySafe: false= (serial), tools opt into parallelism.
- *Our current state*: AI block execution is strictly serial -- one block
  at a time per workspace.  The queue system (=:queue= in session state)
  ensures this.  Within a single Claude Code response, if the AI makes
  multiple tool calls, Claude Code handles the parallelism internally (we
  have no visibility).
- *Opportunity*: When orchestrating multiple workspaces (e.g., running
  code review in workspace A while implementation continues in workspace B),
  we could partition work across workspaces using concurrency metadata.
  Mark read-only operations (grep, file-read) as safe to run in any workspace,
  while write operations (edit, commit) must be serialized per workspace.
  This is a future concern but the pattern is worth adopting now in the
  agent profile struct.
- *Effort*: M (for the metadata; L for actual parallel execution)
- *Impact*: medium -- unlocks parallel multi-workspace workflows

** Finding 10: MCP Transport Diversity and Connection Lifecycle

- *Source*: doc 15, sections "Transport Layer" and "Connection Lifecycle"
- *Claude Code approach*: Supports 6 transport types (stdio, SSE, HTTP,
  WebSocket, SDK, InProcess).  Local and remote servers use different
  concurrency limits (3 vs 20).  Connection lifecycle includes automatic
  reconnection with exponential backoff, needs-auth caching, and a three-stage
  signal escalation for stdio process cleanup (SIGINT -> SIGTERM -> SIGKILL).
  InProcess transport avoids 325MB subprocess overhead.
- *Our current state*: =emacs-mcp-server= uses HTTP (Streamable HTTP via
  =web-server= package).  We have a single transport type.  The server binds
  to localhost and Claude Code connects to it.  There is no reconnection logic
  on the server side (the server is always running).  The =web-server= package
  handles HTTP lifecycle.
- *Opportunity*: Two concrete improvements:
  1. *Health check endpoint*: Add a =/health= HTTP endpoint that returns
     server status, uptime, and registered tool count.  Our E2E tests already
     check liveness via HTTP -- a dedicated health endpoint is cleaner.
  2. *Session timeout*: Track MCP session activity timestamps.  If no requests
     arrive for N minutes, log a warning (helps debug "MCP disconnected"
     scenarios where Claude Code loses connection to our server).
- *Effort*: S
- *Impact*: low -- operational improvement for debugging

** Finding 11: Dynamic Skill Discovery via File Operations

- *Source*: doc 11, section "Dynamic Skill Discovery"
- *Claude Code approach*: When the AI reads or edits a file, the system
  checks if a =.claude/skills/= directory exists in any parent directory
  up to the project root.  Skills discovered this way are dynamically
  registered without restart.  This is "progressive discovery" -- skills
  relevant to a specific subdirectory are only loaded when the AI enters
  that area.
- *Our current state*: No dynamic skill discovery.  Slash commands available
  in AI blocks come from Claude Code itself.  We do not inject project-specific
  skills.
- *Opportunity*: Since our MCP server receives every evalElisp call, we could
  detect file-path arguments and trigger skill discovery.  When evalElisp code
  references a path like =/path/to/project/src/foo.el=, check if
  =/path/to/project/.claude/skills/= exists and register any discovered skills
  as MCP prompts.  This piggybacks on existing evalElisp calls without adding
  a new tool.
- *Effort*: M
- *Impact*: low -- nice to have but most users will not create subdirectory skills

** Finding 12: Permission Rule Suggestion from Command Patterns

- *Source*: doc 10, section "Smart Rule Suggestion"
- *Claude Code approach*: When a user approves a BashTool command, the system
  extracts a reusable prefix (e.g., =git commit= from =git commit -m "fix"=)
  and suggests it as a permanent allow rule (=Bash(git commit:*)=).  Certain
  prefixes (=sudo=, =env=, =bash -c=) are never suggested because they are
  equivalent to allowing everything.
- *Our current state*: =emacs-mcp-server-permission-mode= controls global
  permission behavior.  =emacs-mcp-server-allowed-tools= has a static list
  of patterns (default: =mcp__emacs__*=).  There is no mechanism to learn
  from user approval patterns or suggest new rules.
- *Opportunity*: In the permission callback (=claude-org-cmux--permission-needed=),
  when the user approves a tool use, extract the tool name and log it.  After
  N approvals of the same tool pattern, suggest adding it to the allow list.
  More immediately: add a =claude-org-cmux-auto-approve-read-only= customization
  that auto-approves tool calls classified as read-only (connecting to Finding 2).
- *Effort*: S (auto-approve read-only), M (learning suggestions)
- *Impact*: medium -- reduces approval friction for common patterns

** Finding 13: omitClaudeMd for Read-Only Agents

- *Source*: doc 12, section "BaseAgentDefinition"; doc 13, section "Explore Agent"
- *Claude Code approach*: Read-only agents (Explore, Plan) set =omitClaudeMd: true=
  to skip injecting CLAUDE.md content into the system prompt.  This saves
  5-15 Giga tokens per week across 34M+ Explore agent spawns.  The rationale:
  read-only agents do not need commit, PR, or lint guidelines.
- *Our current state*: We pass =--system-prompt= to Claude Code at launch but
  do not control whether CLAUDE.md is included.  Claude Code itself decides.
  Our agent profiles have no field to influence this.
- *Opportunity*: For read-only agent profiles (future "researcher" or "explorer"
  type), pass =--system-prompt= with explicit instructions and consider setting
  environment variable hints that Claude Code could use.  More practically:
  when launching with =--resume=, avoid re-injecting system prompts that are
  already in the session context.  This is a token optimization that matters
  at scale.
- *Effort*: S
- *Impact*: low -- minimal impact at our usage scale, but good practice

** Finding 14: Fork Subagent for Prompt Cache Reuse

- *Source*: doc 12, section "Fork Subagent"; doc 14, section "Fork Subagent"
- *Claude Code approach*: Fork mode creates a sub-agent that inherits the
  parent's full conversation history and system prompt.  All fork children
  share byte-identical API request prefixes to maximize prompt cache hits.
  Anti-recursion is enforced by both message scanning (look for fork tags)
  and querySource persistence (survives autocompact).
- *Our current state*: Each AI block execution in a workspace is independent
  -- the Claude Code instance in cmux maintains its own conversation context.
  When using =--resume=, the session continues where it left off, which is
  our equivalent of "fork" (same context, new query).  We do not orchestrate
  multiple sub-agents from a single workspace.
- *Opportunity*: When implementing a "research then implement" workflow (e.g.,
  SDD stories), we could open two cmux tabs in the same workspace: one for
  research (read-only) and one for implementation.  Both would share the
  same session context via =--resume=, getting prompt cache benefits.  The
  org property =CLAUDE_CLI_SESSION= already supports this -- we just need
  the orchestration logic to launch the second tab with the same session ID.
- *Effort*: M
- *Impact*: medium -- enables efficient multi-phase workflows within a story

** Finding 15: Task Notification Priority Queue

- *Source*: doc 14, section "Message Queue and Priority"
- *Claude Code approach*: Three priority levels: =now= (urgent), =next= (user
  input), =later= (task notifications).  User input is never starved by
  system notifications.  Notifications use XML-based =<task-notification>=
  protocol with task-type-specific extensions.
- *Our current state*: Response text lands in the org buffer once via the
  =Stop= hook path (=handle_response= → =insert-response=); no polling on the
  Emacs side.  Live terminal echo uses the async verbose mirror
  (=verbose-tick= via =start-process= + sentinel), which does not block the
  main loop.  (/Historical:/ the original =claude-org-cmux--stream-tick=
  timer this review mentioned was sync =call-process= polling and was removed
  in commit 01b4143 — see =.claude/rules/minimize-emacs-mcp-calls.md=.)
- *Remaining opportunity*: User actions still occasionally compete with verbose
  redraws and handle-response MCP calls.  A priority queue for Emacs-side
  events could further smooth this:
  1. =high=: user-initiated actions (C-c C-c to execute, C-g to cancel)
  2. =normal=: response insertion from =Stop= hook
  3. =low=: verbose mirror redraws, status bar updates
- *Effort*: S
- *Impact*: low–medium (the sync =stream-tick= was the dominant source of
  lag; remaining competition is much smaller after its removal)

* Key Architectural Takeaways

** Pattern: Fail-Closed Everywhere

Claude Code's most pervasive pattern is fail-closed defaults.  Tools
default to not-read-only and not-concurrency-safe.  AST parsing rejects
unknown node types.  Permission checks default to "ask."  Our system
should adopt this for evalElisp classification: if we cannot determine
the form is read-only, treat it as a write operation.

** Pattern: Metadata-Driven, Not Code-Driven

Agent behaviors in Claude Code are driven by data (frontmatter fields,
environment variables, feature flags) rather than code branches.  Adding
a new agent type requires a markdown file, not a code change.  Our
=claude-org-cmux--agent-profile= struct partially achieves this, but
extending it with tool constraints, permission modes, and model selection
would bring it closer to the data-driven ideal.

** Pattern: Default Isolated, Explicit Shared

=createSubagentContext= clones everything by default and requires explicit
opt-in for sharing.  This prevents entire classes of concurrency bugs.
When we build multi-workspace orchestration, adopt this pattern: each
workspace gets a fresh copy of state, and shared resources (org buffer,
session registry) require explicit synchronization.

** Pattern: Progressive Enhancement

Skills are discovered progressively (startup -> file operations -> manual
registration).  Agents have progressive levels of constraint (wildcard ->
blacklist -> whitelist).  We should design our extensions similarly:
basic agent profiles work immediately, richer profiles add constraints
incrementally.
