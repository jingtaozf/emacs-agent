* What Is Harness Engineering?

Harness Engineering is a paradigm coined by Mitchell Hashimoto and formalized by
OpenAI's Codex team: /"anytime an agent makes a mistake, engineer a solution so the
agent never makes that mistake again."/ It shifts the engineer's role from writing
code to *designing environments, specifying intent, and building feedback loops*.

The core insight: traditional prompt engineering asks "how do I tell the AI what to
do?" — harness engineering asks "how do I build the infrastructure so the AI can't
go wrong?"

* The Five Principles (OpenAI Codex)

1. *What the Agent Can't See Doesn't Exist* — Push all decisions into repository
   markdown, schemas, and plans. Create ExecPlans: self-contained design documents
   a beginner could follow. No tacit knowledge.

2. *Ask What Capability Is Missing, Not Why the Agent Is Failing* — When agents
   struggle, treat it as a signal to improve the environment. Build custom helpers,
   integrate observability, choose boring technology with high training data.

3. *Mechanical Enforcement Over Documentation* — Enforce consistency through
   structural rules, linters, and tests — not just written guidelines. Custom
   linters fail builds on violations. Error messages double as remediation
   instructions injected into agent context.

4. *Give the Agent Eyes* — Provide real-time visual and operational feedback.
   Connect DevTools, observability stacks, pre/post-task comparisons. Enable
   agents to verify their own fixes.

5. *A Map, Not a Manual* — Concise architectural overview (ARCHITECTURE.org)
   emphasizing structure, boundaries, and invariants. Focus on "what rarely
   changes." Express constraints as absence statements.

* Three Pillars of Harness Design

**Pillar 1: Context Engineering** — Curating what the model sees for better
results. Key strategies:
- /Progressive disclosure/: agents start with small stable entry point, learn
  where to look next (AGENTS.md as table of contents, not encyclopedia)
- /Context isolation/: keep different subtasks in separate context windows
- /Context reduction/: drop irrelevant info (effectiveness drops with too much)
- /Context retrieval/: inject fresh info at the right time
- Structured =docs/= directory as system of record, not external wikis

**Pillar 2: Architectural Constraints** — Trade flexibility for reliability:
- Strict layered architecture: Types → Config → Repo → Service → Runtime → UI
- Custom linters with remediation-aware error messages
- Structural tests validate compliance (like ArchUnit)
- "Taste invariants": naming conventions, file size limits, structured logging
- Paradox: constraining solution space /increases/ AI reliability

**Pillar 3: Periodic Maintenance (Garbage Collection)** — Combat entropy:
- Background agents scan for stale documentation
- "Doc-gardening" agents open fix-up PRs
- Automated consistency checks via CI
- Agent-generated code accumulates different cruft than human code

* Anthropic's Harness Patterns for Long-Running Agents

Key failure modes and solutions:
- /Over-ambition/: agents attempt entire projects, run out of context mid-work
- /Premature completion/: agents declare done after partial progress
- Solution: decompose into manageable phases with three bridging artifacts:
  1. *Feature list* (JSON format) — 200+ granular end-to-end features, pass/fail
  2. *Progress file* (claude-progress.txt) — documents decisions for continuity
  3. *Git history* — enables reverting failed changes, clean mergeable states
- Rule: "unacceptable to remove or edit tests" — prevents destructive shortcuts
- Each session: verify state → read features → work single feature → test → commit

* The Split Engineering Role

Modern harness-oriented engineering divides into two halves:
1. *Building the Environment* — structure, tools, feedback mechanisms
2. *Managing the Work* — planning, direction, quality gates

Agent failures continuously inform environment improvements. Planning before
execution is critical — agents should never begin coding without reviewed plans.

* Round 3: Advanced Patterns & Implementation Details

** Loop Detection & Circuit Breakers

Agent stuck-in-loop is the most common runtime failure. Three layers of defense:

| Layer | Technique | Implementation |
|-------+-----------+----------------|
| Hard Limit | Max turn count | Our =:loop N= already does this |
| Sliding Window | Track last N actions, detect repetition | Compare token-sets via Jaccard similarity |
| Semantic Check | Verify actual task completion externally | Check output artifacts, not agent claims |

*Key insight from [[https://www.fixbrokenaiapps.com/blog/ai-agents-infinite-loops][FixBrokenAIApps]]*:
Loop guardrails must be /external and deterministic/ — never trust the agent to
detect its own loops. The harness, not the agent, enforces termination.

*Circuit breaker pattern*: After N consecutive failures on same action, pause and
either escalate to user or switch strategy. Exponential backoff with jitter
prevents thundering-herd on shared resources.

*Our codebase gap*: =claude-org= has =:loop N= for max iterations but no
/repetition detection/ within those iterations. An agent could repeat the same
failing edit N times before the hard limit stops it.

** Session Startup Rituals (Anthropic Pattern)

From [[https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents][Anthropic's long-running agent harness]]:

Every session begins with a deterministic 5-step initialization:
1. =pwd= — establish working context
2. Read git log + progress file — understand recent work
3. Consult feature list — pick highest-priority incomplete item
4. Run =init.sh= — start development server / verify environment
5. Run baseline E2E tests — confirm nothing is broken

*Key insight*: "Agents that skip the startup ritual spend substantial time
guessing at what happened and trying to get the basic app working again."

*Our SDD analog*: Our =:system_prompt:= section partially does this, but we
lack a structured progress file. The SDD workflow section is closest — it
tracks tasks with checkboxes. Adding a machine-readable progress artifact
(JSON or structured org properties) would improve cross-session continuity.

** Context Compaction as Momentum

From [[https://jxnl.co/writing/2025/08/30/context-engineering-compaction/][Jason Liu's compaction research]]:

Compaction is not just summarization — it's /momentum preservation/. Like
gradient descent momentum in ML, good compaction preserves the optimization
direction, not just the facts.

*Specialized compaction prompts* for different analytical purposes:
- /Failure mode detection/: "loops, linter conflicts, recently-deleted code recreation"
- /Language switching/: "framework switches, cross-language debugging"
- /User feedback clustering/: "correction requests, preference statements"

*Metrics for compaction effectiveness*:
- Task completion rate post-compaction
- Backtracking steps after compaction boundary
- Time to productive work after context reset

*Our gap*: When our sessions hit context limits and auto-recover, the
compaction is generic. Specialized compaction prompts tuned to our SDD
workflow would preserve more useful context.

** Self-Healing Agent Patterns

Three recovery strategies when agents encounter errors:

1. *Retry with modified context* — strip failed tool output, add error
   explanation, re-attempt with cleaner context window
2. *Memory isolation* — quarantine failed conversation turns so they don't
   pollute subsequent reasoning (avoid cascading hallucinations)
3. *Fallback degradation* — when primary approach fails N times, switch to
   simpler strategy (e.g., ask user instead of autonomous action)

*Our strength*: =claude-agent= already has session recovery (file-based
session keys, SDK UUID mapping). The =:on-error= callback in
=claude-agent-query= provides a hook point for self-healing logic.

*Our gap*: No automatic strategy switching. If a query fails, we report the
error but don't attempt an alternative approach.

** Feature Specification as JSON (Not Markdown)

Anthropic's long-running agent harness uses *JSON for feature tracking*, not
markdown. Reason: "the model is less likely to inappropriately change or
overwrite JSON files compared to Markdown files."

Each feature is a self-contained test specification:
#+begin_example
{
  "category": "functional",
  "description": "New chat button creates fresh conversation",
  "steps": ["navigate", "click", "verify", "check state"],
  "passes": false
}
#+end_example

Rule: /"unacceptable to remove or edit tests"/ — prevents agents from taking
destructive shortcuts. Features remain marked =false= until verified.

*Our SDD analog*: Our =:features:= section uses org checkboxes. This works
but is more susceptible to accidental modification. Consider adding a
=features.json= artifact for machine-readable tracking alongside the org view.

** Structural / Architectural Tests for Elisp

No existing ArchUnit equivalent for Emacs Lisp, but we can build lightweight
equivalents using ERT:

#+begin_example
;; Test: no circular dependencies between modules
(ert-deftest test-no-circular-deps ()
  (let ((agent-requires (extract-requires "claude-agent.org"))
        (org-requires (extract-requires "claude-org.org")))
    (should-not (intersection agent-requires org-requires))))

;; Test: all public functions have docstrings
(ert-deftest test-public-functions-documented ()
  (dolist (sym (apropos-internal "^claude-agent-[^-]" #'fboundp))
    (should (documentation sym))))

;; Test: no direct buffer writes outside narrowing guard
(ert-deftest test-writes-use-narrowing ()
  (let ((violations (grep-source "(insert " "claude-org.org"
                      :exclude "with-section-narrowed")))
    (should (null violations))))
#+end_example

These enforce architectural invariants mechanically — Principle 3 applied.

* Round 4: Progressive Disclosure, Reasoning Budget & Practical Patterns

** Progressive Disclosure Architecture

The most important structural pattern for managing agent context. From
[[https://alexop.dev/posts/stop-bloating-your-claude-md-progressive-disclosure-ai-coding-tools/][AlexOp]]
and [[https://www.honra.io/articles/progressive-disclosure-for-ai-agents][Honra.io]]:

Core insight: /"agents get dumber when you give them too much information
upfront."/ Overloading context creates "context rot" — irrelevant information
drowns out signal, causing hallucinations and task drift. Attention mechanisms
weigh every token against others, so noise /actively/ degrades reasoning.

Three-layer architecture:

| Layer | What | Load Mechanism | Budget |
|-------+------+----------------+--------|
| Index | Titles, descriptions, pointers | Every session | ~500 tokens |
| Details | Full docs, gotchas, patterns | When task matches | 200-500 tokens/file |
| Deep Dive | Supporting materials, examples | On-demand during execution | Variable |

*Concrete sizing*:
- Root CLAUDE.md: *50-60 lines max* (~500 tokens)
- Only include: project overview (2-3 sentences), essential commands, stack
  summary, directory structure, and /pointers/ to docs/
- Everything else moves to =docs/= or =.claude/agents/=
- Rule: /"If a tool can enforce it, don't write prose about it"/ —
  linters handle style, not CLAUDE.md

*The =/learn= pattern*: When agent encounters a non-obvious problem, capture
the solution into the appropriate =docs/= file. Knowledge compounds over
sessions without bloating the root file.

** AGENTS.md as Failure Prevention Log

From Mitchell Hashimoto (via [[https://www.aihero.dev/a-complete-guide-to-agents-md][AI Hero guide]] and
[[https://mitchellh.com/writing/my-ai-adoption-journey][Hashimoto's blog]]):

/"Each line in that file is based on a bad agent behavior, and it almost
completely resolved them all."/ AGENTS.md is not documentation — it's a
*curated list of past failures now prevented*.

What belongs in root AGENTS.md:
- One-sentence project description
- Package manager (if non-standard)
- Non-standard build/typecheck commands
- Pointers to domain-specific docs

What does NOT belong:
- Language-specific rules (move to =docs/TYPESCRIPT.md=)
- Testing patterns (move to =docs/TESTING.md=)
- Coding style rules (use linters)
- Auto-generated comprehensive docs

Key anti-pattern: /"stale documentation actively poisons context"/ — out-of-date
file paths, contradictory rules, and documentation drift are worse than having
no documentation at all.

** Reasoning Budget Sandwich (LangChain)

From [[https://blog.langchain.com/improving-deep-agents-with-harness-engineering/][LangChain's harness research]]:

Allocating reasoning compute /strategically/ outperforms constant high reasoning:

| Phase | Reasoning Level | Why |
|-------+-----------------+-----|
| Planning & Discovery | =xhigh= | Thorough problem understanding |
| Implementation | =high= | Balanced — avoid over-thinking simple edits |
| Verification | =xhigh= | Catching final mistakes is critical |

Results: reasoning sandwich (66.5%) > constant xhigh (53.9%). The /same model/
and /same tools/ — only the reasoning allocation changed.

*Our codebase analog*: Our SDD workflow naturally creates this sandwich —
=:research:= and =:design:= phases are high-reasoning exploration,
=:implementation:= is focused building, and pre-commit hooks are the
verification phase. But we don't explicitly control reasoning budget per phase.

** Middleware Patterns (LangChain, detailed)

Three concrete middleware implementations:

1. *PreCompletionChecklistMiddleware* — intercepts agent before exit, enforces
   verification pass against original task specification. Prevents premature
   "I'm done" declarations.

2. *LoopDetectionMiddleware* — tracks per-file edit counts via tool call hooks.
   After N edits to same file, injects /"reconsider your approach"/ prompt.
   Breaks doom loops where models repeat failed variations.

3. *LocalContextMiddleware* — auto-maps working directories, discovers available
   tools (Python installations, bash commands) at startup. Reduces
   environmental discovery errors.

The Build-Verify Loop (4 stages):
1. Plan & Discover → read task, scan codebase
2. Build → implement with tests from the start
3. Verify → execute tests, compare against spec
4. Fix → analyze errors against original requirements, iterate

** Agent Harness = Shell (Architectural Insight)

From [[https://pavpanchekha.com/blog/agents-are-shells.html][Pavel Panchekha]]:

Agent harnesses are fundamentally /collaborative shells/ where users and AI
access identical tools through a shared context. This implies:

- File editing should display diffs (before/after) — both human and AI readable
- Undo functionality benefits humans in learning, AI in recovery
- Timeouts and suspension prevent infinite loops
- Layered permissions: human defaults > model defaults, tighten for risky ops

*Implication for our codebase*: Our Emacs integration is already shell-like
(comint-mode chat, MCP tools). The permission harness
(=.claude/settings.local.json=) implements the layered access pattern. We could
add explicit undo support for section updates (store previous content before
overwriting in =claude-org-update-or-create-subsection=).

** CLAUDE.md Best Practices (Definitive)

From [[https://www.humanlayer.dev/blog/writing-a-good-claude-md][HumanLayer]], [[https://www.builder.io/blog/claude-md-guide][Builder.io]], and [[https://claude.com/blog/using-claude-md-files][Anthropic's official guide]]:

- Don't include prose for what tools enforce — /"if a tool can enforce it, don't
  write prose about it"/
- Never include secrets, API keys, or credentials (it loads as system prompt)

*Our gap*: We have user-level =~/.claude/CLAUDE.md= but no project-level
=CLAUDE.md= in the repo. Project conventions, build commands, and module
boundaries should be documented at project level.

** AGENTS.md Structure (From [[https://www.aihero.dev/a-complete-guide-to-agents-md][AI Hero]] and [[https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/][GitHub's analysis of 2,500+ repos]])

3. *Project structure* — directory layout, module relationships
4. *Code style* — naming conventions, patterns to follow/avoid

** Progressive Disclosure Architecture

From [[https://alexop.dev/posts/stop-bloating-your-claude-md-progressive-disclosure-ai-coding-tools/][alexop.dev]] and [[https://www.honra.io/articles/progressive-disclosure-for-ai-agents][Honra]]:

Three-layer information architecture:

| Layer | What | When Loaded | Token Cost |
|-------+------+-------------+------------|
| Layer 1: Always | CLAUDE.md (~50 lines) | Every session | ~500 tokens |
| Layer 2: Task-relevant | =docs/*.md= files | When agent needs domain knowledge | On-demand |
| Layer 3: Specialist | =.claude/agents/*.md= | When specific domain activated | Isolated context |

*Implementation pattern*: CLAUDE.md says "Read =docs/TESTING.md= before writing
tests" — the agent loads Layer 2 only when relevant. Layer 3 agents run in
isolated contexts, preventing constant context pollution.

*=/learn= command pattern*: Capture insights systematically —
1. Analyze conversation for non-obvious, reusable patterns
2. Identify correct documentation file location
3. Request approval before saving
4. Enable on-demand loading by triggering agents when relevant

*Our current implementation*: Already strong — 9 agents (Layer 3), 13 skills
(domain injection), =prompts/tags/= (behavioral configuration). Main gap:
no Layer 2 =docs/= folder with task-specific guidance documents.

** Reasoning Budget Allocation ("Reasoning Sandwich")

From [[https://blog.langchain.com/improving-deep-agents-with-harness-engineering/][LangChain's harness engineering]] and [[https://arxiv.org/abs/2412.18547][Token-Budget-Aware LLM Reasoning]]:

The "reasoning sandwich" allocates compute by phase:

| Phase | Budget | Rationale |
|-------+--------+-----------|
| Planning & Discovery | =xhigh= | Critical — wrong plan = wasted execution |
| Implementation | =high= | Standard — following established plan |
| Verification | =xhigh= | Critical — catch errors before completion |

*Token elasticity phenomenon*: When given too-small budgets, LLMs actually
use /more/ tokens (they fail to follow the constraint and ramble). Optimal
budget is task-dependent — 67% token reduction possible with dynamic allocation.

*Our SDD analog*: Our SDD phases (research → design → planning →
implementation) naturally implement this. But we don't vary reasoning budget
per phase. The =:loop N= header partially controls iteration depth.

** Pre-Completion Verification (Middleware Pattern)

From [[https://blog.langchain.com/improving-deep-agents-with-harness-engineering/][LangChain]]:

=PreCompletionChecklistMiddleware= intercepts before agent exit and forces a
verification pass against the original task spec. Combined with time-budget
warnings that nudge agents toward verification as timeout approaches.

Pattern: /"Planning & Discovery → Build → Verify → Fix"/ — verification is
not optional, it's mechanically enforced.

*Our SDD analog*: Our =:implementation:= tag prompt already says "run tests at
end, fix failures, repeat until pass or max retries." This IS pre-completion
verification — we just don't call it middleware.

** Agent Drift & Entropy (From [[https://arxiv.org/abs/2601.04170][Agent Drift paper]] and [[https://mtrajan.substack.com/p/harness-engineering-is-not-context][Mtrajan]])

*Agent drift*: Progressive degradation of behavior over extended interactions.
Agents replicate existing patterns — good AND bad. Drift is inevitable.

*Entropy as harness metric*: OpenAI team spent "about a day a week" cleaning
"AI slop" before automating it with garbage collection agents.

*Three defenses against entropy*:
1. *CI gates* — reject PRs that increase complexity metrics
2. *Background agents* — scan for deviations, open auto-merged refactoring PRs
3. *Mechanical linting* — errors teach the agent how to fix violations

*Our gap*: No entropy detection. We could add ERT tests that measure:
- Average function length in =.org= files (flag if growing)
- Public API surface area (flag if expanding without intent)
- Dead code detection (unused =defun= / =defvar=)

** Production Failure Mode Taxonomy

From [[https://dev.to/epappas/the-agent-harness-is-the-architecture-and-your-model-is-not-the-bottleneck-3bjd][Pappas: Agent Harness as Architecture]],
the most complete failure classification found:

| Failure Mode | Symptom | Mitigation |
|--------------+---------+------------|
| Context exhaustion | Agent loses track of earlier decisions | Compaction hierarchy (raw → compressed → summarized) |
| Lost-in-the-middle | Agent ignores info in middle of context | Todo-list mechanism; recite objectives at context end |
| Tool misrouting | Wrong tool for task | Reduce tool count; use general-purpose tools |
| Hallucinated tool calls | Agent invents non-existent tools | Schema validation; strict tool registration |
| Retry loops | Same failed action repeated | Error trace retention; approach blacklisting |
| State corruption | Progress lost or overwritten | Progress files; version control checkpoints |
| Premature termination | Agent declares done when incomplete | Feature checklists; verification steps |
| Timeout cascades | One slow step blocks everything | Step budgets; circuit breakers |

*Key insight*: /"Signal-to-noise ratio dominates over raw window size."/ Adding
more context doesn't help if it's noise — attention mechanisms weigh every
token against all others, so irrelevant info actively degrades reasoning.

*Our codebase mapping*:
- Context exhaustion: ✓ handled by session recovery + =:loop N=
- Lost-in-the-middle: ✗ no re-injection of objectives mid-session
- Tool misrouting: ✓ mitigated by permission system, few focused tools
- Retry loops: ✗ no approach blacklisting
- State corruption: ✓ org-based state is version-controlled
- Premature termination: ✗ no forced verification before completion

Critical insight from multiple sources: harness engineering only works /above/
a model capability floor (GPT-4-class). Below this threshold, no orchestration

- *Orchestration errors* (model had the capability but harness failed) →
  harness improvement needed

For our use case with Claude (well above the floor), virtually all failures
should be orchestration errors — validating that harness investment is the
right focus.

* Stream B: Bug Hunting Experiment — Findings and Meta-Analysis

Deployed a bug-hunting agent with full codebase access, instructed to find
real bugs and architecture issues. This was both a /research experiment/
(find bugs) and a /meta-experiment/ (can agents do this reliably?).

**8 issues reported, 2 claimed "critical".**

**Bug #1 (CRITICAL — FALSE POSITIVE)**: Agent claimed sentinel cleanup code
on line ~1485 of =claude-agent.org= was unreachable dead code:

#+begin_example
(if (zerop exit-code)
    (sentinel-handle-normal-exit ...)
  (sentinel-handle-error ...)
  (sentinel-cleanup ...))   ;; Agent: "unreachable!"
#+end_example

*Verification*: Emacs Lisp =if= has /implicit progn/ for else forms —
=(if COND THEN ELSE-1 ELSE-2)= executes BOTH else forms. Confirmed:

#+begin_example
(let ((results nil))
  (if nil
      (push "then" results)
    (push "else-1" results)
    (push "else-2" results))
  results)
;; => ("else-2" "else-1") — both execute
#+end_example

This is *correct working code*. The agent applied C/Python =if-else= semantics
to Emacs Lisp, producing a confident but wrong diagnosis.

**Bug #2 (CRITICAL — VALID BUT LOW RISK)**: Race condition in stdin close —
=(run-at-time 0.1 nil ...)= timer could fire after process death. Valid in
theory, but Emacs is single-threaded and process sentinels run synchronously
before timers, so the window is narrow.

**Bugs #3-#8**: Mostly defensive coding improvements (better error handling
in JSON parser, marker lifecycle guards, timer cleanup). Reasonable
suggestions but not actual bugs — more like code hardening.

**Meta-findings (critical for harness engineering)**:

1. *Agents lack Emacs Lisp semantic knowledge*. The false positive on Bug #1
   is not a prompting failure — it's a /knowledge gap/. The agent had full
   access to the code and still misinterpreted fundamental Emacs Lisp control
   flow. This will recur for any Lisp-specific construct (=condition-case=
   multiple handlers, =unwind-protect= cleanup forms, =prog1=/=prog2=, etc.).

2. *Agents don't self-verify*. The bug-hunting agent never /tested/ its
   hypotheses. It could have evaluated =(if nil 'then 'else-1 'else-2)= in
   =*scratch*= to check. It reported with high confidence instead.

3. *Confidence ≠ correctness*. The agent labeled Bug #1 as "CRITICAL" with
   detailed explanation of why cleanup never runs. Every detail was internally
   consistent — and wrong. /Structured confidence without verification is
   dangerous for autonomous agents./

4. *Agent-generated files need review*. The agent created =BUG_REPORT.md=,
   =BUG_FIXES.md=, =FINDINGS_SUMMARY.md=, etc. — all containing the false
   positive as a confirmed critical bug. If merged without review, these would
   pollute project documentation.

* Synthesis: Agent-Readiness Gap Analysis

Combining all three streams, the core gap is: *agents can build features
(proven by F0-F6 in previous rounds) but cannot reliably verify claims
about existing code.* Building new code uses tests as guardrails;
analyzing existing code requires language-specific semantic understanding
that agents lack.

*The Three Readiness Levels*:

| Level | Capability | Current Status |
|-------+------------+----------------|
| L1: Build | Write new code, pass new tests | ✅ Proven (F0-F6, MCP protection) |
| L2: Fix | Find and fix real bugs | ⚠️ Partial — needs verification hooks |
| L3: Analyze | Correctly assess code quality | ❌ Bug #1 false positive shows gap |

*Root cause analysis of each gap*:

- *L2 gap*: Agents can fix bugs IF told where to look (targeted TDD works).
  But autonomous bug /discovery/ requires understanding runtime behavior,
  Emacs-specific semantics, and multi-function interactions — areas where
  agents lack grounding.

- *L3 gap*: Agents pattern-match syntax without understanding language
  semantics. Emacs Lisp has unusual constructs (implicit progn, dynamic
  binding, advice system, buffer-local variables) that don't match the
  C/Python/JS mental models agents default to.

*Three interventions to close the gaps*:

1. *Verification hooks*: Pre-commit or pre-test hooks that mechanically
   catch common agent mistakes (e.g., structural tests for new code patterns)

2. *Emacs Lisp semantic reference*: A concise =ELISP_IDIOMS.org= in the
   project that covers the constructs agents consistently misunderstand
   (=if= implicit progn, =condition-case=, dynamic binding, etc.)

3. *Claim-then-verify workflow*: Require agents to /test their hypotheses/
   before reporting — e.g., "evaluate this expression to confirm the
   behavior" before claiming dead code.

* Literate Programming as Harness: Our Unique Position

OpenAI's harness engineering solves a fundamental problem: code and
documentation are /separate artifacts/ that drift apart. ARCHITECTURE.org
maps the territory (source files) because the territory has no narrative.

Our project doesn't have this problem. Or rather, it has a /different/
problem.

**What literate programming already gives us (for free):**

1. *Code IS documentation* — Each =#+begin_src elisp= block is surrounded by
   prose explaining /why/ it exists. An agent reading =claude-agent.org= sees
   23 narrative sections (Introduction → Process Management → JSON Protocol →
   Core API → ...) that tell a /story/, not just a collection of functions.

2. *Section headings ARE the architecture* — The org hierarchy of each .org
   file IS a table of contents. =claude-org.org= has 25 top-level sections
   that describe the module's structure. No separate ARCHITECTURE.org can be
   more authoritative than the file's own outline.

3. *The "why" is always visible* — In traditional codebases, agents see
   /what/ the code does but not /why/. In literate code, the prose paragraph
   before each code block explains intent, tradeoffs, and context.

4. *Org properties are machine-readable metadata* — =:CUSTOM_ID:=, =:EFFORT:=,
   =:ORDERED:= — these give agents structured data alongside the narrative.

**What literate programming does NOT give us:**

1. *Cross-module relationships* — Each .org file tells its own story. No
   single .org file describes how =claude-agent.org=, =claude-org.org=, and
   =emacs-mcp-server.org= relate to each other. This is the /gap/ an
   architecture document fills.

2. *Global invariants* — "Process filters must never signal errors" is true
   across ALL modules but lives as a rule in CLAUDE.md. Invariants that span
   files have no natural home in a literate document.

3. *Absence constraints* — "=claude-agent.org= has NO dependency on org-mode"
   is not stated anywhere in =claude-agent.org= because you don't narrate
   what /isn't/ there. Yet this constraint is critical for agents to know.

4. *Extension points* — Where should a new backend go? A new MCP tool? A new
   test category? The individual .org files don't say "add your thing here."
   This navigational guidance is what agents need most.

5. *The harness lifecycle* — How does the development process itself work?
   Edit → reload → test → verify. This meta-process isn't in any .org file.

**The architectural insight:**

In a literate programming project, ARCHITECTURE.org is not a /map of the
code/ (the code maps itself). It's a *meta-map* — a navigational aid for
what falls /between/ the literate documents:

- Cross-module boundaries and dependency direction
- Global invariants and absence constraints
- Extension points and future development guidance
- The development lifecycle and verification workflow

This is a SMALLER, more focused document than in traditional projects.
The .org files carry the heavy documentation load; ARCHITECTURE.org only
covers what they structurally cannot.

**The "living" requirement:**

OpenAI's Codex team uses "garbage collection" — background agents that scan
for drift and open cleanup PRs. For us, the equivalent is simpler: because
ARCHITECTURE.org is small and covers only cross-module concerns, it needs
updating only when:

- A new .org module is added
- Dependency direction changes
- A new invariant is discovered
- An extension point is created

This should be a /rule in CLAUDE.md/: "After architectural changes, update
ARCHITECTURE.org." And a structural test should verify the meta-map stays
current: every .org module must be mentioned, and the file stays under its
size limit.

**Four Principles for Our Harness:**

Derived from the synthesis of OpenAI's 5 principles with our literate
programming context:

*Principle 1: The Territory IS the Map*
In literate programming, code files ARE documentation. ARCHITECTURE.org is a
meta-map that navigates /between/ literate documents, not a separate
documentation layer. It should reference .org sections, not duplicate them.
(Subsumes OpenAI P1 + P5)

*Principle 2: Enforce the Invariants, Narrate the Rest*
Structural tests enforce hard invariants mechanically. Literate prose in .org
files narrates everything else. The harness feedback loop migrates repeated
violations from "narrated" (CLAUDE.md rule) to "enforced" (structural test).
(Subsumes OpenAI P3)

*Principle 3: Agents Verify, Never Trust*
Every claim an agent makes must be mechanically verifiable. Verification
commands, testable idiom examples, =make test-smoke=. Agents should never
commit code they cannot verify. The MCP =evalElisp= tool gives agents direct
runtime inspection — deeper than Chrome DevTools.
(Subsumes OpenAI P4)

*Principle 4: The Harness Grows With Each Mistake*
ARCHITECTURE.org auto-updates when modules change. Structural tests grow when
agent mistakes reveal uncovered invariants. =ELISP_IDIOMS.org= gains entries
when agents misunderstand language constructs. The harness co-evolves with
the codebase — every bug is a harness improvement opportunity.
(Subsumes OpenAI P2)
