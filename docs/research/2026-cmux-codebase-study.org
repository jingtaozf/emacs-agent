#+TITLE: cmux Codebase Study — Architecture, Internals, and Lessons for Emacs Integration
#+DATE: 2026-03-16
#+STATUS: complete

* Executive Summary

cmux is a macOS-native terminal multiplexer written in *Swift*, built on top of the
*Ghostty* terminal emulator (Zig xcframework) for all PTY/rendering work. It communicates
via a *Unix domain socket* with a dual-protocol (V1 text + V2 JSON-RPC) CLI tool. It has
deep *Claude Code integration* via a dedicated =claude-hook= CLI subcommand that manages
session state, sidebar status, and notifications.

Key findings for our Emacs integration:

| Finding | Impact |
|---------+--------|
| cmux has 100+ V2 methods; we use ~15 | Many unused capabilities |
| =claude-hook= manages sidebar status natively | We duplicate this partially |
| =pipe-pane= and =wait-for= exist for event-driven I/O | We poll instead |
| Shell integration pushes CWD/git/ports/PR state | We don't leverage this |
| Browser automation API is extensive | Completely unused |
| No MCP server in cmux | Correct — we provide MCP via Emacs |
| Session persistence handles scrollback/restore | We don't use this |

* Architecture

** Technology Stack

| Component | Technology |
|-----------+-----------|
| App | Swift + SwiftUI (macOS native) |
| Terminal engine | Ghostty (Zig xcframework, forked at manaflow-ai/ghostty) |
| Split panes | Bonsplit (custom Swift library, =vendor/bonsplit=) |
| CLI | Swift standalone binary (9652 lines, bundled in app) |
| IPC | Unix domain socket (=AF_UNIX=, =SOCK_STREAM=) |
| Build | Xcode (=GhosttyTabs.xcodeproj=) |

* IPC Protocol

** Dual Protocol

- *V1 (text)*: =<command> [args]\n= → =OK ...\n= or =ERROR: ...\n=
- *V2 (JSON-RPC)*: ={"id":"uuid","method":"surface.send_text","params":{...}}\n=
  → ={"id":"uuid","ok":true,"result":{...}}\n=

Auto-detected: lines starting with ={= are V2.

** Socket Path Resolution

| Build | Path |
|-------+------|
| Production | =~/Library/Application Support/cmux/cmux.sock= |
| Debug | =/tmp/cmux-debug.sock= |
| Override | =CMUX_SOCKET_PATH= env var |

** Security Model

| Mode | Access |
|------+--------|
| =cmuxOnly= (default) | Descendants of cmux process only (PID ancestry check) |
| =automation= | Same macOS user |
| =password= | Any process with correct password |
| =allowAll= | All local processes |

** Addressing

=--workspace=, =--pane=, =--surface= accept: UUID, ref string (=workspace:1=,
=surface:3=), or integer index. Env vars =CMUX_WORKSPACE_ID= and =CMUX_SURFACE_ID=
serve as defaults in terminal sessions.

* Claude Code Integration (=claude-hook=)

cmux has a dedicated =cmux claude-hook <subcommand>= CLI command that serves as
Claude Code's hook endpoint. This is separate from our =sdd-bridge=.

** Hook Subcommands

| Subcommand | Claude Event | Action |
|------------+-------------+--------|
| =session-start= | =SessionStart= | Register session, set agent PID |
| =prompt-submit= | =UserPromptSubmit= | Clear notifications, set "Running" status |
| =pre-tool-use= | =PreToolUse= | Set verbose tool status (optional) |
| =stop= | Turn ended | Set "Idle" status, send notification |
| =notification= | =Notification= | Set "Needs input" status, notify |
| =session-end= | =SessionEnd= | Clear all state |

** Sidebar Status States

| State | Icon | Color | Trigger |
|-------+------+-------+---------|
| Running | =bolt.fill= | =#4C8DFF= blue | =prompt-submit=, =pre-tool-use= |
| Idle | =pause.circle.fill= | =#8E8E93= gray | =stop= |
| Needs input | =bell.fill= | =#4C8DFF= blue | =notification= |

** Session Persistence

=ClaudeHookSessionStore= persists session→workspace→surface mappings to
=~/.cmuxterm/claude-hook-sessions.json= using =flock(LOCK_EX)= for safe
concurrent access. Sessions older than 7 days are pruned.

** Verbose Tool Status

When =claudeCodeVerboseStatus= UserDefaults is true, =pre-tool-use= shows
tool-specific text: "Reading file.txt", "Running git status", etc.
This gives real-time visibility into what Claude Code is doing.

* Shell Integration

cmux injects shell hooks (=preexec=/=precmd=) that report state changes to the
socket. This enables the sidebar to show real-time information without polling:

| Event | Mechanism | Data |
|-------+-----------+------|
| CWD change | =precmd= → =report_pwd= | New directory path |
| Git branch | =precmd= → async =git rev-parse= → =report_git_branch= | Branch + dirty flag |
| PR status | Polling loop (45s) → =gh pr view= → =report_pr= | PR number, URL, state |
| Port detection | =preexec= → =ports_kick= | Active listening ports |
| Shell activity | =preexec= → =running=, =precmd= → =prompt= | Running vs idle |
| TTY name | Once on init → =report_tty= | =/dev/ttys042= |

** Gaps and Opportunities

*** Critical Gaps

| Gap | Impact | Fix Effort |
|-----+--------+------------|
| Permission notification uses iTerm2 function | cmux sessions call wrong backend | Low — create =claude-org-cmux--permission-needed= |
| No session recovery after Emacs restart | Lost sessions can't reconnect | Medium — scan org buffers for =CMUX_SURFACE_ID= |
| No stale workspace cleanup | Old workspaces accumulate in cmux | Low — close workspace on new session create |

*** Efficiency Opportunities

| Opportunity | Current | Improvement |
|-------------|---------|-------------|
| Ready detection | =while= polling =capture-pane= every 1s (up to 30s) | Use =wait-for= or =pipe-pane= for event-driven detection |
| Status monitoring | Hook file + =capture-pane= fallback | Use =claude-hook= native status (already in sidebar) |
| Sidebar feedback | Only =set-status "agent" "Running..."= | Use =log=, =set-progress=, =report_meta_block= for richer feedback |
| Response extraction | Python reads JSONL transcript via file | Could use =read-screen --scrollback= for simple responses |

*** Unused Capabilities

| cmux Feature | Potential Use in Our Workflow |
|--------------|------------------------------|
| =browser.*= automation | Test web UIs, preview Phoenix traces |
| =markdown.open= | Show design docs / research in cmux sidebar |
| =pane.create= / =surface.split= | Add a monitoring pane alongside Claude Code |
| =notification.create_for_target= | Native cmux notifications (supplement macOS ones) |
| =report_meta_block= | Show rich agent progress in sidebar |
| Shell integration data | Read CWD/git/ports from sidebar state instead of probing |

* Lessons for Emacs AI Block Execution

** Lesson 1: Let the Terminal Tool Do Terminal Work

cmux delegates ALL PTY management to Ghostty. It doesn't implement scrollback,
resize, or terminal rendering — it wraps an expert tool. Similarly, our Emacs
backend should delegate terminal operations to cmux via its CLI and not try to
reimplement screen scraping or output parsing when cmux provides structured APIs.

** Lesson 2: Event-Driven > Polling

cmux's shell integration pushes state changes to the socket. Our backend polls
=capture-pane= every 1 second in =wait-for-ready=. The =wait-for= command and
=pipe-pane= output streaming could eliminate this polling entirely.

** Lesson 3: The Sidebar Is an Agent Dashboard

cmux's sidebar isn't just a tab list — it's an agent observability dashboard with
status entries, progress bars, logs, git state, PR status, and listening ports.
We use only =set-status= and =set-progress=. The =log=, =report_meta_block=, and
=report_meta= commands could provide much richer feedback during AI block execution:

#+begin_example
  [claude_code]  Running (bolt icon, blue)
  [query]        "Implement feature X" (meta entry)
  [progress]     ████████░░ 80% — 4/5 TODOs done (progress bar)
  [log]          14:32 Starting code review... (log entry)
  [log]          14:33 Found 3 issues (log entry)
  [log]          14:34 All tests passing (success log)
#+end_example

** Lesson 4: =claude-hook= Is the Canonical Claude Code Integration

cmux ships a complete Claude Code hook handler (=claude-hook=) that manages
session state, sidebar status, and notifications. Our =sdd-bridge= duplicates
some of this. We should understand what =claude-hook= does natively and avoid
conflicting with it.

Currently: =claude-hook= and =sdd-bridge= BOTH fire on the same hook events.
=claude-hook= manages cmux sidebar. =sdd-bridge= manages Emacs org integration.
They coexist because =claude-hook= is registered in cmux's =settings.json= and
=sdd-bridge= is registered in our plugin's =hooks.json=. No conflict as long as
both hooks return successfully.

** Lesson 5: Session Persistence Enables Recovery

cmux persists session state (=ClaudeHookSessionStore= in JSON with =flock=)
including workspace/surface mappings, PIDs, and timestamps. After Emacs restart,
we lose our in-memory hash tables. We could either:
- Read cmux's session store file (=~/.cmuxterm/claude-hook-sessions.json=)
- Scan org buffers for =CMUX_SURFACE_ID= properties (like iTerm2 backend does)
- Call =cmux tree --all= to discover all living workspaces

** Lesson 6: Browser Automation Is Available

cmux has 50+ browser automation methods (click, type, fill, screenshot, evaluate
JS, wait for selectors, manage cookies/storage). This could enable:
- Automated Phoenix trace verification in E2E tests
- Web UI testing for projects with web frontends
- Screenshot capture for documentation
