** Web Research

*** Session Granularity: What Works

Power users converge on *one session per concern/role*, not per-story and not per-repo:

- *Claude Squad* (5.1k stars): TUI managing multiple Claude Code sessions in tmux,
  each in its own git worktree. Common topology: one agent per open PR.
- *Ralph method* (Geoffrey Huntley): ~while :; do cat PROMPT.md | claude; done~ —
  extreme persistent session, one concern running indefinitely.
- *Atomic framework* (flora131): shipped 100k LOC in 2 weeks with 50 concurrent
  agents. Key rule: "Each agent implements ONE feature then stops."

Practical session topology that practitioners describe:
- Dev session: long-running, focused on current work
- Review session: separate, read-only review
- Deploy session: short-lived, invoked for release

*** Context Management

Three-artifact bridge (Anthropic's recommendation):
1. Feature list (JSON) — 200+ items with pass/fail, machine-readable
2. Progress file — decisions made, approaches tried, what failed
3. Git history — clean, mergeable states

Compaction is "momentum preservation, not summarization" (Jason Liu).
Specialized compaction prompts preserve direction, not just facts.

Deterministic startup ritual (Anthropic):
1. ~pwd~ — establish context
2. Read git log + progress file
3. Consult feature list — pick highest-priority incomplete item
4. Run init script — verify environment
5. Run baseline tests — confirm nothing is broken

"Agents that skip the startup ritual spend substantial time guessing."

*** Multi-Agent Orchestration

Separate agents by *role*, not by task parallelism:

| Agent Role | Purpose | Tools |
|------------|---------|-------|
| Locator | Find WHERE files live | Glob, Grep, LS |
| Analyzer | Understand HOW code works | Glob, Grep, Read |
| Implementer | Write code, one feature | All tools |
| Reviewer | Read diffs, check quality | Read-only |

Critical rule: research agents never touch code. Implementation agents
never do research. Roles communicate through artifacts (files, JSON),
not shared memory.

*** Autonomy Tradeoffs

The "40-60 Rule" (widely cited):
#+begin_quote
Agents get you 40-60% of the way there. Humans provide the remaining
polish through: reviewing specs before implementation, reviewing code
after each feature, managing context between steps.
You own the decisions. Agents own the execution.
#+end_quote

Human checkpoints where practitioners always intervene:
1. After research, before design (architectural decisions)
2. After spec, before implementation (scope approval)
3. After each feature completes (quality gate)
4. When circuit breaker opens (agent is stuck)

*** Harness > Model

Can.ac measured: harness improvement (same model, no prompt changes)
improved task completion from 6.7% to 68.3%. The model is rarely the
bottleneck; the feedback environment is.

LangChain "reasoning sandwich": 66.5% vs 53.9% completion using same
model, varying only reasoning allocation across phases.

** Community Patterns

*** Claude Squad — Multi-Session TUI
GitHub: smtg-ai/claude-squad (5.1k stars)
- Each session gets its own git worktree
- tmux panes show live output from all agents
- Session state persists; can pause/resume
- Pattern: one agent per PR

*** Continuous Claude — Autonomous PR Workflow
GitHub: AnandChowdhary/continuous-claude (825 stars)
- Claude Code runs in CI, picks up issues, creates branches, implements, opens PRs
- Human only approves PRs — completely async

*** Ralph Orchestrator — Production Loop Infrastructure
- Circuit breaker (CLOSED/HALF_OPEN/OPEN) prevents runaway loops
- ~CB_NO_PROGRESS_THRESHOLD=3~ — open after 3 loops without file changes
- ~CB_SAME_ERROR_THRESHOLD=5~ — open after 5 loops with same error
- Semantic response analysis detects real vs. declared completion

*** AGENTS.md as Failure Log (Mitchell Hashimoto)
"Each line in that file is based on a bad agent behavior."
Not documentation — curated list of past failures. Start with zero lines,
grow only after real failures. This is exactly what ~.claude/rules/~ does
in the claude-agent project.

*** Progressive Disclosure (alexop.dev)
Agents get dumber with more upfront information. "Context rot" — irrelevant
tokens actively degrade reasoning.
- Layer 1 (always loaded): CLAUDE.md, max 50-60 lines, ~500 tokens
- Layer 2 (task-relevant): docs loaded when agent needs domain knowledge
- Layer 3 (specialist): agent definitions running in isolated contexts

** Emacs-Specific Patterns

*** gptel — Dominant Emacs LLM Package
- "Chat in a buffer" model, backend-agnostic
- ~gptel-context~ system: add buffers/regions as context before asking
- Org-mode as interaction surface: prompts as plain text, responses stream inline
- Per-buffer system prompts: different personas for different tasks

*** org-ai — Most Org-Native Approach
- ~#+begin_ai~ blocks become interactive sessions
- Conversation threads stored in .org files, navigable via outline

*** Emacs as Control Plane — The Architecture
#+begin_example
Emacs (coordinator)
├── Spawns/controls: Claude Code CLI subprocess
├── Reads: JSON stream output (newline-delimited JSON)
├── Controls: external terminal (cmux via Unix socket)
├── Exposes: MCP server for AI tool calls back into Emacs
└── Stores: session state in org properties (persistent)
#+end_example

Bidirectional control (Emacs → Claude, Claude → Emacs via MCP) is unique.

*** Key Distinction: Emacs AI vs IDE AI
Three things separate Emacs AI integration:
1. *Org-mode as universal interface* — document, database, programming env,
   task manager, and presentation format in one system
2. *Bidirectional control via MCP* — AI is a participant in the same
   environment, not a separate tool
3. *Inspectability* — every part visible: process buffers, JSON streams,
   Elisp callbacks, org properties

** Lisp/Hacker Patterns

*** REPL-Driven Development as AI-Native
The Lisp REPL and AI conversation have the same shape:
- Try something → see what happens → refine
- Code and data are both S-expressions; AI assistance fits naturally
- CL image persistence parallels AI session continuity (~--resume~)
- ~evalElisp~ via MCP is REPL-driven development where the "REPL user" is Claude

*** The Living Document as Smalltalk Image
Smalltalk's image-based persistence (running env IS saved state) parallels
org-mode literate programming:
- The .org file IS the program, documentation, AND session history
- Reloading via ~literate-elisp-load~ is like recompiling a method —
  the rest of the running system is unaffected
- AI-generated sections mix with human-written sections, like Smalltalk
  images mix compiled methods with interactive changes

*** Incremental, Verifiable Development
Lisp hackers distrust "big bang" rewrites:
- Never let agent work on the entire project at once
- Decompose into verifiable phases
- Test each function before assembling (656+ tests in claude-agent)
- The pre-commit hook is the mechanical expression of this

*** Hammock-Driven Development + AI (Rich Hickey)
- Use AI for information gathering phase (survey alternatives, explain tradeoffs)
- Do the "hammock time" yourself (design decisions require human judgment)
- Return with a clear plan, using AI to execute efficiently
- Maps to: research doc → design doc → implementation (current SDD flow)

*** Developer Experience Philosophy
- "Efficient" (fewest keystrokes) vs "Comfortable" (low cognitive load, control)
- Emacs users optimize for comfort — explicit, inspectable, user-controlled
- Token streaming reduces "dead waiting" that breaks concentration
- Live output mirror embodies Bret Victor's "immediate connection" principle
- Flow state: AI responses in same buffer as code (no window switching)

*** UX/Philosophy Deep Dive (Iter 8)

**** The Three Developer Loops (Kim & Yegge, IT Revolution)

A framework that maps perfectly onto the four designs:

| Loop | Timescale | AI Role | Design Mapping |
|------+-----------+---------+----------------|
| Inner | seconds-minutes | Request-output-verify | Design B (REPL) |
| Middle | hours-days | Context persistence | Design A (workspace) |
| Outer | weeks-months | Architecture boundaries | Design C (gates) |

Key insights:
- Inner loop: "AI should write tests as part of its specification process"
  — verification is the human's new primary inner-loop activity
- Middle loop: external memory systems (AGENTS.md, org properties) maintain
  continuity across sessions — validates Design A's workspace persistence
- Outer loop: humans prevent "stewnamis" — catastrophic collisions between
  parallel AI agents. Design D needs coordination mechanisms.
- *4x commit frequency*: AI workflows need frequent checkpoints for rollback.
  All designs should default to more granular commits.

**** Bret Victor's Liveness Principle

Victor's core insight: "creators need an immediate connection between what
they imagine and what they see. Latency destroys creative flow."

Applied to our designs:
- *Design B* (REPL) most directly embodies liveness — type a prompt,
  see the result immediately in the same buffer
- *Design C* (autonomous loop) sacrifices liveness for autonomy — the
  human reviews after the fact, losing the "immediate connection"
- *Design D* (hybrid) can preserve liveness in interactive mode while
  allowing asynchronous autonomous work

Victor's "bricolage programming" (Turkle & Papert 1990s):
- Building understanding by tinkering, not by designing upfront
- Matches the REPL/notebook mode: write a prompt, see what happens,
  adjust, repeat — this IS tinkering
- Contrasts with Design C's specification-first approach

Design implication: *default to interactive (liveness), escalate to
autonomous only when the task is well-understood and specification-ready.*

**** Rich Hickey's Background Mind

Hickey's hammock-driven development thesis:
- "Your background mind is where you solve most non-trivial problems"
- You can only *feed* it, not *direct* it
- "You need to get away from the computer" — close eyes, switch brain
  from external to internal input

Applied to AI workflows:
- AI excels at the information-gathering that *feeds* the background mind
  (research agent, web search, codebase analysis)
- But AI cannot do the hammock time for you — design decisions require
  human reflection away from the screen
- *The SDD research → design → implement flow already maps to this*:
  research feeds the background mind, design is hammock time, implement
  is execution

Implication for our designs:
- Don't make the workflow so efficient that it eliminates thinking time
- Design B's interactive mode naturally creates pauses (read response,
  think, write next prompt) — these pauses ARE thinking time
- Design C's autonomous mode risks eliminating thinking — the agent runs,
  the human reviews, but *when does the human think?*
- Design D should include an explicit "reflect" phase between autonomous
  loop completion and the next task specification

**** Flow State in the AI Era

Key findings from 2025-2026 research:
- *Flow = verify, not write*: In AI-assisted development, the flow state
  shifts from writing code to verifying AI output. The developer's skill
  becomes evaluation speed, not typing speed.
- *"Vibe coding"*: immersive, emotionally aligned programming where tools
  adapt to your pace — AI suggests in rhythm, predicts context switches
- *Environment design for flow*: minimize friction between engineer and
  work. Context switching is the primary flow killer. All designs should
  minimize context switching — especially between Emacs and terminal.
- *AI deepens flow* when it handles routine work (boilerplate, test
  scaffolding) while the human focuses on design and verification
- *AI breaks flow* when it requires constant supervision ("agent babysitting")
  or when latency exceeds ~10 seconds between action and feedback

Design principle: *the best AI workflow is one where the human barely
notices the AI is there — it just makes the work flow faster.*

* Design Proposals

** Design A: Workspace-Bound Agents (Role-Based)

*** Concept
Replace per-story sessions with *per-workspace roles*. Each cmux workspace
runs a persistent Claude Code bound to a concern (dev, review, deploy),
not a story. Org-mode serves as a shared journal, not a session controller.

*** How It Works
- *Dev workspace*: one long-running Claude Code, handles all dev tasks
  for the repo. No session restart between tasks.
- *Review workspace*: dedicated to PR review. Receives review requests
  from dev workspace via ~cmux send~.
- *Deploy workspace*: handles CI monitoring, deployment, release.
- *Org journal*: a single ~PROJECT-log.org~ file per repo that captures
  what happened, not what to do. Auto-appended by hooks.
- *Session continuity*: Claude Code's built-in ~--resume~ handles
  context across restarts. No org property ceremony.

*** Startup
Open cmux → workspaces already exist → Claude Code auto-resumes.
No story creation step. Start typing.

*** Capture
- Git log IS the capture (commit messages, diffs)
- Hooks auto-append to journal: timestamp + summary of each completion
- ~claude-org-sdd-bridge-insert-response~ writes to journal, not to story

*** Pros
- Zero setup friction — workspaces persist, sessions resume
- Matches actual behavior (you already do this)
- Role separation prevents context pollution
- Cross-workspace communication via ~cmux send~ already works

*** Informed by: Long-Running Agent Research (Iter 4)

Key findings from Zylos Research and CIO articles that strengthen/refine Design A:

- *35-minute degradation*: "every AI agent experiences performance degradation
  after 35 minutes of human time spent on a task." Workspace-bound agents need
  *active session management* — periodic context compaction or session restart
  with state checkpointing, not just indefinite ~--resume~.

- *Planner-Worker split*: use frontier model (Opus) for planning/architecture,
  cheaper model (Sonnet/Haiku) for repetitive execution. In Design A, the dev
  workspace could run Opus for design decisions and auto-delegate boilerplate
  to a Sonnet subagent.

- *State checkpointing* (LangGraph pattern): save agent state at regular
  intervals so it can recover from crashes or context exhaustion. In Design A,
  this maps to: org properties + git commits as checkpoints. On session restart,
  the startup ritual reads these checkpoints.

- *Role taxonomy convergence*: industry converges on Researcher / Writer /
  Reviewer / Integrator. Maps directly to cmux workspace roles:
  dev=Writer, review=Reviewer, deploy=Integrator. Could add a research workspace.

- *Creator → Curator shift*: "engineer of 2026 spends less time writing code
  and more time orchestrating AI agents." Design A's journal-based capture
  supports this — the human curates, the agent executes.

*** Cons
- Loses org-mode as the *driving* interface (becomes passive journal)
- Long sessions accumulate context debt — need periodic ~--resume~ with compaction
- 35-minute degradation means sessions need active management, not just persistence
- No natural "story boundary" for review — when is a unit of work "done"?
- Journal can become a dumping ground without structure

** Design B: Literate Agent Notebook

*** Concept
Double down on org-mode as the primary interface, but simplify it.
Remove SDD ceremony. AI blocks become an inline REPL — think Jupyter
notebook meets Lisp image, where the .org file IS the development
environment.

*** How It Works
- *One .org file per project* with simple sections (not SDD stories):
  ~* Tasks~, ~* Research~, ~* Notes~
- *AI blocks as REPL*: ~#+begin_src ai~ blocks are just prompts.
  No session IDs, no backend properties. The system auto-selects
  the workspace's Claude Code.
- *Response capture*: AI responses appear as org subsections below
  the block (existing behavior), but with auto-generated TODO items
  extracted from the response.
- *Background execution*: long tasks run autonomously; a modeline
  indicator shows status. Results written back when done.
- *Session binding*: workspace ↔ org file is implicit (based on
  ~default-directory~), not explicit (no org properties).

*** Startup
Open the project .org file → write a prompt → C-c C-c → done.
The system finds (or creates) the appropriate cmux workspace.

*** Capture
- The .org file itself is the capture — prompts + responses + your notes
- ~org-archive~ moves completed work to archive
- Search with ~org-occur~ or ~consult-org-heading~

*** Pros
- Org-mode remains the driving interface (Emacs-native comfort)
- Near-zero ceremony — write prompt, execute, get response
- Natural capture: the conversation IS the document
- Familiar to any org-mode user — no new concepts
- Literate programming philosophy preserved

*** Informed by: Literate + REPL Research (Iter 5)

- *Literate programming solves the AI context bottleneck* (byteiota.com):
  "Context engineering has replaced prompt engineering as the critical
  bottleneck for AI coding success in 2026." Literate programming embeds
  intent alongside code — AI agents see *what* and *why* simultaneously.
  Design B's org-as-notebook naturally provides this.

- *AI reverses the 40-year literate programming failure*: LP failed because
  humans had to maintain prose-code sync. AI agents handle sync automatically.
  Design B leverages this — agent maintains the org document, not just code.

- *SYNERGY REPL* (logicgrimoire.wordpress.com): A REPL for AI assistants
  with Forth-inspired context stack (~,push~, ~,swap~, ~,rot~, ~,drop~ for
  file context). Key insight: REPL > TUI because "select any arbitrary text
  in any arbitrary buffer and send it to the subprocess for evaluation."
  Design B's ai blocks are org-native REPLs — even more integrated than
  SYNERGY because they live in the document itself.

- *Forth-inspired context stack for Design B*: SYNERGY's ~,push file~ /
  ~,drop~ pattern could inspire an org-mode context system:
  - ~C-c C-a~ to add current buffer/region to AI context
  - Context shown in header-line or modeline
  - ~C-c C-d~ to drop last context item
  - This replaces the need for explicit ~gptel-context~ ceremony

- *gptel-agent* described as "the best way to do agentic AI workflows if
  you're already an Emacs user" — validates Design B's direction of
  doubling down on Emacs-native AI interaction.

- *Limitation*: literate programming "adds overhead for routine CRUD" and
  "only pays off when code complexity justifies narrative structure."
  Design B should support a lightweight mode for simple queries (no prose
  required) alongside full literate mode for complex work.

*** Cons
- .org file grows large — need archiving discipline
- Single file per project may not scale for large teams
- Loses explicit role separation (all prompts go to same agent)
- ~--resume~ management is implicit (may surprise user)
- Less autonomous — user is always driving
- Literate overhead may not be justified for simple CRUD tasks

** Design C: Autonomous Loop + Review Gate

*** Concept
Maximum autonomy with structured review gates. The agent runs a loop
(implement → test → fix) autonomously. Human reviews at defined gates
via org-mode checklist. Capture via git + auto-generated org summary.

*** How It Works
- *Task specification*: user writes a brief spec in org TODO item
  with acceptance criteria (checkboxes)
- *Autonomous loop*: Claude Code runs with circuit breaker:
  - implement → run tests → if fail, fix → repeat
  - max iterations (configurable, default 10)
  - halt on: N consecutive failures, no file changes, same error repeated
- *Review gate*: when loop completes (success or circuit break),
  Emacs generates a review buffer:
  - git diff of all changes
  - test results summary
  - agent decision log (extracted from Claude Code output)
  - org TODO with checkboxes for approval
- *Human review*: user checks diff, marks TODO as DONE or REJECTED
  - DONE: changes committed, next task starts
  - REJECTED: user adds feedback, loop restarts with feedback

*** Startup
Write TODO with acceptance criteria → ~C-c C-c~ → agent runs
autonomously → notification when review gate reached.

*** Capture
- Git commits at each gate (clean, reviewable)
- Auto-generated org summary: what changed, what was tried, decisions made
- Circuit breaker events logged (why agent stopped)

*** Pros
- Maximum autonomy — agent runs while you do other work
- Structured review gates prevent drift
- Circuit breaker prevents runaway loops
- Good capture: git + auto-summary covers both "what" and "why"
- Scales to parallel tasks (multiple TODOs running simultaneously)

*** Informed by: Autonomous Loop Research (Iter 6)

- *Plan-Execute-Verify-Iterate cycle* (daviddaniel.tech): The fundamental
  autonomous loop. Key insight: agents must run actual code and observe real
  failures — abstract reasoning about errors is insufficient. "Execution-grounded
  feedback" is critical.

- *Specification-driven completion, not time-bound*: the loop runs until "the
  specification is met." This validates Design C's org TODO checkboxes as
  acceptance criteria — the agent checks them off, the loop ends.

- *Sobering data*: "38% of autonomous agent PRs passed automated tests, but
  none were mergeable without human modification" (METR study). This confirms
  that review gates are NOT optional — they're architectural requirements.
  Design C's review gate is validated as essential, not overhead.

- *Review burden increased 91%* under high AI adoption (Faros AI data).
  Review shifts from micro-reviews to holistic evaluation. Design C should
  provide *structured review aids* (not just raw diffs) to manage this burden:
  - Annotated diff (agent explains each change)
  - Test result matrix (what passed/failed/new)
  - Decision log (why agent chose this approach)

- *State machine workflow* (vellum.ai): Formal state progression:
  INTENT → SPEC → PLAN → IMPLEMENT → VERIFY → DOCS → REVIEW → RELEASE.
  "Agents may advance states only when deterministic gates pass and policy
  allows." Design C's review gate should be one of several gates — not just
  at the end, but also after SPEC and PLAN phases.

- *Fresh context per iteration* (Ralph pattern): spawn new sessions per
  iteration, persist state via git/filesystem. This avoids the 35-minute
  degradation problem from Design A research. Design C naturally fits this
  because each loop iteration can be a fresh Claude invocation.

- *42 minutes*: average estimated fix time per autonomous PR in production
  review (METR study). Budget expectation for autonomous work units.

*** Cons
- Requires good test infrastructure (agent needs automated feedback)
- Review gates add latency — you must review before next task
- Review burden increases 91% — need structured review aids, not just diffs
- Auto-generated summaries may miss nuance
- Circuit breaker tuning is trial-and-error
- 38% pass rate means human polish is always needed — set expectations
- Less interactive — you're reviewing, not collaborating

** Design D: Hybrid — The Lisp Image Model (Revised)

*** Concept
Combine the best elements: org as REPL (Design B) for interactive work,
autonomous loops (Design C) for delegated work, workspace roles (Design A)
for separation. The mental model is a Lisp image — a living, persistent
environment you incrementally modify.

*Key refinement*: keep stories as lightweight org subsections under a
workspace heading. Stories organize work on the Emacs side; the cmux
workspace + Claude Code session is the persistent execution unit they
all share.

*** Org Structure: Workspace → Stories

#+begin_example
  * claude-agent-dev                              ← workspace heading
  :PROPERTIES:
  :CMUX_WORKSPACE: claude-agent-dev               ← binds to cmux workspace
  :END:

  ** Fix parser bug                                ← story (lightweight)
  :PROPERTIES:
  :STORY_STATUS: DONE
  :END:
  *** Workflow
  #+begin_src ai
  please fix the parser bug in claude-agent.org...
  #+end_src
  **** Response                                    ← captured response
  ...

  ** Add new API endpoint                          ← another story, same workspace
  :PROPERTIES:
  :STORY_STATUS: IN-PROGRESS
  :END:
  *** Research
  #+begin_src ai
  what patterns exist for REST endpoints in this codebase?
  #+end_src
  *** Workflow
  #+begin_src ai
  implement the /health endpoint with...
  #+end_src

  ** TODO Refactor session management              ← autonomous task (has checkboxes)
  - [ ] Extract shared code into base module
  - [ ] Update tests
  - [ ] Run make check

  * claude-agent-review                            ← separate workspace
  :PROPERTIES:
  :CMUX_WORKSPACE: claude-agent-review
  :END:

  ** PR #42 review                                 ← review story
  #+begin_src ai
  please review PR #42...
  #+end_src
#+end_example

*** Key Design Decisions

- *Top-level heading = cmux workspace*: one Claude Code session, bound
  via ~CMUX_WORKSPACE~ property. The only required property.
- *Sub-headings = stories*: lightweight organizational units. Just a heading,
  optional ~STORY_STATUS~ property. No session IDs, no backend properties.
- *Stories share the workspace's Claude Code*: all ai blocks under a workspace
  heading route to the same Claude Code session. No session restart between stories.
- *Story lifecycle managed in org*: TODO/DONE, tagging, archiving, notes — all
  org-native. ~org-archive-subtree~ moves completed stories to archive.
- *Workspace lifecycle managed in cmux*: persistent, auto-resume. Workspace
  outlives any individual story.
- *One active story per workspace at a time*: the workspace tracks which story
  currently owns the Claude Code session. See Story-Aware Routing below.

*** Story-Aware Routing

Two critical problems: (1) preventing story collisions when multiple stories
exist under one workspace, and (2) routing Claude Code responses back to the
correct story subsection.

**** Problem 1: Story Collision Prevention

One workspace = one Claude Code = one active story at a time.

When user executes ~C-c C-c~ on an ai block:

#+begin_example
  1. Find workspace heading (nearest ancestor with CMUX_WORKSPACE)
  2. Find story heading (nearest ancestor sub-heading under workspace)
  3. Is workspace busy?
     NO  → Set ACTIVE_STORY property on workspace heading
           → proceed with execution
     YES → Is it the SAME story?
           YES → queue (existing behavior)
           NO  → WARN: "Workspace busy with story 'Fix parser bug'.
                  [w]ait, [q]ueue after current, [i]nterrupt?"
                  - wait: do nothing, user decides when to retry
                  - queue: queue this ai block, execute after current story's
                    request completes
                  - interrupt: send Ctrl+C to Claude Code, then execute new story
#+end_example

The ~ACTIVE_STORY~ property on the workspace heading tracks which story
currently owns the Claude Code:

#+begin_example
  * claude-agent-dev
  :PROPERTIES:
  :CMUX_WORKSPACE: claude-agent-dev
  :ACTIVE_STORY: Fix parser bug         ← auto-set, auto-cleared
  :END:
#+end_example

When the request completes (response finished), clear ~ACTIVE_STORY~.
The workspace is now available for any story.

**** Problem 2: Response Routing — Which Story Gets the Response?

This is the harder problem: when Claude Code calls back to Emacs (via MCP
hooks or SDD bridge), how does it know where to insert the response?

Three channels of interaction, each with different routing:

**Channel A: ai block execution (Emacs → Claude Code → Emacs)**

#+begin_example
  C-c C-c on ai block under "** Fix parser bug"
  1. Emacs records: request-id → {buffer, story-marker, insert-point}
  2. Emacs sets env: SDD_STORY_HEADING="Fix parser bug"
  3. Emacs sends prompt to workspace's Claude Code
  4. Claude Code processes, streams response
  5. Response arrives → look up request-id → find story-marker
  6. Insert response as subsection under "Fix parser bug"
#+end_example

This is similar to current behavior (request-id based routing), but keyed
to a *story marker* instead of a *session*. The story marker is an org
marker pointing to the story heading — survives buffer modifications.

**Channel B: Direct cmux input (user types in terminal)**

#+begin_example
  User switches to cmux terminal, types directly to Claude Code.
  Claude Code has no org context — it's just a terminal session.

  Response routing options:
  a) Use ACTIVE_STORY if set → insert under that story
  b) No ACTIVE_STORY → don't route to org, capture in workspace journal
  c) Claude Code MCP hook reads ACTIVE_STORY from org → knows context
#+end_example

Recommended: option (c). When Claude Code starts processing (via SDD hook),
it calls ~evalElisp~ to read the workspace's ~ACTIVE_STORY~ property:

#+begin_src elisp :load no
;; Claude Code SDD hook calls this to determine current story
(defun claude-org-get-active-story (workspace-name)
  "Return the active story heading for WORKSPACE-NAME, or nil."
  (claude-org-terminal--find-session-property
   workspace-name "ACTIVE_STORY"))
#+end_src

If ~ACTIVE_STORY~ is set, Claude Code includes the story heading in its
response metadata, and Emacs routes the response there.
If nil, response goes to workspace journal.

**Channel C: Event-driven hooks (background)**

#+begin_example
  on-commit hook fires → auto-journal entry

  Routing: always append to ACTIVE_STORY if set,
  otherwise append to workspace-level journal.
  Hook output is lightweight (one-line summary), so
  appending under the wrong story is low-risk.
#+end_example

**** Story Context for Claude Code

When executing an ai block, Emacs prepends the story heading as context
so Claude Code knows what it's working on:

#+begin_example
  [Story: Fix parser bug]

  please fix the parser bug where nested quotes are not handled...
#+end_example

This is a lightweight prefix — not a system prompt change, just prepended
to the user's prompt text. Claude Code sees it and can reference it in
responses. For direct cmux input, the SDD hook can inject this prefix
by reading ~ACTIVE_STORY~ from Emacs.

*** How It Works
- *Workspace roles*: dev / review / deploy — each a top-level heading
  bound to a cmux workspace
- *Interactive mode*: write in ai block under any story → ~C-c C-c~ →
  routes to the workspace's Claude Code (Design B)
- *Autonomous mode*: write TODO with checkboxes under a story →
  ~C-c C-c~ → autonomous loop with circuit breaker (Design C)
- *Mode switching*: same workspace, same Claude Code, different interaction
  patterns based on task type:
  - Exploratory? → Interactive (ai block under story, immediate response)
  - Well-defined? → Autonomous (TODO with checkboxes, review gate)
  - Review? → Cross-workspace (cmux send to review workspace)
- *Story navigation*: ~org-occur~, ~consult-org-heading~, or sparse tree
  to find work across stories
- *Journal*: auto-maintained per workspace. Each ai block completion
  appends a timestamped entry under the story heading.

*** Startup
Open project org file → navigate to story → write in ai block → ~C-c C-c~.
System finds workspace from nearest ancestor ~CMUX_WORKSPACE~ property.
If workspace doesn't exist in cmux, auto-create it.

*** Capture
- *Per-story*: ai blocks + responses captured under the story heading
- *Per-workspace*: git commits, auto-journal
- *Searchable*: ~org-occur~ across stories, git log for commits,
  ~org-agenda~ for TODO stories
- *Archivable*: ~org-archive-subtree~ moves completed stories cleanly

*** What Stories Give You (vs. flat workspace)
- *Context when you return*: re-read the story heading and its ai blocks
  to remember what you were doing — the conversation IS the context
- *Parallel stories*: multiple threads of work organized under one workspace,
  each with its own ai block history
- *Review scope*: a story defines a reviewable unit of work — "this story
  is done, review it"
- *Archive*: completed stories move to archive, keeping the main file clean
- *Org-agenda integration*: TODO stories appear in agenda views

*** What Stories DON'T Do (vs. current SDD)
- No per-story Claude Code session — all stories share the workspace session
- No per-story session ID or backend properties
- No per-story system prompt — the workspace's Claude Code has one context
- No story creation ceremony — just create a heading

*** Pros
- Adapts to task type — interactive when exploring, autonomous when clear
- Preserves org-mode as *both* organizing interface AND driving interface
- Stories provide structure without ceremony
- Role separation via workspaces (top-level headings)
- Best capture: per-story in org, per-workspace in git + journal
- Matches Lisp philosophy: incremental, verifiable, living environment
- Low ceremony for simple tasks, structured for complex ones
- Familiar to current SDD users — stories are just simpler
- ~org-archive-subtree~ cleanly manages story lifecycle

*** Cons
- Most complex to implement (mitigated by phased migration — see Recommended Hybrid)
- Three interaction modes may cause cognitive switching (mitigated by simple heuristic — see Mode Detection)
- Shared Claude Code context across stories means agent may confuse stories
  if multiple are active (mitigate: ai block includes story heading as context)
- Auto-journal may produce noise without curation (mitigated by per-story journal)
- See *Recommended Hybrid* section for the refined version of this design

* Missed Pattern: Event-Driven Agents (Iter 7)

A pattern not covered in Designs A-D: *reactive, event-driven agents* triggered
by hooks rather than user prompts or loops.

*** How It Works
- Claude Code hooks (~PreToolUse~, ~PostToolUse~, ~Notification~) trigger
  agent actions automatically
- Git hooks (~post-commit~, ~pre-push~) invoke AI for review/lint/test
- File watchers trigger AI on save (auto-format, auto-test, auto-doc)
- The agent is *dormant* until an event fires — no persistent session needed

*** Key Insight (Confluent, Oracle)
Event-driven decouples agents: each maintains a single connection to the
event bus (O(n)) vs point-to-point (O(n^2)). Enables independent scaling
and loose coupling between workspace roles.

*** Relevance to Design D (Hybrid)
Event-driven is a *third interaction mode* alongside interactive (REPL) and
autonomous (loop). Design D could add:
- ~on-commit~: auto-run tests, update journal
- ~on-push~: trigger review workspace
- ~on-test-fail~: auto-fix loop with circuit breaker
- ~on-idle~: context compaction, doc generation

This is the "daemon" layer — always-on background intelligence.

* Recommended Hybrid: The Living Workspace (Iter 9)

** Vision

A *living workspace* — like a Lisp image — where the development environment
is persistent, incrementally modifiable, and adapts to how you work. Three
interaction modes map to the Three Developer Loops. The system defaults to
liveness (Bret Victor) and preserves thinking time (Rich Hickey).

** The Three Modes

*** Mode 1: Interactive REPL (Inner Loop — seconds to minutes)
From Design B. The *default* mode.

- Write in ~#+begin_src ai~ block → ~C-c C-c~ → response streams inline
- Zero ceremony: no session IDs, no backend properties, no story creation
- Auto-selects the dev workspace's Claude Code (implicit binding by ~default-directory~)
- Org file captures the conversation — prompts + responses = living document
- Forth-inspired context stack: ~C-c C-a~ add buffer/region, ~C-c C-d~ drop
- *Liveness*: sub-10-second feedback loop preserves flow state

When to use: exploration, debugging, quick questions, design thinking,
any task where you don't have clear acceptance criteria.

*** Mode 2: Autonomous Task (Middle/Outer Loop — minutes to hours)
From Design C. *Escalated* when task is well-defined.

- Write TODO with acceptance criteria (checkboxes) → ~C-c C-c~ on TODO
- System detects checkboxes → launches autonomous loop with circuit breaker
- Agent runs: implement → test → fix → repeat (max N iterations)
- On completion or circuit break → Emacs notification + review buffer:
  - Annotated diff (agent explains each change)
  - Test result matrix
  - Decision log
- Human reviews: DONE (commit) or REJECTED (feedback → re-run)
- *Fresh context per iteration* avoids 35-minute degradation

When to use: well-defined features, refactoring with clear specs,
bug fixes with reproducible test cases.

*** Mode 3: Event-Driven Daemon (Always — background)
From the missed pattern (Iter 7). *Always running*.

- Claude Code hooks trigger on events:
  - ~on-commit~: auto-update journal, run smoke tests
  - ~on-push~: trigger review workspace via ~cmux send~
  - ~on-test-fail~: auto-diagnosis with circuit breaker
  - ~on-idle~: context compaction, doc generation
- Git hooks integrate with the autonomous loop
- *Zero user friction*: you don't invoke this mode, it runs itself

When to use: always (it's background infrastructure).

** Workspace Roles (from Design A)

Three persistent cmux workspaces per project:

| Workspace | Role | Primary Mode | Agent Config |
|-----------+------+--------------+--------------|
| Dev | Write code | Interactive + Autonomous | Opus, full tools |
| Review | Review PRs/code | Interactive (read-heavy) | Opus, read-only |
| Deploy | CI/release | Event-driven + Interactive | Sonnet, ops tools |

Workspaces are *auto-created* on first use. No manual setup.
Cross-workspace communication via ~cmux send~ + ~cmux capture-pane~.

** Four Design Principles

1. *Default to liveness* (Victor): interactive mode is always one ~C-c C-c~ away.
   Never require ceremony to start working.

2. *Preserve thinking time* (Hickey): between autonomous task completion and
   next task specification, the system waits. No auto-queue. The pause IS
   the hammock time.

3. *Flow = verify, not write*: the developer's skill is evaluation speed.
   Design the review buffer for fast scanning, not deep reading.
   Annotated diffs, test matrices, decision logs — structured for glanceability.

4. *The harness, not the agent, enforces safety*: circuit breakers, commit
   frequency (4x normal), test gates, and role separation are mechanical —
   not prompt-based. Linters > documentation. Tests > trust.

** Capture Strategy

| What | How | Where |
|------+-----+-------|
| Interactive work | Org file (prompts + responses) | ~PROJECT.org~ |
| Autonomous work | Git commits + auto-summary | Git log + journal |
| Decisions | Agent decision log at review gates | Review buffer → journal |
| Events | Hook output with timestamps | ~PROJECT-journal.org~ |
| Architecture | Human-written design docs | ~docs/design-docs/~ |

Journal is a *separate* file (~PROJECT-journal.org~) auto-appended by hooks.
Main org file stays clean for interactive work.

** Mode Detection Heuristic (answers Open Question #4)

#+begin_example
  User writes in ai block:
    → Has checkboxes / acceptance criteria?
      YES → Autonomous mode (Mode 2)
      NO  → Interactive mode (Mode 1)

  User writes in TODO item:
    → Always Autonomous mode (Mode 2)

  Event fires (hook, git, file change):
    → Always Event-driven mode (Mode 3)
#+end_example

Simple, predictable, no AI-based detection needed.

** Migration Path (answers Open Question #10)

Phase 0 (now, no code changes):
- Stop creating new SDD stories
- Use existing cmux workspaces as role-based (dev/review/deploy)
- Keep using ai blocks as-is — they're already the REPL

Phase 1 (simplify, ~2 weeks):
- Remove mandatory org properties (session ID, backend) — auto-detect
- Implicit workspace binding by ~default-directory~
- Auto-journal hook on query completion
- Keep SDD bridge for backward compatibility

Phase 2 (autonomous mode, ~4 weeks):
- TODO-based autonomous loop with circuit breaker
- Review buffer generation
- Mode detection heuristic

Phase 3 (event-driven, ~2 weeks):
- Claude Code hook integration
- Git hook → review workspace trigger
- Auto-compaction on idle

Phase 4 (polish, ongoing):
- Forth-inspired context stack UI
- Structured review aids (annotated diffs)
- Performance tuning (circuit breaker thresholds)

** Open (need answers during implementation)

1. *Context compaction*: Claude Code's built-in compaction may suffice for
   workspace-bound sessions. Test empirically: does ~--resume~ after 2+ hours
   maintain quality? If not, add org-based "session summary" at compaction.

2. *Circuit breaker thresholds*: start with CB_NO_PROGRESS=3, CB_SAME_ERROR=5
   (Ralph defaults). Tune per-project. Expose as org property or defcustom.

3. *Journal file location*: use separate ~PROJECT-journal.org~ (decided in
   Recommended Hybrid). Main org stays clean for interactive work.

5. *Cross-workspace reliability*: ~cmux send~ + ~capture-pane~ polling works
   but is fragile. Future: add ~cmux~ event subscription (webhook/callback)
   if upstream supports it. For now, polling with exponential backoff.

6. *SDD infrastructure reuse*: high reuse. ai blocks, response insertion,
   MCP server, cmux socket API all carry forward. Remove: per-story session
   management, mandatory org properties, query manager complexity.

8. *Review burden*: implement structured review aids in Phase 2 (annotated
   diffs, test matrices, decision logs). Measure before/after review time.

9. *Cognitive overload*: the three modes have clear triggers (user prompt vs
   TODO vs event). Users don't "choose" — the system detects. Event mode is
   invisible. In practice, users only consciously choose between REPL and TODO.

** Remaining Gaps

- No empirical data on how long cmux workspace sessions maintain quality
  with ~--resume~. Need to test with real workloads.
- Circuit breaker thresholds are borrowed from Ralph; may need different
  values for Emacs/org workflow (shorter iterations, smaller changes).
- Annotated diff generation (agent explains each change) is not yet
  designed — needs a design doc of its own.
- Cross-workspace event subscription (cmux webhook/callback) requires
  upstream cmux changes — not in current fork.
