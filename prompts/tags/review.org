You are performing a *Code Review*. This is a two-stage process that ensures
both correctness (matches spec) and quality (clean, maintainable code).

** Two-Stage Review Process

Reviews MUST follow this order. Stage 2 only runs after Stage 1 passes.

*** Stage 1: Spec Compliance Review

*Purpose*: Verify implementation matches requirements exactly.

Ask yourself:

| Question | Check For |
|----------+-----------|
| Does it match spec EXACTLY? | All requirements implemented |
| No over-building? | Features NOT in spec that were added |
| No under-building? | Requirements in spec that are missing |
| Acceptance criteria met? | All checkboxes satisfiable |

*Over-building examples*:
- Added caching when spec didn't mention it
- Implemented extra endpoints "for future use"
- Added configuration options not in requirements

*Under-building examples*:
- Missing error handling specified in spec
- Skipped a checkbox item
- Partial implementation of a requirement

*Stage 1 Output*:

#+begin_example
Stage 1: Spec Compliance Review

✓ PASS - Implementation matches spec exactly
  - [list what was verified]

OR

✗ FAIL - Spec compliance issues found
  - Over-built: [what was added that shouldn't be]
  - Under-built: [what is missing]
  - Action: Fix these issues before proceeding to Stage 2
#+end_example

*** Stage 2: Code Quality Review

*Purpose*: Ensure code is clean, maintainable, and follows best practices.

*Only run Stage 2 after Stage 1 passes.*

| Category | Check |
|----------+-------|
| *Clean Code* | Good naming, no dead code, appropriate comments |
| *Error Handling* | Errors caught, meaningful messages, no silent failures |
| *Patterns* | Follows existing codebase conventions |
| *Security* | No injection, proper auth, no exposed secrets |
| *Testing* | Adequate coverage, edge cases considered |
| *Performance* | No obvious inefficiencies (but don't over-optimize) |

*Stage 2 Output*:

#+begin_example
Stage 2: Code Quality Review

✓ PASS - Code quality acceptable
  - [list strengths]

OR

⚠ ISSUES - Quality improvements needed
  - [Category]: [specific issue and suggested fix]
  - Action: Address issues before marking complete
#+end_example

** Review Severity Levels

| Level | Meaning | Action |
|-------+---------+--------|
| ✓ PASS | Meets standards | Proceed |
| ⚠ MINOR | Small improvements | Fix if easy, otherwise note for later |
| ✗ FAIL | Must fix | Cannot proceed until resolved |

** Use Cases

*** Standalone Review

#+begin_example
,#+begin_src ai :review:
Please review the changes in src/auth module
,#+end_src
#+end_example

*** With Implementation

#+begin_example
,#+begin_src ai :implementation:review:
Implement the auth feature with thorough review
,#+end_src
#+end_example

Adds detailed review to each feature completion.

*** With Design

#+begin_example
,#+begin_src ai :design:review:
Design the API with review of the approach
,#+end_src
#+end_example

Reviews design decisions against requirements.

** Self-Review vs External Review

This tag supports both:

| Mode | When | Reviewer |
|------+------+----------|
| Self-review | During =:implementation:= | Claude reviews own work |
| External review | Standalone =:review:= | Claude reviews existing code |

For self-review, be honest and critical. Don't rationalize issues.
