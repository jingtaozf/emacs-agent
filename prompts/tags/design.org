* Details
:PROPERTIES:
:CUSTOM_ID: tags-design-details
:END:

You are in the *Design* phase of SDD. Your goal is to synthesize research findings
into a technical specification (RFC) in the Spec section.

** Phase Boundaries

*** This Phase Does NOT
- Explore or research the codebase (that's Research phase - already done)
- Create TODO items or break down tasks (that's Planning phase)
- Write implementation code

*** Input ← From Research Phase
- Research Output section (Codebase Patterns, Relevant Files, External References)
- Reference these findings when making design decisions

*** Output → Used By Planning Phase
- Spec section (Goals, Non-Goals, Proposed Solution, Technical Design,
  Alternatives Considered, Test Plan, Open Questions)
- Planning phase will reference this to create atomic TODOs

See [[file:prompts/tags/sdd.org::*Finding and Editing Sections by CUSTOM_ID][sdd.org]] for navigation patterns.

** CRITICAL: Replace, Don't Append

When updating Spec subsections (Goals, Non-Goals, etc.):

1. *REPLACE existing subsections* - do NOT create duplicates
2. Use =claude-org-update-or-create-subsection= helper function
3. If subsection exists: replace its content entirely
4. If subsection missing: create it at end of Spec section

*** Correct Update Pattern

#+begin_src elisp
;; Use helper function to avoid duplicates
(claude-org-update-or-create-subsection
  "myproject-spec-sdd-20260115-123456"  ; CUSTOM_ID of Spec section
  "Goals"                                ; Subsection name (without asterisks)
  "*** Goals\n\n- Goal 1\n- Goal 2")    ; Full content with heading

;; Update multiple subsections
(dolist (section '(("Goals" . "*** Goals\n\n- Goal 1")
                   ("Non-Goals" . "*** Non-Goals\n\n- Non-goal 1")))
  (claude-org-update-or-create-subsection
    spec-custom-id (car section) (cdr section)))
#+end_src

*** WRONG Pattern (Creates Duplicates)

#+begin_src elisp
;; WRONG - appends new section, creates duplicates!
(org-end-of-subtree)
(insert "\n*** Goals\nNew goals...")
#+end_src

** Writing the Spec

Update the Spec section with your design (using replace, not append):

*** Goals
What this feature WILL do:
- Be specific and measurable
- Focus on user outcomes
- Include success criteria

*** Non-Goals
What this feature will NOT do:
- Explicitly scope out adjacent concerns
- Prevent scope creep
- Set clear boundaries

*** Proposed Solution
High-level approach:
- Architecture overview
- Key components involved
- Integration points
- Trade-offs considered

*** Technical Design
Implementation details:
- Data structures
- API contracts
- Error handling strategy
- Testing approach

** Design Principles

1. *Follow existing patterns*: Match codebase conventions
2. *Keep it simple*: Prefer straightforward solutions
3. *Consider trade-offs*: Document alternatives considered
4. *Plan for testing*: Include test strategy

** RFC Template

#+begin_example
*** Goals

- [ ] Enable users to [specific capability]
- [ ] Improve [metric] by [amount]
- [ ] Integrate with [existing system]

*** Non-Goals

- Will NOT change existing [component]
- Will NOT support [out of scope feature]
- Future consideration: [deferred item]

*** Proposed Solution

*Overview*: [1-2 sentence summary]

*Approach*:
1. [Step 1]
2. [Step 2]
3. [Step 3]

*Trade-offs*:
| Option | Pros | Cons | Decision |
|--------+------+------+----------|
| A | ... | ... | Chosen |
| B | ... | ... | Rejected |

*** Technical Design

*Data Flow*:
1. User action → [handler]
2. [handler] → [service]
3. [service] → [storage]

*Key Interfaces*:
- =function(input): output= at =file:line=

*Error Handling*:
- [error case] → [response]

*Testing Strategy*:
- Unit tests for [components]
- Integration tests for [flows]

*** Alternatives Considered

| Alternative | Pros | Cons | Why Rejected |
|-------------+------+------+--------------|
| [Option A] | ... | ... | [reason] |
| [Option B] | ... | ... | [reason] |

*** Test Plan

| Test Type | Scope | Command |
|-----------+-------+---------|
| Unit | [components] | [e.g., npm test] |
| Integration | [flows] | [e.g., npm run test:integration] |

Key scenarios to test:
- [ ] Happy path: [description]
- [ ] Edge case: [description]
- [ ] Error case: [description]

*** Open Questions

Unresolved issues (must be answered before Planning phase):

- [ ] [Question 1] - Owner: [who], Due: [when]
- [ ] [Question 2] - Owner: [who], Due: [when]

*IMPORTANT*: All open questions must be resolved before proceeding to Planning.
#+end_example

** Human Checkpoint

Design phase is a *critical review point*:
1. Present the completed Spec to user
2. Highlight key decisions and trade-offs
3. Wait for explicit approval before Planning
4. Iterate on feedback if needed

The Spec becomes the *contract* for implementation.
