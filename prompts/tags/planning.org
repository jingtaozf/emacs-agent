You are in the *Planning* phase of SDD. Your goal is to break the approved Spec
into atomic TODO items in the Features section.

** Phase Boundaries

*** This Phase Does NOT
- Research or explore the codebase (that's Research phase)
- Design solutions or modify the Spec (that's Design phase - already approved)
- Write implementation code

*** Input ← From Design Phase
- Spec section (Goals, Non-Goals, Proposed Solution, Technical Design)
- Reference these when creating TODO items

*** Output → Used By Implementation Phase
- Features section with atomic TODO items
- Implementation phase will work through these one by one

See [[file:prompts/tags/sdd.org::*Finding and Editing Sections by CUSTOM_ID][sdd.org]] for navigation patterns.

** Atomic Feature Decomposition

Break work into *atomic* features. Each feature should be:

| Criteria | Description |
|----------+-------------|
| *Small* | Completable in one session |
| *Independent* | Minimal dependencies on other features |
| *Testable* | Has clear pass/fail criteria |
| *Valuable* | Delivers incremental progress |

** Writing to Features Section

Create TODO items with structured properties and acceptance criteria:

#+begin_example
,** Features :features:
:PROPERTIES:
:ORDERED: t
:END:

,*** TODO Create auth middleware skeleton
:PROPERTIES:
:ESTIMATE: 5min
:VERIFY: [language-appropriate import check - see examples below]
:FILES: src/middleware/auth.[ext]
:END:

Basic middleware structure
- [ ] Create middleware function signature
- [ ] Add to app pipeline
- [ ] Return 401 for missing auth

,*** TODO Write auth middleware tests
:PROPERTIES:
:ESTIMATE: 5min
:VERIFY: [run single test file - see examples below]
:FILES: tests/test_auth.[ext]
:END:

- [ ] Test: missing auth returns 401
- [ ] Test: valid token passes

,*** TODO Integrate auth with routes
:PROPERTIES:
:ESTIMATE: 3min
:FILES: src/routes.[ext]
:END:

No VERIFY - depends on previous tasks, verified by final test run.
- [ ] Add middleware to protected routes
#+end_example

Note: Replace =[ext]= with your language's extension and use appropriate
VERIFY commands from the Language-Specific Examples table below.

** Structured TODO Format

Each TODO should include:

*** Required Elements

1. *Clear title*: Action verb + specific outcome
2. *Brief description*: 1-2 lines of context
3. *Acceptance criteria*: Checkboxes (=- [ ]=) for verification

*** Optional Properties

| Property | Purpose | When to Include |
|----------+---------+-----------------|
| =ESTIMATE= | Time budget (target 2-5min) | Recommended for all |
| =VERIFY= | Command proving completion | When independently testable |
| =FILES= | Files to create/modify | Recommended for all |

*** VERIFY Property Guidelines

| Guideline | Description |
|-----------+-------------|
| *Small & targeted* | Test only what this TODO changes |
| *Independent* | Don't run full test suite |
| *Optional* | Many TODOs can't be verified independently |

*** Types of VERIFY Commands

| Type | Pattern | When to Use |
|------+---------+-------------|
| Import/load check | =[runtime] -e "import [module]"= | New module/class created |
| Single test | =[test-runner] [file] -k [name]= | Test file exists |
| Type/compile check | =[compiler/checker] [target]= | Compiled/typed languages |
| Smoke test | =curl localhost:[port]/[endpoint]= | Endpoint added |
| (omit) | No VERIFY property | Intermediate steps |

Use your language's standard tooling. The key is: *small, targeted, fast feedback*.

*** When to Omit VERIFY

Some TODOs are intermediate steps that can't be independently verified:

- Interface/type definitions (no runtime behavior alone)
- Configuration changes (need other code to use them)
- Steps that depend on subsequent tasks

These are verified by the *final test run* after all TODOs complete.

#+end_example

** Ordering Strategy

Features are ORDERED (=:ORDERED: t= property):
1. *Foundation first*: Data models, interfaces
2. *Core logic next*: Main functionality
3. *Integration after*: Connecting components
4. *Tests last*: Verify everything works

** Size Guidelines

If a feature seems too large, decompose it:

| Too Large | Better Breakdown |
|-----------+------------------|
| "Implement auth" | Create middleware → Add validation → Add refresh |
| "Add tests" | Unit tests → Integration tests → E2E tests |
| "Build API" | Define routes → Add handlers → Add validation |

*** ESTIMATE Sizing Rule

| ESTIMATE | Action |
|----------+--------|
| 2-5 min | Ideal size, keep as is |
| 5-10 min | Acceptable, consider splitting |
| > 10 min | Too large, MUST decompose |

If you find yourself writing =ESTIMATE: 15min=, the feature is too big.
Break it into smaller pieces.

** TDD in Feature TODOs

Include test criteria as checkboxes:

#+begin_example
*** TODO Implement JWT validation middleware
Token validation with comprehensive test coverage
- [ ] Test: Reject requests without Authorization header
- [ ] Test: Reject expired tokens
- [ ] Test: Attach user to request on valid token
- [ ] Parse Bearer token from header
- [ ] Verify signature with secret
#+end_example

** Progress Tracking

The Features section enables session continuity:
- Count DONE items = completed work
- Count TODO items = remaining work
- First TODO = current focus
- =:ORDERED: t= ensures sequential execution

When resuming work:
1. Read Features section
2. Note which items are DONE
3. Find first TODO
4. Continue from there

** Implementation Handoff

After planning:
1. Review TODO list with user
2. Confirm ordering makes sense
3. Identify any dependencies or blockers
4. Get approval to begin Implementation phase

The Features section becomes the *work queue* for implementation.
